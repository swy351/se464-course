Security: Trust, Identity and Access

Week 10 · November 11

Define trust boundaries, protect credentials, and separate authentication from authorization.

Policies, threats and the guard

Imagine a document service where a student successfully logs in and requests another student's private submission. Authentication can correctly identify the requester while the requested read must still be denied. Put a guard before the document operation: it receives the authenticated identity, the action, and the specific document. The policy might permit the owner and assigned marker to read, but nobody else. Draw those inputs separately so identity is not mistaken for authority. Confidentiality is violated if the read succeeds incorrectly; integrity is violated if an unauthorized edit succeeds. Availability asks whether legitimate readers can still obtain access. A useful threat model specifies which requests an attacker can send and which boundaries the system promises to enforce.

Security begins with an explicit policy: who may perform which actions on which resources. A threat model states what an adversary can observe, control or compromise. Confidentiality protects information from unauthorized disclosure, integrity protects permitted changes, and availability protects legitimate access. Attacks are adaptive rather than independent random failures, so one unguarded path may defeat otherwise reliable components.

A permission check can be undermined if later code lets untrusted input rewrite the operation being checked. Suppose a profile query is intended to select only public records. If the application builds SQL by joining strings, hostile input may alter the query's condition instead of remaining a value. The guard may have approved a public-profile lookup while the database executes a broader query. Parameter binding keeps the query structure fixed and supplies input as data. The architectural lesson extends beyond this example: validate the operation that actually reaches the protected resource, and avoid alternate paths that skip mediation. Test a denied request, a malformed request, and an allowed request so the evidence covers the boundary rather than only successful use.

The guard model places a decision before protected operations. Identify the requester, protect the request against modification, and check permission for this resource and action. The SQL example shows why a check is insufficient if untrusted input changes the query structure: a public-profile condition can be bypassed by altered logic. Parameterized queries preserve the distinction between data and commands. Security confidence comes from bounded evidence, not a claim that no defect can exist.

Predict: If a profile query checks that a user is signed in, may it return any profile requested by that user?

No. Authentication identifies the requester; authorization must check permission to view the selected profile and fields.

Security principles as architecture decisions

A backup worker needs to read production data and create a protected copy. Giving it the administrator account also lets it delete production records, disable auditing, or erase every backup. Those powers are unrelated to its purpose. Draw separate credentials for reading production and writing a backup destination, then remove deletion rights where the workflow does not need them. If an attacker compromises the worker, the remaining damage is bounded by those permissions. Least privilege is therefore a design decision about component responsibilities and interfaces, not merely a checkbox on an account. Follow the recovery path too: a backup is useful only if the recovery process can access a trustworthy copy after the production system is compromised.

Least privilege limits the power of each component. Fail-safe defaults deny access unless it is granted. Economy of mechanism favors security logic that can be understood and reviewed. Complete mediation asks where each access decision is enforced and what happens when permissions change. Open design assumes an adversary can understand the mechanism; cryptographic keys and other credentials still need secrecy.

Consider an authorization service that is temporarily unavailable. If an application interprets a timeout as permission, an outage becomes an access bypass. A fail-safe design rejects the protected operation or uses an explicitly bounded, previously authorized decision whose freshness rules are understood. Complete mediation requires examining every route, including batch jobs and internal APIs, rather than protecting only the public page. Defense in depth then adds independent boundaries: a narrow service identity, network restrictions, and storage permissions can still constrain damage when one check fails. These controls must remain understandable to operators. A complicated emergency procedure that routinely requires disabling all checks creates an operational weakness even if the normal architecture diagram looks secure.

Separation of privilege makes sensitive actions depend on multiple conditions, while least common mechanism reduces unnecessary sharing across protection domains. Psychological acceptability makes secure behavior practical for users and operators. Defense in depth combines independent barriers, such as authentication, restricted service permissions and isolation. Apply these principles to the backup example: reading backup data should not automatically imply permission to erase production files. Describe failure behavior and recovery instead of merely listing controls.

Predict: A backup job needs to read production files. Should it run with unrestricted administrator privileges for convenience?

No. Grant the narrow read and destination-write privileges it needs, and separate restore or delete authority where practical.

Passwords, hashes and protected transport

Suppose a database leak exposes account records. If the records contain plain passwords, the attacker can immediately try them on other services where people reused those passwords. Password verification should instead compare against a dedicated password-hashing result with a unique salt per account. During login, the server repeats the configured calculation using the submitted password and stored salt. The salt is not a secret replacement password: its role is to prevent one reusable precomputed result from serving many accounts. An expensive password-hashing function increases the work required for offline guesses. Rate limiting helps with guesses sent through the login endpoint, but it cannot control an attacker computing guesses independently from a stolen verifier database.

Authentication establishes control of an authenticator associated with an account; it does not automatically prove a legal identity or grant permission. Enrollment binds the authenticator to the account, and later verification checks it. Knowledge, possession and inherence describe different factor categories. HTTPS protects traffic in transit when peer identity and the connection are verified, but application logs and compromised endpoints remain outside that protection.

Trace a password from the browser to the login service over HTTPS. Transport protection prevents an observer along that connection from simply reading or changing the request, provided the peer and connection are correctly verified. Once the request reaches the application, however, the plaintext password may be available to its code. Logging the entire request can copy that secret into another system with different access controls and retention. Requiring the password on every API operation multiplies these opportunities and forces the client to keep a powerful long-lived secret available. Authenticate through the login workflow, then use an appropriately protected session credential for later operations. Transport security, secret handling, and account verification solve different parts of the same journey.

Never store account passwords as plain text or treat a fast general-purpose hash as sufficient password storage. A dedicated password-hashing function with a unique salt makes stolen verifier data more expensive to guess. Salts defeat reusable precomputed tables, not guessing itself. The course examples contrast online guessing, which can be rate-limited, with offline guessing after a database leak. Repeating a password in every API request unnecessarily spreads a valuable long-lived secret.

Predict: Does adding a unique salt make a weak password impossible to guess after the verifier database is stolen?

No. The attacker can still test guesses against each verifier; a suitable password-hashing cost raises the work per guess.

Sessions, cookies and phishing resistance

After a successful login, the backend generates an unpredictable session identifier and stores its association with the user and expiry. The client sends that identifier on subsequent requests. In a feed request, the API first translates the token into a user identity, then reads the feed for that identity; it should not trust a separately supplied username as proof of ownership. A cookie can carry the identifier automatically for a browser, while another client may use an authorization header. These are transport choices around the same underlying session idea. Revoking the session invalidates that credential without changing the user's memorized password. The token is still a secret: possession can be enough to impersonate the session while it remains valid.

After authentication, an application can issue an opaque random session identifier and keep its meaning on the server. A browser cookie is one transport and storage mechanism for that identifier. Alternatively, a server can authenticate structured claims using a standard message-authentication or signature scheme. A plain hash of public fields proves nothing about their issuer; inventing a keyed-hash construction is not a substitute for a reviewed protocol.

Now place a cache in front of session verification so every API request does not make another network round trip. Performance improves, but a session revoked at the authentication service may still be accepted by a cache holding an older decision. Choose a bounded lifetime or invalidation mechanism that matches the harm of stale authorization. A temporary browsing session and an administrator action may require different policies. Keep tokens out of ordinary URLs because request paths often reach histories, logs, and monitoring systems. A second factor adds another check, but recovery must protect the same account: a weak reset process can bypass a strong login. Evaluate both normal access and credential loss as complete workflows, including revocation and renewed authentication.

Treat bearer sessions as credentials: whoever steals one may use it until expiry or revocation. Protect transmission, avoid secret-bearing URLs, and design logout, rotation and recovery. A central authentication service changes dependency and caching tradeoffs; cached decisions need a freshness policy. The slides also motivate phishing resistance, but hashing a password with a challenge alone does not provide it. Account recovery and additional factors must be evaluated against the same threat model as login.

Predict: Would adding H(username | expiration) to a cookie stop a client from changing the username?

No. Both the fields and hash algorithm are public, so the client can recompute the hash. Use a standard authenticated token or an opaque server-side session.

Authorization: lists, capabilities and labels

A shared document can authorize access by consulting a list: the guard identifies the requester and checks whether that identity may read the document. A capability-style design instead gives a principal an unforgeable reference carrying narrowly defined authority, such as permission to download one object until a deadline. Presenting the valid capability proves that authority under the scheme's rules. Draw where the policy lives in each case. With a list, changing one central entry can affect future checks. With a copied ticket, revocation may require short expiry, an online revocation check, or another explicit mechanism. Neither design is automatically safer; the choice depends on delegation, sharing, and how quickly permission changes must take effect.

Authorization decides whether an identified principal may perform a particular action on a particular object. In a list-based model, the guard consults permissions associated with identities. In a capability-style ticket model, possession of a valid unforgeable authority-bearing reference grants defined access. The distinction changes delegation, revocation and what a verifier must store. A ticket must not be confused with a printable string anyone can forge.

Suppose an export service must let a browser download one generated report. Giving the browser the service's storage administrator credential would expose unrelated files and future operations. Instead issue authority limited to that report, the download action, and a short validity period. If the user shares that ticket, the recipient may gain the same limited authority, so this sharing behavior must be intentional. Contrast this with mandatory labels: a centrally defined policy can prevent a document owner from granting access outside an approved classification boundary. A hybrid can authenticate the user against organizational policy and then issue a narrow capability for delivery. Trace who can create, copy, inspect, and revoke authority at every stage of that workflow.

Discretionary control allows designated owners to manage access, whereas mandatory control enforces centrally defined policy, often using security labels. Every access-control scheme is policy-based in a broad sense, so that phrase alone does not distinguish mandatory control. Hybrid designs are common: an identity check can issue a short-lived capability for a narrowly scoped action. Trace how permissions are added, delegated and withdrawn, including copies and cached decisions.

Predict: Why can revoking a transferable ticket be harder than removing a principal from an access list?

The ticket may have been copied or delegated. Revocation needs expiry, a revocation check, indirection or replacement of the authority accepted by guards.

Impersonation, replay and trust

Imagine a valid approval message for transferring ten dollars. An attacker captures it and submits it twice. The signature or authentication code may still verify because the contents are genuine; that check alone does not establish that this is a new authorized action. Include an operation identifier, bind the approval to its intended recipient and purpose, and define whether repeated delivery returns the same result or creates another transfer. An expiry limits the usable time window but does not by itself prevent two uses within that window. Freshness, origin, integrity, and authority are separate claims. The protocol must state which evidence supports each claim rather than using the word authenticated as shorthand for all of them.

An authenticated-looking message can still be dangerous if its credential was stolen or its valid contents are replayed at the wrong time. Distinguish origin, integrity, freshness and authority. A legitimate old approval may not authorize a new purchase. Protocols therefore need explicit rules about challenges, expiration, audience and whether an operation can be repeated safely. Compromised keys change the trust assumptions rather than merely producing another bad input.

A login challenge can be sent through an already registered channel to test control of that channel. The challenge must be unpredictable, bound to the relevant attempt, and accepted under explicit expiry and reuse rules. If an attacker controls the recovery mailbox, that control may undermine the protection expected from the login flow. Likewise, a service's good reputation is evidence about past behavior, not a credential authorizing a particular action today. In a collaborative marketplace, reputation might determine how urgently a transaction is reviewed, while access to private records still follows an enforceable policy. Separate confidence in a participant from validation of this message, this account, and this requested effect. Otherwise a favorable history can become an accidental bypass around concrete controls.

The slides broaden the discussion to misrepresentation, collusion, fraudulent actions and unknown participants. Trust is a contextual expectation; reputation is evidence from past behavior. Neither replaces enforceable permissions or proof that a specific message is valid. Credential-and-policy systems and reputation-based systems answer different questions. In a collaborative service, a strong reputation might influence review priority while a resource access decision still follows explicit authorization rules.

Predict: Can a valid signature alone prove that a request has not already been used?

No. Signature validity does not establish freshness or uniqueness; the protocol needs replay controls appropriate to the action.

Browser isolation and the patching lifecycle

A browser renders pages supplied by parties the user does not control. Suppose a malicious page exploits a renderer bug. If the renderer runs with broad access to local files, the exploit can immediately become a data theft problem. A restricted renderer process changes that consequence: privileged operations must cross a boundary to a component that can enforce policy. Draw the boundary between rendering content and accessing sensitive operating-system resources, then label the allowed messages. The design assumes defects may exist and tries to limit what a successful exploit can reach. It does not make malicious content harmless, nor does it prove the boundary implementation is correct. Evaluate both the compromise and the attempted next step beyond the compromised component.

A browser processes content from many parties, so architecture should limit the damage if a parser or renderer is compromised. The historical Chrome case separates a more privileged browser component from restricted rendering processes. Sandboxing and site isolation establish boundaries, while mediated communication allows only selected operations across them. A boundary limits consequences; it does not prove the code inside is free of vulnerabilities.

Once a vulnerability is known, a patch can remove the specific defect while isolation continues to limit damage from other defects. The patch must reach users, so distribution and adoption time matter as much as producing a corrected binary. Regression checks help establish that the fix works without breaking expected behavior. Dangerous-site warnings address a different point in the chain by reducing exposure to known hostile destinations. Draw prevention, containment, and repair as separate stages rather than treating them as interchangeable controls. The detailed browser process topology changes across versions, so use the historical architecture as an example of reasoning about privilege boundaries. The enduring question is what the attacker can do after one layer has failed.

Other measures address different parts of risk. Updates shorten the period in which a known vulnerability remains exposed, and tests help check both the fix and regressions. Dangerous-site warnings reduce encounters with known threats. These mechanisms evolve: the slide-era process and Safe Browsing lookup description should be labeled historical. Connect each control to confidentiality, integrity or availability, and ask what remains possible if one layer fails.

Predict: Why keep sandboxing if the team rapidly patches every reported renderer bug?

Bugs can be exploited before discovery or update installation. Isolation limits consequences during that exposure window.

Self-check

A student is authenticated but requests another student’s unpublished grades. Which decision is still required?

Object-level authorization must deny access unless the policy explicitly grants it; authentication alone is insufficient.

What does a unique salt accomplish, and what does it not accomplish?

It prevents reusable precomputed password tables and identical verifiers for identical passwords. It does not prevent per-account offline guesses; a suitable password-hashing scheme and strong credentials remain necessary.

A file permission is revoked while a process holds an already opened descriptor. What architectural question does this expose?

Whether revocation affects existing authority or only future opens. State the revocation semantics and avoid assuming a cached authorization decision always reflects current policy.

Design exercise

Design access to a course grade service. Students read their own grades, instructors update grades for their courses, and a backup job reads records. Mark guards, identities, permissions and durable state. Then explain password-verifier theft, session theft and instructor-access revocation without running any attacks.

Place authorization before each grade read/write and bind it to course and student identifiers. Give students self-read, instructors course-scoped update, and backup read-only authority. Store password verifiers with a dedicated salted hashing scheme, use protected expiring sessions, and define logout/revocation behavior. Separate authentication from permission checks, minimize credential logging, and document how cached decisions and existing sessions react to role changes.

Additional practice

Questions-only worksheet · Worked answer sheet

1. Recovery must not bypass the guard

A document-sharing service loses connectivity to its authorization database. Engineers suggest temporarily allowing any authenticated account to download a document if it knows the document ID, arguing that IDs are difficult to guess and this preserves availability. The documents include confidential contracts. Which response best follows fail-safe defaults without confusing authentication with authorization?

  1. Deny protected downloads without established permission and preserve permitted public operations.
  2. Allow access only for long document IDs.
  3. Allow downloads because authentication proves all necessary permission.
  4. Log every unauthorized download and approve it automatically.

Worked answer

Best answer: A.

Deny protected downloads when permission cannot be established, while returning an appropriate temporary-failure response and allowing genuinely public operations to continue. Authentication establishes an account context, not permission for every document, and hard-to-guess identifiers are not a replacement for the intended authorization policy. A previously established bounded authorization cache could be considered only if its freshness and revocation risk were explicitly accepted in advance. The outage should trigger operational recovery, not an improvised expansion of privileges. Availability matters, but this proposed fallback changes the confidentiality policy precisely when the guard cannot evaluate it.

Fail-safe defaults require an explicit grant, not a guess that a requester probably has one. A degraded mode must be designed against the actual security policy.

Check your work

  • Choose fail-closed protected access.
  • Separate public availability from confidential authorization.
  • Reject secret-looking IDs as substitute permissions.

2. A one-use export ticket

A research archive wants to issue a download ticket for one restricted dataset. The ticket should work for ten minutes and permit only one completed export. Workers are stateless, and the ticket is signed by the archive. Two requests carrying the same valid ticket arrive at different workers simultaneously. Explain why signing and expiry are insufficient and design the shared decision needed to enforce the one-use requirement.

Worked answer

The signature protects ticket integrity and the expiry limits its time window, but both concurrent requests can satisfy those checks. Give the ticket a unique identifier, bind it to the intended dataset and operation, and atomically claim or consume it in authoritative shared storage. Define what counts as completed export and how an interrupted transfer resumes without creating a second authorization; a short-lived claimed state or a stable export job can separate retries from new consumption. Enforce account binding if the policy requires it. Document whether revocation is checked before use and how failure between claiming and delivery is recovered.

A stateless verifier can validate a signature but cannot independently know whether another worker consumed the same ticket. The one-use invariant needs coordinated state or an equivalent authority.

Check your work

  • Distinguish authenticity/expiry from replay prevention.
  • Use atomic shared consumption and scope binding.
  • Define retry and interrupted-delivery semantics.

3. Diagnostics with bounded authority

A customer-support team needs enough diagnostic data to investigate failed file uploads. A proposed debug endpoint returns environment variables, request headers and the last 500 log lines, and runs under the same account that can delete stored files. Design a narrower diagnostic interface. Identify one confidentiality risk, one integrity risk and one availability risk, and specify useful information support can still obtain.

Worked answer

Expose a bounded, structured report with correlation IDs, sanitized error categories, timestamps, upload sizes and relevant service status. Redact credentials and sensitive content from headers, logs and environment data to address confidentiality. Run report generation with read-only, scoped access rather than file-deletion authority, reducing integrity risk. Bound report size, query cost and request rate so repeated diagnostics cannot exhaust the service, addressing availability. Authorize access to the relevant customer or case, audit sensitive report requests and define retention. Keep deeper privileged investigation behind a separate controlled workflow instead of expanding every support session’s authority.

This design applies least privilege to both data disclosure and execution authority. Bounded work prevents a troubleshooting feature from becoming an uncontrolled resource consumer.

Check your work

  • Identify concrete CIA risks.
  • Preserve useful sanitized diagnostics.
  • Limit authority and resource consumption.
