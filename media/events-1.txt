Delivery, ordering and poison messages

A subscriber records an experiment-completed event and then sends a researcher a notification. If it crashes after sending but before recording progress, a retry can send the notification again. Repeated delivery and repeated business effects are different issues: a stable event identifier lets the handler recognize a prior effect only when the relevant state is recorded with an appropriate consistency rule. Simply labelling the handler idempotent does not establish that rule. Now deliver result version three before version two. Duplicate detection alone cannot prevent an old version from overwriting a newer result. Define ordering per experiment or reject obsolete updates using their version. When a malformed event repeatedly fails, bound retries and retain enough information for diagnosis and controlled replay. Monitor subscription age as well as message counts so a small set of stuck events is visible. These decisions belong to the consumer contract and broker configuration; a distributed delivery system does not offer one universal ordering or exactly-once guarantee for every downstream effect.


ROS as an architectural example

The robotics example organizes computation into nodes with typed messages. Topics carry streams such as sensor readings, services provide request-and-response interactions, and actions support longer goals with progress and a final result. These interfaces let sensing, planning, control and visualization evolve separately while still communicating through explicit data contracts suited to their interaction patterns and timing needs.
