Scalability, services & HTTP

Move from a program to a concurrent service, identify resource limits, and trace an HTTP request through a web application.

Source: [Week3.1]scalability_web_http.pptx. Generated companion; original slides unchanged.

From programs to services

Source slides 1–6

An algorithm solves a problem for an input; a service repeatedly accepts requests from users. Complexity still matters, but a fast individual request does not guarantee a healthy service under many simultaneous requests. Requests compete for CPU, memory, disks, network capacity and shared data. Measure throughput together with latency and errors, and specify the workload.

Concurrent users describe how much activity overlaps, while requests per second describe a rate. Monthly active users describe audience size and say little about a sudden burst. As an example, a registration portal can have modest daily use but a large opening-minute surge. The architectural question is whether it can absorb that surge while keeping response times and correctness acceptable.

Predict: If a service doubles its throughput but response time grows tenfold, has it necessarily scaled successfully?

No. Throughput alone hides queueing and user experience; the result must meet a stated latency and error target.

Scaling up and scaling out

Source slides 7–13

Vertical scaling adds capacity to an existing machine: more memory, faster storage or more CPU resources. Horizontal scaling adds machines. The first often keeps coordination simpler; the second opens more capacity but requires work distribution, shared-state management and failure handling. Neither guarantees proportional improvement. The bottleneck determines whether the next resource is useful.

Threads can overlap IO waits even on a single CPU core. A blocked worker is waiting rather than performing useful CPU work, allowing another to run. CPU-bound tasks need actual execution resources for parallel speedup. Before buying capacity, inspect whether work waits for storage, exhausts CPU, competes for memory or contends on shared locks. A larger machine cannot remove every architectural limit.

Predict: Will doubling CPU cores necessarily halve request latency?

No. IO waits, serial work, locks and external dependencies can dominate.

Request processing and HTTP

Source slides 14–23

A service framework accepts network messages and routes them to application logic. The slide worker loop takes a request from a queue, performs work and queues a response. Empty queues can block readers; full bounded queues can block producers or trigger rejection. These details matter during overload: unlimited waiting can consume memory and create unacceptable response times.

HTTP defines request and response semantics. A request includes a method, target and fields, and may include content. A response includes status and fields and may include content. The textual example illustrates HTTP/1.1. Frameworks can implement concurrency using threads, processes or asynchronous event handling; the request-response contract does not require one specific execution model.

Predict: What happens if requests enter faster than workers can finish them for a sustained period?

The queue grows unless bounded; latency rises, and a bounded system eventually rejects or slows arrivals.

A Wikipedia request, end to end

Source slides 24–34

In the supplied historical Wikipedia example, the browser requests an article and MediaWiki produces HTML. The application retrieves wiki text, converts it to markup, adds page structure and may add a personalized header. The database stores durable article data while application instances execute rendering logic. This separation explains why the system has more than just a web server.

Trace which work repeats across readers. The article body may be shared, but identity-dependent content may differ. That distinction motivates the next unit on caching and stateless workers. The historical architecture diagram is a teaching model rather than an inventory of current Wikimedia infrastructure. Repeated diagram-build slides can become one step-by-step request walkthrough with each component highlighted in turn.

Predict: Can the entire personalized HTML response always be reused for another visitor?

No. Shared article content and user-specific response content require different reuse policies.

Self-check

A server spends most request time waiting for disk. Why can multiple workers help even on one CPU core?

While one worker blocks on IO, another can use the CPU. This improves utilization without parallel CPU execution.

Adding 8 app servers gives little improvement because every request waits on one shared database. What is the implication?

Horizontal app scaling moved neither the database capacity nor its contention bottleneck. Measure and address that shared resource.

Trace a wiki page request through the uncached design.

Browser sends HTTP request; MediaWiki reads wiki text from the database, renders and wraps HTML, adds request-specific content, then returns an HTTP response.

Design exercise

A portal receives 15 requests per second. Each worker can process 5, but all requests use a database capped at 12. Describe the effect of moving from two to four workers, and propose a measurement plan.

Two workers cap ideal throughput at 10; four workers move the cap to the database at 12. At a steady arrival rate of 15, the queue continues to grow. Measure throughput, tail latency, errors, CPU, database wait time, and query costs under a reproducible workload. Consider reducing database work and controlling admission before adding further workers.

1. Replicate work or remove work?

A rendering service runs on one machine with eight CPU cores. Each request uses 40 ms of CPU and no significant I/O. At 180 requests/s, CPU use is roughly 90%. A proposal doubles the number of worker processes on the same machine without adding cores or changing request work. Which prediction is best justified for sustained throughput, ignoring scheduler overhead for the estimate?

  1. Throughput must double because worker count doubles.
  2. Throughput falls to zero because workers cannot share cores.
  3. The ideal CPU bound remains about 200 requests/s.
  4. The machine can sustain unlimited requests if its queue is unbounded.

Worked answer

Best answer: C.

The same eight cores provide at most eight CPU-seconds per second. At forty milliseconds per request, the ideal CPU capacity is 8/.040=200 requests/s, so 180 requests/s consumes 7.2 CPU-seconds/s, or 90%. More worker processes may alter scheduling but cannot double this CPU budget. Additional cores, lower per-request work or reduced offered work can raise the bound. Real capacity may be lower because of scheduling, synchronization and other overhead, so the calculation is an upper-bound model rather than a guaranteed throughput.

Workers expose concurrency, while cores provide execution capacity for a CPU-bound workload.

Check your work

  • Computes the resource capacity bound
  • Separates worker count from CPU capacity

2. Rolling deployment with local conversation state

A customer-support service has four application instances. Each holds a conversation draft only in local memory, and a load balancer uses sticky routing. Operators want to replace all instances one at a time without losing drafts or interrupting ongoing conversations. Propose a migration sequence and failure test. Explain why sticky routing alone does not satisfy the deployment requirement, even if ordinary traffic remains correctly routed.

Worked answer

Introduce an authoritative shared draft store with versioned updates, then migrate active drafts before relying on replacement instances. A transitional release can persist drafts and read shared state while retaining compatibility with old clients. Drain an instance from new traffic, finish or transfer active work, verify persistence and then terminate it. Sticky routing only selects a process; it does not preserve that process’s memory. Test abrupt termination during an acknowledged draft update and require another instance to recover the acknowledged version without overwriting a newer edit.

Deployment continuity is a state-ownership and update-semantics problem as well as a routing problem.

Check your work

  • Provides an ordered migration and drain plan
  • Explains sticky-routing limitation
  • Tests abrupt failure and version preservation

3. Estimate bandwidth before buying compute

A download portal must serve 90 files per second during a launch. Each response transfers exactly 2 MB, using decimal units. The application has ample CPU, but its outbound link is limited to 1 Gbit/s; ignore protocol overhead. Calculate whether the link can sustain the load. A compressed representation averages 1.2 MB and takes an extra 3 ms CPU per response. Evaluate the bandwidth effect and identify the next measurement needed.

Worked answer

The original traffic is 90×2=180 MB/s, or 1,440 Mbit/s, exceeding the 1,000 Mbit/s link. Its ideal link-limited capacity is 125 MB/s divided by 2 MB, or 62.5 responses/s. Compression lowers demand to 108 MB/s=864 Mbit/s, which fits the ideal link budget but leaves limited overhead margin. Its added CPU demand is 90×.003=.27 CPU-seconds per second. Measure actual transfer sizes, protocol overhead, compression CPU and burst behavior to verify that the new bottleneck has not moved elsewhere.

Scaling choices should address the limiting resource; adding application workers cannot widen a saturated network link.

Check your work

  • Converts units and identifies the initial bottleneck
  • Computes compressed load and CPU demand
  • Names relevant validation measurements
