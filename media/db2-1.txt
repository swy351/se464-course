Distributed data & consistency
Illustrated lesson · Part 2 · Synthetic narration

Session guarantees — Reading backward in time

Consistency becomes easier to discuss when we describe an actual user's sequence of operations. Monotonic reads means that after a session observes a version, a later read does not go backward to an older version. Read-your-writes means that after the session completes an update, its later reads include that update or a later one. These promises are different. A user who has never written anything can still suffer a nonmonotonic read when requests alternate between a current replica and a lagging one. A user who saves a profile can fail to read their own write even if every subsequent read consistently returns the same old version.

Session guarantees — Carry a minimum observed version

Draw two read arrows from one client: the first reaches A at version eight, and the second reaches B at version seven. That is a monotonic-read violation. Then replace the first arrow with a completed write of version eight: the same stale second response violates read-your-writes. Routing the session to one sufficiently current node can help, but the promise must survive reconnection and failover. A session can carry a minimum version or replication position that a new node must satisfy. Waiting until that position is applied preserves the promise at the cost of delay; accepting an older response preserves immediate availability at the cost of the promise. The system needs to choose deliberately.

Quorums and their limits — Two read responses intersect two writes

A quorum is a threshold of replica responses required before an operation is treated as complete. With three replicas, consider writes acknowledged by two and reads answered using two. If A and B acknowledged a completed write, any set of two read responders must contain A or B. The overlap is the essential arithmetic: R plus W greater than N guarantees intersection between the selected read set and the acknowledged write set, under a stable replica membership. It does not mean the two read values must be identical. A read can receive one older value and one newer value, so the system still needs meaningful version information and a reconciliation rule.

Quorums and their limits — Thresholds change failure behavior

Change the thresholds to see the workload tradeoff. With W equal to three and R equal to one, a completed write has reached every replica, allowing a subsequent read to use a single response under the model's assumptions. But the write must wait for the slowest required participant, and one unavailable replica prevents completion. With W and R both equal to two, one unavailable replica can still leave enough responders for both kinds of operation. This is a latency and failure-policy choice, not just a consistency switch. The relevant replicas belong to this key; another key may have a different replica group and remain unaffected by the same failed machine.

Stronger consistency and synthesis — Completion constrains a later read

Begin with an observable history rather than a product label. A user completes an update to a shared register and then another user starts a read. Linearizability requires that read to behave consistently with a single order in which each operation takes effect at one instant between its invocation and response. Real-time precedence matters: an operation completed before another began must appear earlier in that order. Operations that overlap may admit more than one order. This is stronger than merely preserving each client's own sequence. A diagram should therefore show request and response intervals, not just a list of values with no indication of when clients were told an operation had finished.

Stronger consistency and synthesis — Separate three architectural decisions

Compare that promise with a replicated social display. One session may always read its own updates and never move backward, while another session still sees a previous version. Those session guarantees can make the interface understandable without creating a globally linearizable object. Conversely, a linearizable single-key operation does not automatically make a transaction spanning several keys serializable. The design question is which unit of state needs which guarantee. For a shared reservation count, ordering updates may be essential; for a cached display of recent activity, bounded or eventual freshness may be acceptable. Naming the guarantee prevents students from treating every successful quorum read as proof of the strongest possible model.
