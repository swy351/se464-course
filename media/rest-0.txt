HTTP as an API contract — An interface hides implementation

A network API plays the role of an interface between programs that do not share a process. The caller needs to know what operation is available, how to supply its inputs, and how to interpret success or failure. It should not need to know the implementation language or internal database schema. Consider a weather service: a client requests a forecast for a named location, and the service returns structured data with a documented meaning. This example distinguishes the resource identifier, request parameters, and response representation. These pieces form a contract that lets a browser application, a mobile application, or another backend use the same service independently of its implementation.

HTTP as an API contract — Success and failure are contracts

HTTP provides an existing envelope for that contract. A request selects a target and method, supplies fields such as authorization or accepted media types, and may carry a body. The service responds with an appropriate status and a representation whose content type tells the client how to decode it. For a forecast endpoint, a successful JSON response and an unknown-location error are different documented outcomes. This example branches on the service's result rather than assuming every response contains usable forecast data. A client that ignores status and attempts to parse every body as a forecast can turn a clear service error into a confusing application failure.

Retries and resource identity — A lost reply makes writes uncertain

A client sends a write and waits, but the connection fails before it receives a response. The server may have completed the write; the client simply cannot tell. Retrying can therefore repeat an operation that already happened. Compare two ways to create a document. A PUT to a client-chosen identifier replaces the representation at that identifier, so repeating the same intended operation has the same effect on that resource. A POST to a collection may ask the server to allocate a new identifier each time, creating two documents after a retry. Follow the lost response, then contrasts the stable target with two newly allocated targets.

Retries and resource identity — Remember one result per key

The important distinction is the intended effect, not whether repeated responses have identical bytes or status codes. Deleting an existing resource and deleting it again can leave the same final absence even if the second response reports that nothing was found. A safe read does not request a state change; an idempotent write can request a change whose repetition has the same intended effect. For an operation such as charging an account, the API can define an idempotency key and atomically associate that key with one accepted result. Here, we see a repeated key returning the recorded result rather than initiating a second charge, provided the documented retention and parameter rules are satisfied.
