Stateless services, proxies & caches
Part 1 • Synthetic narration

Where does state live?

A bicycle rental application remembers an unfinished booking in worker A’s memory. The customer’s next request reaches worker B, which has never seen the booking. Both workers run identical code, but they are not interchangeable for this interaction because their retained information differs. Calling the protocol HTTP does not remove that dependency: application state can exist above a stateless request protocol. Identify the information needed for the next operation and locate its authoritative copy. A stateless worker may still read changing data and perform writes. For example, it can accept a booking identifier, load that booking from shared storage and update it there. The worker does not need the customer’s previous requests to have visited that same process. This distinction separates deployment statelessness from a mathematical pure function. To test your design, replace the worker between consecutive requests. If another healthy worker can continue using the request and shared services, the application has avoided a hidden dependency on the original process.


Stateless workers with stateful data

Move the bicycle booking into shared storage, and a replacement worker can retrieve it after a restart. That improves replaceability but exposes a second question: what if two workers reserve the final bicycle concurrently? If both read availability before either writes, each may believe the reservation is valid. Shared storage solves access to a common record; a suitable atomic operation or version check must also protect the booking rule. For example, worker A reads booking version 12, while worker B changes it to version 13. A conditional update based on version 12 should now fail rather than silently overwrite B’s change. The application can reload and explain the conflict. A session cookie can identify the customer whose request is being processed, but it does not itself enforce inventory correctness. Explain these responsibilities separately: the request carries identity or a session reference, shared storage retains durable state, and the update protocol decides which concurrent change is accepted.
