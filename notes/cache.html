Stateless services, proxies & caches

Make worker state explicit, understand intermediary roles, and reason about cache hits, eviction, and stale data.

Source: [Week3.2]cache_proxie.pptx. Generated companion; original slides unchanged.

Where does state live?

Source slides 1–12

State is information retained across operations. A worker with local session or game state cannot automatically be replaced by any other worker, because another instance may lack that information. The SMTP conversation illustrates a protocol interaction whose later commands depend on earlier commands. A self-contained HTTP request provides a useful contrast, but HTTP applications can still maintain state.

A stateless application worker does not require durable per-client memory in that specific worker between requests. It may consult a changing database or perform writes. This is different from a pure function: stateless deployment does not imply deterministic output or absence of side effects. Locate the state explicitly before deciding whether a request can move to a different instance.

Predict: If two stateless workers read a database at different times, must they produce identical responses to the same URL?

No. Shared data, time or randomness can change; statelessness concerns worker-local conversational state.

Stateless workers with stateful data

Source slides 13–21

The chess example begins with games stored in an application dictionary. Replicating the process produces separate dictionaries, so a player must reach the instance holding the game. If that instance fails, its in-memory games may be lost. Moving authoritative game data to shared storage allows another application instance to continue a request.

This moves coordination rather than eliminating it. Two concurrent moves need validation and an atomic or version-checked update. The shared database may become a capacity or availability bottleneck. Cookies similarly carry information with a request, often an opaque reference to session data. Signed claims can be verified without a lookup, but signing does not hide their contents or solve every expiry and revocation problem.

Predict: Does moving a chess game to a database by itself prevent two concurrent moves from overwriting each other?

No. The update must enforce the game rules with appropriate transactions, conditions or version checks.

Proxies and cache hits

Source slides 22–28

A proxy forwards requests to another component and returns responses. A caching proxy can sometimes answer using a saved representation; a load-balancing proxy selects among backends. These roles can coexist but are distinct. The intermediary itself needs capacity and availability planning, even if forwarding costs less than generating a dynamic page.

A cache hit avoids an expensive fetch; a miss obtains the value from backing storage and may insert it. Eviction frees space when capacity is limited. LRU evicts the least recently accessed entry, so an access trace lets you predict behavior. In cache-aside designs application code manages lookup and fill; transparent designs hide these steps behind the normal data-access interface.

Predict: With capacity two, after accesses A, B, A, which item does inserting C evict under LRU?

B, because A was accessed more recently.

Popularity, freshness and HTTP caching

Source slides 29–34

Skewed demand makes caching powerful: a small popular set can account for much of the request volume. The long tail contains many rarely requested items. A high hit rate depends on workload, cache capacity and freshness policy; it is not guaranteed by adding a cache. Personalized or rapidly changing content can limit safe reuse.

Writes make saved copies potentially stale. TTL bounds freshness only under its assumptions; invalidation needs reliable delivery and race handling; immutable versioned names avoid overwriting the same representation. HTTP adds explicit caching controls. Distinguish no-cache, which permits storage but requires validation before reuse, from no-store. Private responses must not become shared-cache answers for other users.

Predict: Can a cache with a 95% hit rate still be incorrect?

Yes. A high hit rate can serve stale or identity-inappropriate data; correctness and hit rate are separate.

Self-check

A chess move is handled by a different app instance from the previous move. What must the design guarantee?

The new instance must access authoritative game state and apply the move atomically or with version checking. Stateless workers alone do not prevent conflicting moves.

An initially empty two-entry LRU cache receives A, B, A, C, B. How many hits occur?

One hit, on the third access A. C evicts B; the final B is a miss.

Why must a shared cache not reuse Alice's personalized wiki header for Bob?

The representation depends on identity. Use correct private/no-store policy or safe cache key and variant handling; URL equality alone is insufficient.

Design exercise

A public course page and a private student-results page share an application. Design a caching policy and explain what happens when a course description changes.

Cache public responses only when their freshness and variation rules allow it. Keep personalized results out of shared caches unless a carefully designed private partitioning scheme permits it. Define TTL, validation, or invalidation for updated course content. Versioned immutable assets simplify cache reuse. Include cache keys, user identity, and stale-content tolerance in the design.

1. A cache that increases failure load

A train timetable API caches one popular route for sixty seconds. At expiry, 500 requests arrive nearly together; every request independently fetches the same route from the database before storing it. The database becomes overloaded although the long-run cache hit rate is high. Which design most directly reduces this duplicate refresh work without extending freshness beyond the published limit?

  1. Coalesce simultaneous misses by key, with bounded waiting and refresh-failure handling.
  2. Increase capacity so the route occupies more cache entries.
  3. Serve expired data forever whenever the database is busy.
  4. Give every requester a separate database connection and refresh immediately.

Worked answer

Best answer: A.

Coalescing concurrent misses for the same key lets one request fetch and populate the new value while others await that refresh. It avoids five hundred identical database reads without serving content beyond the allowed freshness limit. The refresh coordination needs a timeout and failure path so a failed owner does not block everyone forever. Increasing cache capacity does not address synchronized expiry for one key. Indefinitely serving stale content would change the correctness promise rather than solving the stated problem.

A high average hit rate can hide a dangerous burst at expiry; refresh coordination targets that burst.

Check your work

  • Identifies coordinated single refresh
  • Preserves freshness and handles refresh failure

2. Budget the origin after a traffic change

A media service sees 2,000 requests/s: 70% request thumbnails and 30% request originals. Thumbnail cache hit rate is 95%; original hit rate is 40%. Each origin request costs the same CPU work. Calculate the origin request rate and overall hit rate. Then a release changes the mix to 40% thumbnails and 60% originals, with hit rates unchanged. Quantify the origin-load change and explain why a single old hit-rate number is unsafe for capacity planning.

Worked answer

Initially, thumbnail misses are 2000×.7×.05=70/s and original misses are 2000×.3×.6=360/s. Origin load is 430/s and hit rate is 1−430/2000=78.5%. After the mix changes, misses are 40/s plus 720/s, totaling 760/s; hit rate becomes 62%. Origin load rises by 330/s, or about 76.7%, despite unchanged total traffic and per-class hit rates. Capacity planning must preserve workload composition, not assume that a historical aggregate cache ratio stays valid. Track these classes separately when setting origin-capacity alerts.

Cache effectiveness is a workload-dependent weighted quantity; changing popularity or object classes can expose the origin.

Check your work

  • Computes both weighted miss rates
  • Quantifies relative origin increase
  • Explains why aggregation hides workload change

3. Prevent an old refresh from undoing an edit

A catalog cache is initially empty. Reader A begins loading version 10 from the database. An editor commits version 11 and invalidates the cache. Reader A then finishes and stores version 10, so subsequent readers receive stale data for the full TTL. Propose a cache-population protocol that prevents this specific race. State the ordering or version assumption it needs and a deterministic test for it.

Worked answer

Associate cache population with a version or generation and reject writes from an older generation. For example, refresh A reads generation g before loading; after commit, the editor atomically advances the cache generation and invalidates the value. A may populate only if the generation remains g. This requires coordination that preserves the generation marker even when the value is absent and orders invalidation after commit. In a test, pause A after its old read, commit and invalidate version 11, then resume A and assert version 10 is not installed.

Invalidation alone cannot stop an in-flight stale writer; the protocol must check whether the writer’s evidence is still current.

Check your work

  • Describes version-aware conditional population
  • States coordination and ordering assumptions
  • Tests the exact interleaving
