Why the server cannot simply call the phone

Source slides 1–4

A ride arrival or an auction bid happens because another participant acts. The recipient needs an update without repeatedly asking whether anything changed. Yet a phone is not an ordinary public server: its address changes, NAT and firewalls restrict inbound connections, and the application may be suspended. Email and SMS provide useful notification channels, but do not replace every in-app interaction.

The architectural requirement is therefore a reachable delivery path, not merely an HTTP endpoint on the device. An outbound connection can establish that path while the device is online. Offline periods still require a policy for retaining, expiring or replacing messages. Distinguish notifying a person from synchronizing the authoritative state: a missed alert should not erase the underlying ride or bid.

Worked walkthrough

A building maintenance app should alert a resident when a repair appointment changes. The scheduling server knows the resident's account, but that knowledge does not give it a reachable network endpoint on the resident's phone. The phone may change networks, sit behind address translation or have its application suspended. Treating the phone as an ordinary public HTTP server leaves those constraints unexplained, even if the notification payload is only a few bytes.

Instead, the device or platform establishes an outbound delivery path that the backend can use indirectly. Now consider the phone being offline when the appointment changes twice. Decide whether to retain both changes, replace the first with the latest state, or simply notify the app to refresh. This is a product-level delivery policy, not a detail solved by opening a socket. Keep the authoritative appointment in durable storage so that reconnecting clients can recover their current state even when a notification never arrives.

Registration and mobile delivery

Source slides 5–8

Mobile push services let an application backend address a registered app instance through platform infrastructure. The app obtains a provider-issued identifier and sends it to its authenticated backend. Later, the backend associates an event with the relevant installations and submits a notification. The operating system manages the delivery connection, avoiding a separate continuously active connection for every installed application.

Treat registration identifiers as changeable routing information rather than permanent user identities. A user can own multiple devices, and a device installation can receive a new identifier. Update registration records and remove invalid destinations. Provider acceptance is not proof of display or user attention; retention limits, connectivity and device policy affect delivery. Use notifications to prompt a state refresh when correctness matters.

Worked walkthrough

A library app user signs in on a phone and a tablet. Each installation registers for platform notifications and sends its current provider-issued routing token to the authenticated backend. The backend associates both installations with the account. When a reserved book becomes ready, the notification service resolves the account to eligible installations and submits delivery requests. The account identifies the person; the tokens identify destinations through the platform's delivery mechanism.

Now uninstall and reinstall the phone app. Its routing information may change, while the person's account remains the same. Registration updates and invalid-token cleanup are therefore part of normal operation. Logging out also requires a policy that prevents the next device user from receiving the previous user's private notifications. Provider acceptance only says a delivery request entered that provider's process; it does not prove the message was displayed or read. A notification can prompt a fresh authorized read of the library record instead of carrying all sensitive details itself.

WebSockets, long polling and alternatives

Source slides 9–12

An active browser can open a WebSocket and exchange messages in both directions while the connection remains alive. Long polling instead leaves an HTTP request pending until data or a timeout arrives, then starts another request. Both permit an update to arrive without a fresh user action. Their latency and operational behavior differ from repeatedly making short periodic polling requests.

Choose transport from communication needs. Server-sent events provide a server-to-browser stream over HTTP; WebSockets support bidirectional messages. Browser background Web Push is a separate mechanism from an open page connection. Every active connection can break, so design reconnection, authentication renewal and recovery of missed state. A timeout such as sixty seconds is an implementation choice, not part of the definition of long polling.

Worked walkthrough

A workshop dashboard polls every ten seconds for a changed machine status. With changes occurring at arbitrary times, the average wait until the next poll is about five seconds, ignoring request latency. Reducing the interval lowers that wait but increases the number of requests even when nothing changes. A WebSocket keeps a bidirectional channel open, while long polling lets the server hold a request until data or a timeout becomes available.

The connection does not eliminate state recovery. If a browser loses its network for thirty seconds, it may miss several transitions regardless of the chosen live transport. On reconnect, retrieve the current authoritative status or resume from a position supported by the application protocol. Distinguish a dashboard that needs only the latest temperature from an audit screen that needs every transition. That requirement determines how much history must be retained. Compare latency, idle connection resources and reconnect behaviour, rather than choosing a protocol solely because it is described as real time.

Routing to the correct connection

Source slides 13–17

A distributed notification service must find the worker holding each live client connection. Other backend services should send a logical user notification rather than guess the physical socket owner. A registry connects user and installation identities to provider destinations or live connection identifiers. This allows the notification service to serve multiple devices and browser tabs without duplicating routing logic across domain services.

Connection records become stale when clients disconnect or workers fail. Remove obsolete entries, renew registrations and tolerate races between lookup and delivery. A managed gateway may expose a connection identifier rather than a raw socket address; the same lifecycle problem remains. Store durable business state separately so reconnecting clients can recover even when transient delivery fails, and authorize both subscription and outbound routing.

Worked walkthrough

An account has two browser tabs, one connected to notification worker A and another to worker B. An appointment service running elsewhere generates an update. Sending the update to an arbitrary notification worker is insufficient: only the worker holding a particular live connection can write to it. A registration directory maps the logical recipient to connection identifiers and their owners, allowing the notification layer to route to both tabs.

Close one tab just after the directory lookup. The route can become stale between lookup and send, so lookup success cannot guarantee delivery. Clean up failed destinations and let reconnecting clients establish fresh registrations. Keep transport failures separate from the underlying appointment change, which remains stored independently. If the design promises recovery of missed updates, retain an appropriate event history or provide a fresh-state read. Trace a worker restart as well as a normal send; this reveals why connection ownership, authoritative data and notification progress are different kinds of state.

Self-check

Why is a push token not a permanent user ID?

It identifies a provider destination or app installation and can change; the backend maps current destinations to an authenticated user.

When is SSE a useful alternative to WebSockets?

When the active client chiefly needs a server-to-client event stream; bidirectional application messaging may favor WebSockets.

What should a client do after reconnecting following a missed seat-availability alert?

Retrieve authoritative current availability or replay from a supported cursor; do not infer state from the missing alert alone.

Design exercise

Design delivery for course cancellation alerts to a phone and two browser tabs. Include offline behavior.

Maintain authorized per-user installation and connection records; send through mobile providers or owning WebSocket workers; use message IDs and expiry; clean stale registrations; clients fetch authoritative course status on reconnect.

1. A shared tablet changes users

A clinic tablet receives appointment push messages through one installed app. Patient A signs out and patient B signs in on the same installation. The push provider has not changed the installation token. A delayed message for A is still queued. Which design best limits accidental disclosure while allowing the installation to receive future notifications for B?

  1. Keep A’s binding because a provider token permanently identifies a person.
  2. Put full appointment details in every push so the app need not check identity.
  3. Assume logout automatically deletes all messages queued by the provider.
  4. Refresh account bindings and use minimal notifications followed by authorized account-scoped fetches.

Worked answer

Best answer: D.

Update the authenticated account-to-installation binding on logout and login, and keep sensitive content out of an unauthenticated notification preview. Send a minimal notification that prompts the app to fetch authorized account data; the app must reject or ignore account-mismatched stale messages. Removing A’s backend binding prevents future routing but cannot necessarily recall a provider-queued message. Token rotation alone is not a complete confidentiality mechanism. The design should also clear local account data and define whether any notifications may appear while signed out. Delivery to the same installation does not confer permission to show one patient’s details to another.

The privacy boundary is the account session, while the provider routes to an installation. A queued message can outlive the account-to-device association that caused it.

Check your work

  • Distinguish installation from account.
  • Handle already queued stale messages.
  • Require authorized fetch or account-safe presentation.

2. Comparing connection overhead

A foreground monitoring app has 2,400 active devices. Design P polls every 15 seconds, including when nothing changes. Design S uses one established stream per device and sends a keepalive every 45 seconds. Ignoring setup, retries and actual event traffic, estimate messages per minute for each design, counting one poll exchange as two messages and one keepalive as one message. Explain why these counts alone do not prove a battery-life advantage.

Worked answer

Design P performs four poll exchanges per device per minute, or eight messages: 2,400 × 8 = 19,200 messages per minute. Design S averages 60/45 keepalives per device per minute, giving 3,200 messages per minute. That is one sixth of the counted messages under the stated convention. Energy also depends on payload sizes, radio wakeups and tail time, batching, connection maintenance, network loss, TLS setup and operating-system scheduling. Measure the real device workload before claiming battery savings. The stream also needs reconnect, resynchronization and server connection capacity; fewer messages do not establish reliable event delivery.

The arithmetic isolates idle protocol overhead. It deliberately excludes the physical and operating-system costs that make message count an incomplete energy proxy.

Check your work

  • Compute 19,200 and 3,200 messages/minute.
  • Respect the counting assumptions.
  • Explain energy and delivery limitations.

3. An old disconnect deletes a new connection

A notification router stores user U → worker A, connection 7. U reconnects through worker B, which replaces the record with connection 8. A delayed disconnect callback from A then deletes the record by user ID alone. Later alerts cannot find U even though connection 8 is healthy. Design registration and cleanup semantics that handle this race and explain how the same scheme can support two legitimate devices.

Worked answer

Store a connection identifier or generation with the owner, and delete only if the stored entry still matches the disconnecting connection. A’s callback for connection 7 then cannot remove connection 8. Use atomic compare-and-delete or equivalent versioned storage semantics, and consider expiring leases for owners that disappear without callbacks. For multiple devices, key registrations by authenticated account plus installation or connection identity, yielding a set of valid destinations rather than one user-wide slot. Authorize registration changes and bound stale entries. Reconnection should also trigger state reconciliation, since a correct directory does not recover events missed during the gap.

The race is stale ownership, not merely network failure. Versioned cleanup preserves the newest registration without preventing intentionally concurrent destinations.

Check your work

  • Use generation/connection-scoped atomic cleanup.
  • Support a destination set per user.
  • Address stale leases and missed-event recovery.
