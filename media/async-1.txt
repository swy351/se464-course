Independent scaling and queue boundaries

An image service accepts twenty uploads per second during a burst. Each preview worker completes five jobs per second under the assumed image mix. Two workers can process ten jobs per second, so the backlog grows by approximately ten jobs each second during that burst. Adding two more workers could match the arrival rate if shared storage and other dependencies have spare capacity. The queue exposes the difference between accepting work and providing enough capacity to finish it. Keep admission through the service API, where authorization, validation and workload limits belong, rather than letting public clients publish arbitrary broker messages. Producers and consumers can scale separately, but the queue itself and downstream storage still have limits. A larger queue changes how long work can wait; it does not increase processing throughput. Measure task duration by job type, since a thousand small previews may cost less than a few large ones. Scale against useful completion rate and queue age, and test whether adding workers shifts contention elsewhere.

Backpressure, ordering and recovery

Suppose a report queue holds six hundred pending jobs and its workers finish ten jobs per second while new arrivals temporarily stop. A rough drain time is sixty seconds. If arrivals continue at eight jobs per second, the net drain rate is only two, stretching the estimate to five minutes. These simplified calculations explain why queue length alone is insufficient: arrival rate, service rate and the age of waiting work determine user experience. Set an admission policy before storage fills. Depending on the product, reject excess work, postpone low-priority jobs or coalesce requests that genuinely supersede one another. Recovery also needs ordering rules. Two changes to the same report configuration should not accidentally apply in reverse order merely because different workers finish at different times. A broker's guarantees depend on its configuration and partitioning, so define the scope of required order. Bounded retries and a visible failed-job state prevent one malformed message from consuming capacity indefinitely while legitimate work waits.
