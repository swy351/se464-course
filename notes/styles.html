Architecture styles and their tradeoffs

Compare repositories, pipelines, layers, interpreters, control loops and peer-to-peer systems.

Source: [Week11]Arch_styles.pptx. Generated companion; original slides unchanged.

Describe a style through its constraints

Source slides 1–12

An architectural style defines a vocabulary of components and connectors together with constraints on their organization and behavior. A label such as layered or client–server is therefore only the beginning of a description. Identify what components do, what communication means and which arrangements are permitted. The same graph shape can represent different styles if its edges have different semantics.

The opening examples combine several ideas: distributed communication, objects, layers and pipelines. Real systems can combine styles, so classification should clarify a design rather than force an exclusive label. Ask what problem a style addresses, which invariants must hold and what advantages require those invariants. The slide list includes implicit invocation but does not develop a dedicated treatment; event-driven content elsewhere can supply that connection without implying it is fully covered here.

Predict: Can one system use both repository and pipeline structures?

Yes. Different responsibilities or views may combine styles; explain where each applies and how their constraints interact.

Repository and blackboard architectures

Source slides 13–21

A repository architecture centers collaboration on a shared body of information. Independent components read or modify that state according to a common schema. An IDE offers a useful example because multiple tools can inspect and transform program information. A blackboard specialization allows cooperating computations to contribute partial results that other computations use, with coordination organized around the evolving shared information.

Centralized data management can consolidate access policy, backup and concurrency control. It also creates coupling through the data model: a schema change can affect many consumers even when their code does not call one another. Persistence and distribution are implementation choices, not automatic consequences of drawing one repository box. Ask who owns schema evolution, how concurrent updates are coordinated and whether the repository becomes a capacity or availability constraint.

Predict: If repository clients never call each other, are they independent of each other’s changes?

Not completely. They share schema and data semantics, so changes can affect other clients through the repository.

Pipes, filters and compiler hybrids

Source slides 22–38

Filters transform streams and pipes carry output to subsequent input. In the pure style, filters avoid shared state and do not depend on the identity of adjacent filters. Compatible data contracts let stages be replaced or reordered when semantics allow. A pipeline is a linear specialization; batch sequential processing waits for an entire input batch before the next transformation produces its result.

The shell example illustrates composition, while the compiler history shows why pure categories can be insufficient. Compiler phases may follow an ordered pipeline while sharing symbol tables or an intermediate representation, forming a hybrid with repository structure. Streaming can support overlap, but throughput, buffering and synchronization still matter. Data conversion between stages introduces cost, and interactive feedback may require additional coordination beyond a one-way transformational flow.

Predict: If compiler phases all update a shared symbol table, is the design a pure stateless pipe-and-filter system?

No. It combines pipeline sequencing with shared repository state.

Objects and layers as boundaries

Source slides 39–57

Object-oriented organization groups state with operations that preserve its invariants. Clients should rely on a contract rather than internal representation. Shared mutable objects can still create unexpected interactions when one client changes state another observes. Encapsulation reduces certain dependencies, but does not make every implementation change invisible or require hard-coded identities in every caller; indirection can manage references.

Layering organizes services by abstraction and restricts dependencies between them. Strict layering normally permits adjacent interactions; relaxed designs document deliberate bypasses. A layer is logical organization, while a tier describes deployment separation, so several layers may reside in one process or tier. Stable contracts can localize changes, but effects may propagate when behavior or assumptions change. Evaluate dependency direction and runtime cost instead of assuming a fixed upper bound on affected layers.

Predict: Does a three-layer codebase require three physical servers?

No. Layers express logical responsibility; deployment tiers and server count are separate choices.

Interpreter and virtual-machine architectures

Source slides 58–66

An interpreter architecture represents a program as data and uses an execution engine to advance it. The model distinguishes the interpreted program, its state and the engine’s state. This separation can make an unavailable machine or language executable on an existing platform. It also introduces responsibility for instruction semantics, validation and runtime behavior that ordinary direct execution may not expose in the same way.

Virtual machines need not be implemented solely through interpretation. The JVM specification defines an abstract machine without requiring a particular implementation technique; compilation and hybrid execution are possible. The deck’s Java and compiler-bootstrap examples connect runtime organization to build-time architecture. Portability depends on the specified abstraction and compatible implementations, while performance depends on execution strategy and workload. Treat specific implementation-version statements as historical examples unless they have been rechecked.

Predict: Does running JVM bytecode imply that every instruction is interpreted one at a time?

No. The specification permits different implementation technologies, including compilation.

Control systems and feedback

Source slides 67–73

A process-control architecture aims to keep a controlled variable near a desired set point. Sensors measure relevant variables, and a controller chooses changes to manipulated variables. Cruise control provides a concrete vocabulary: desired speed is the set point, measured speed is feedback and throttle is manipulated. These roles describe the causal relationship, not merely a chain of function calls.

Feedback adjusts actions using observed results; open-loop control does not use the controlled output to correct its action. An open-loop approach may be adequate under predictable conditions, while disturbances make feedback valuable. A software architecture must also consider measurement delay, failure and actuator limits, even if a simple block diagram omits them. Preserve the distinction between an explanatory teaching model and a design validated for a safety-critical application.

Predict: If a heater follows a fixed schedule without measuring temperature, is it closed-loop temperature control?

No. Without feedback from the controlled variable, it is open loop for temperature.

Client–server responsibilities and remote calls

Source slides 74–80

Client–server organization gives one component a requesting role and another a service-providing role in an interaction. A file server supplies files, while a database server can execute queries near the stored data and return selected results. Remote communication makes message meaning, latency, availability and discovery part of the design. One component may act as server for one interaction and client for another.

Centralizing a service can simplify management and allow heterogeneous clients, but horizontal scaling depends on state, coordination and routing. Query processing at the server may reduce transfer for selective queries; it does not guarantee small responses for every workload. Location transparency can simplify interfaces without removing network failure. Explain timeout, retry and authorization responsibilities alongside the boxes so the design remains meaningful when a service is slow or unavailable.

Predict: Is a remote database query equivalent to a local procedure call in its failure behavior?

No. Communication failures and ambiguous outcomes require explicit timeout, retry and consistency reasoning.

Peer-to-peer structure and practical hybrids

Source slides 81–88

Peer-to-peer systems distribute service roles among participants rather than assigning all work to one permanent server. Peers can both request and provide data, and the overlay need not connect everyone directly. BitTorrent distributes pieces among participants, allowing downloaders to contribute verified pieces before completing the entire file. A complete participant can continue serving as a seed, but partial participation is already useful.

Decentralized data transfer does not imply the absence of centralized discovery or bootstrap dependencies. The source’s original Napster characterization should be treated as a hybrid example rather than a proof of fully decentralized control. Availability and privacy depend on the actual protocol, peer behavior and metadata exposure. Networks can partition, peers can disappear and discovery can fail, so assess resilience from concrete replication and routing mechanisms rather than from the peer-to-peer label alone.

Predict: Must a BitTorrent participant finish the entire file before uploading useful data?

No. The protocol allows peers to exchange available pieces while downloads are still in progress.

Self-check

What distinguishes a layer from a tier?

A layer organizes logical functionality or abstraction; a tier describes deployment separation.

Why is a compiler with shared intermediate representation a hybrid?

Its passes may form a pipeline while sharing repository state, so it does not satisfy pure independent-filter assumptions.

Does peer-to-peer imply no single point of failure?

No. Discovery, bootstrap, identity or scarce data replicas may remain centralized or fragile.

Design exercise

Choose a style or hybrid for an IDE, a log transformation job and a room-temperature controller. State one invariant and one risk for each.

IDE: repository-centered tools share a program model; schema evolution couples clients. Log job: pipes and filters agree on record format and avoid shared state; buffering and conversion can bottleneck. Temperature controller: feedback adjusts output from measured temperature; delayed or faulty sensing can undermine control.

1. Interpreting a workflow language

A laboratory application lets technicians save experiment recipes in a small language with variables, conditional branches and repeat-until steps. At runtime an execution engine reads the recipe, maintains variable values and chooses the next operation. Hardware adapters perform permitted instrument actions. Which architectural description best explains the recipe-execution core, without claiming that the entire application has only one style?

  1. Pure pipe and filter because the recipe has more than one step.
  2. Interpreter/virtual-machine style because an engine evaluates a program representation.
  3. Peer-to-peer because many technicians author recipes.
  4. Repository style alone because recipes can be saved.

Worked answer

Best answer: B.

The core follows an interpreter or virtual-machine style: the recipe is a program representation, the engine evaluates its constructs, and stored variables plus control position form execution state. Hardware adapters may separately use object-oriented or client-server patterns. Calling every sequence of steps a pipe-and-filter system would miss the branching and mutable execution context described here. A central recipe store alone also does not explain execution semantics. The style label is useful because it highlights language validation, resource limits and separation between user-defined programs and the trusted engine, while allowing a hybrid overall architecture.

The defining relationship is an engine giving semantics to a program representation. Storage location and the existence of several steps are secondary features.

Check your work

  • Identify interpreter/VM core.
  • Relate components to program and execution state.
  • Allow hybrid styles around the core.

2. A pipeline whose buffer keeps growing

A document-processing pipeline has three filters: parsing at 120 documents per second, classification at 70, and indexing at 100. A producer supplies 90 documents per second continuously. Assume average rates are stable, no documents are discarded and parsing can keep up. Identify the bottleneck, estimate buffer growth before classification over two minutes, and propose controls that preserve correctness rather than hiding the overload.

Worked answer

Classification is the bottleneck at 70 documents per second, so the upstream queue gains 90 − 70 = 20 documents per second, or 2,400 over two minutes under these assumptions. Indexing has capacity for the classifier’s output but cannot repair the earlier deficit. Use bounded buffers and backpressure, or durably admit work under an explicit backlog policy. Scaling classification is useful only if documents can be processed independently and ordering or shared-model constraints remain satisfied. Measure sustainable rates and provide lag observability. Silently dropping documents or adding an unlimited in-memory queue would violate the stated correctness requirement.

Pipes decouple stages through an agreed record flow, but they do not create capacity. Buffering absorbs a finite burst; sustained excess arrival requires capacity or admission changes.

Check your work

  • Find 70/s bottleneck and 2,400-document growth.
  • Propose bounded backpressure or durable admission.
  • Discuss parallelism and correctness constraints.

3. Feedback with stale measurements

A greenhouse controller samples humidity every second and opens a mist valve whenever the latest reading is below a target. A network change delays sensor messages by 25 seconds, yet the controller treats every arriving sample as current. Humidity now repeatedly overshoots the target. Explain the architectural failure and propose sensing, control and safety boundaries; you do not need to derive a numerical control law.

Worked answer

The controller is acting on delayed plant state, so it can keep adding moisture after the real humidity has crossed the target. Carry measurement timestamps, detect stale or out-of-order observations and make delay an explicit control-design assumption. Use an appropriate tested control strategy with bounded actuation rather than repeatedly reacting as if each sample were current. Define a safe stale-sensor behavior, maximum valve-open duration and independent limits where the hazard warrants them. Observe actuator status as well as sensor values. Separating sensing, decision logic and actuation clarifies responsibilities but does not itself guarantee stability.

Process-control architecture makes the feedback loop central. Communication delay is part of that loop and must be considered alongside sensing accuracy and actuator behavior.

Check your work

  • Explain delayed feedback and overshoot.
  • Track freshness and bound actuation.
  • Separate responsibilities without claiming automatic stability.
