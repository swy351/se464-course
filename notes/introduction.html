Why software needs architecture

Source slides 9–21

Software supports everyday activities, and a large system can exceed what any one developer can understand at once. The historical codebase examples in the slides illustrate growth and complexity. Their exact line counts are snapshots, not a measure of design quality or a rule for when architecture becomes necessary.

Complexity creates practical questions: where should a change go, what might it break, how can we inspect security and quality, and how will the system run and evolve? Architecture provides a manageable account of important parts, their relationships, and the decisions that constrain them. It connects a problem and its requirements to a solution that developers can implement and test.

The engineering analogy in the slides emphasizes planning, coordination, and checking the result. It does not require every decision to be completed before coding. Architectural reasoning can continue as implementation and feedback reveal new constraints. Maintenance and evolution make preserving the reasons behind important decisions valuable.

Predict: Two systems have the same number of source lines. Must they need the same architectural effort?

No. Relationships, stakeholder concerns, quality requirements, and the cost of changing important decisions matter. Line count alone does not reveal these factors.

Systems, stakeholders, and decisions

Source slides 22–28

A system exists in an environment and serves a mission. Its stakeholders are people or organizations with an interest in its behavior or development. For a museum catalog, the mission might be to help visitors discover exhibits; curators, visitors, and maintainers have different concerns. State the system boundary so that external people and systems are not mistaken for internal components.

The definitions in the slides emphasize components, relationships, interfaces, behavior, composition, and guiding principles. Architectural decisions are the design decisions significant to the system as a whole: they shape how major responsibilities fit together and how important qualities can be achieved. Architecture is design, but a local design choice is not automatically architecturally significant.

Significance depends on context. An algorithm or data structure can become an architectural concern if it determines system-wide performance, compatibility, or feasible behavior. Conversely, a small local implementation choice may be easy to replace. Architecture supports communication among stakeholders, analysis of a proposed system, and reuse of successful structures; a diagram is useful only when people agree on its meaning.

Predict: Is choosing an algorithm always outside software architecture?

No. A locally replaceable algorithm may be detailed design, but one that constrains the whole system or determines a critical quality can be architecturally significant.

Intended and implemented architecture

Source slides 29–35

Prescriptive, or intended, architecture describes how the system is supposed to be organized. Descriptive, or implemented, architecture describes what actually exists. The two can differ because software evolves, documentation becomes stale, or implementation decisions bypass agreed boundaries. Treat an intended diagram as a statement of design intent, not proof of the current code structure.

Architecture drift means new implementation decisions are absent from the intended description without violating it. Architecture erosion means the implementation violates the intended architecture. Suppose the intended design permits a presentation module to call only an application interface. An allowed new implementation behind that interface may be undocumented drift; a direct presentation-to-storage dependency violates the stated boundary and is erosion.

Architecture recovery reconstructs an account of the implemented system from evidence such as source code, executable structure, configuration, and developer knowledge. Record uncertainty rather than filling gaps with guesses. Compare the recovered account with the intended one, investigate differences, and decide whether to repair the implementation or deliberately revise the intended design and its rationale.

Predict: An undocumented component is added within all permitted dependency rules. Is that necessarily erosion?

No. Under the distinction in the slides, a compatible undocumented decision is drift. Erosion requires evidence of a violated intended rule.

Views and meaningful diagrams

Source slides 36–46

A single box-and-arrow picture rarely answers every architectural question. A static decomposition can show code responsibilities and dependencies. A runtime view can show processes and interactions. A deployment view can show where software executes across devices. State what each box and arrow represents, and distinguish a code dependency from a runtime message or a deployment relationship.

The 4+1 model organizes complementary views. The logical view describes key abstractions and responsibilities; the process view addresses runtime concurrency and interactions; the development view describes code organization; the physical view maps software onto hardware or execution nodes. The additional scenarios connect and help examine the views through representative system behavior.

For a museum catalog, a logical view might distinguish exhibits and collections, a development view might show modules, and a physical view might place the application on a server. A visitor searching for an exhibit is a scenario that can be traced through the relevant views. These descriptions must agree, but they need not contain identical boxes or identical levels of detail.

Predict: A maintainer asks which device runs a process. Would a class diagram alone answer the question?

Usually not. A physical or deployment view identifies execution placement. A class diagram describes a different concern and needs an explicit mapping to runtime and deployment elements.

Abstraction, reuse, and C4

Source slides 47–48, 50

Architectural descriptions can reuse ideas at different scopes. A style describes a family of structures through constraints on elements and relationships. A reference architecture gives a reusable architectural organization for a domain. A product-line architecture captures shared structure and planned variation across related products. These concepts help teams reuse reasoning, rather than copy a diagram without checking its assumptions.

C4 provides four nested levels of structural description: system context, containers, components, and code. Context shows the system in relation to people and external systems. Containers show major running applications or data stores within the system; components describe responsibilities within a container; code shows implementation detail when useful. A C4 container is a modeling concept, not necessarily a Docker container.

C4 levels and 4+1 views answer different organizing questions. C4 changes the level of detail; 4+1 separates concerns such as code organization and runtime processes. Neither requires every diagram for every audience. Architectural significance also does not follow a fixed line-count threshold or a rule that architecture happens only early: revisit consequential decisions as the system evolves.

Predict: A context diagram contains every class in the application. Does the extra detail necessarily help its audience?

No. A context audience needs the system boundary, people, and external relationships. Class detail can obscure that purpose; move it to a more detailed description when it answers a relevant question.

Patterns and architectural styles

Source slides 51–57

An architectural pattern describes a recurring design problem and an arrangement of responsibilities that addresses it in a context. A style constrains the kinds of elements and relationships allowed in a family of architectures. The terms can overlap in use; explaining the responsibilities, constraints, and consequences is more useful than relying only on a name.

The three-tier example separates presentation, application processing, and data management. This helps identify responsibilities and the interfaces between them. A logical separation of these concerns does not by itself prove that they run on three separate machines. MVC separates model, view, and controller responsibilities around an interface; it should not be assumed to be a one-to-one synonym for three deployment tiers.

The sense–compute–control example organizes observation, computation, and action on an environment. It highlights a different set of responsibilities from a typical presentation-and-data application. When selecting any pattern, state the problem it addresses and the constraints it imposes. A named style may support desired qualities, but its name alone cannot guarantee maintainability, performance, or other outcomes.

Predict: A team labels three boxes MVC. Has it demonstrated a three-machine deployment?

No. MVC describes responsibilities. Deployment requires separate evidence about where those responsibilities execute; a diagram label does not establish placement.

Self-check

How does an architectural decision differ from an ordinary local design choice?

Its significance comes from its system-wide consequences, relationships, quality concerns, or cost of change. The boundary is contextual, not a fixed size or phase rule.

What evidence distinguishes architecture drift from erosion?

Compare the implemented decision with an explicit intended constraint. An undocumented compatible addition is drift; a violated constraint is erosion. Without a known constraint, do not assert a violation.

How do C4 levels differ from the 4+1 views?

C4 organizes structural descriptions by abstraction level. The 4+1 model separates architectural concerns and relates them through scenarios. They are not a one-to-one mapping.

Design exercise

Design an introductory architecture description for a museum exhibit catalog. State its mission and two stakeholders. Draw a system-context diagram and one complementary view, with a legend. Describe one significant decision, then explain how you would check whether the implementation follows it.

A possible mission is helping visitors find exhibits. Visitors need understandable search results; curators need a maintainable catalog. The context diagram shows people, the catalog boundary, and any explicitly assumed external system. A development view can show presentation, application, and data-access modules with arrows meaning permitted dependencies. Record a decision that presentation uses the application interface, then inspect code dependencies for direct storage access. Other decompositions are valid when their rationale and notation are clear.

Questions-only worksheet · Worked answer sheet

1. An undocumented adapter

A weather-display application requires its presentation module to call only a display interface. A developer adds a new screen adapter behind that interface, obeying all intended dependency rules, but leaves the architecture description unchanged. Which classification best fits the distinction in this unit?

  1. Architecture erosion because any new component violates the design.
  2. Architecture drift because the compatible addition is undocumented.
  3. No architectural change because an interface exists.
  4. A physical view because the adapter drives a screen.

Worked answer

Best answer: B.

Architecture drift: the new decision is undocumented but does not violate the intended architecture. Update the descriptive account and decide whether the intended description should also record the extension.

A difference from documentation does not automatically establish erosion.

Check your work

  • Identifies drift
  • Uses compatibility with the intended rules as evidence

2. Choose two complementary views

A library kiosk team needs to answer two questions: which source modules may depend on the catalog module, and which device runs the kiosk process? Choose a suitable 4+1 view for each. Specify what boxes and arrows mean and explain why one unlabeled diagram is insufficient.

Worked answer

Use the development view for source modules and permitted dependency arrows. Use the physical view for devices and explicit process-to-device placement. Include a legend and a consistent mapping between the descriptions. An unlabeled box might mean a module, process, or machine, so it cannot reliably answer both questions.

Views organize different concerns; consistency does not require identical notation or detail.

Check your work

  • Matches development view to code dependencies
  • Matches physical view to execution placement
  • Defines notation and relates the views

3. Explain a pattern without overclaiming

A greenhouse system reads temperature, computes a desired adjustment, and commands a vent. Describe it using sense–compute–control. Identify a stakeholder concern and one architectural decision. Can the pattern name alone prove the system will respond quickly enough?

Worked answer

Sensing obtains temperature observations; computation decides the adjustment; control issues a vent command. A grower may care about protecting plants from excessive heat. A significant decision could define the interfaces and interaction between these responsibilities. The pattern alone does not prove adequate response: the design and implementation must be checked against a stated response requirement. No numerical threshold is implied by this scenario.

A pattern supplies an organizing idea; system-specific evidence supports quality claims.

Check your work

  • Maps all three responsibilities
  • Connects a stakeholder concern to a decision
  • Rejects an unsupported quality guarantee
