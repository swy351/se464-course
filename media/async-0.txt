Asynchronous processing and message queues
Part 1 • Synthetic narration

Accepted is different from completed

A researcher requests an export of a large experiment dataset. Waiting for every file to be prepared inside the initial request could exceed a useful response deadline. Instead, the service validates the request, records an export job and returns a job identifier. That response means the service accepted responsibility for attempting the export. It does not mean a downloadable archive already exists, so the user interface should display queued or processing rather than completed. The client can later query the job record for success or a failure reason. A webhook is another option for a client with a reachable endpoint, but it introduces its own authentication and retry contract. A phone behind a changing network cannot simply be assumed to accept callbacks. Include a terminal failure state so that accepted jobs do not appear pending forever. Trace a worker failure after acceptance and identify how another worker discovers the job. The shorter response time moves completion tracking into explicit application state.

Queues as durable work contracts

A document service places a preview-generation request on a queue. The message contains a job identifier, document identifier, desired representation and schema version. These fields are an API contract even though no synchronous response carries the finished preview. The worker must know which document version to process and where to record the result. A queue containing only an ambiguous instruction such as generate preview leaves important business decisions to guesswork. Consider a worker that stores the preview and crashes before acknowledging the message. Redelivery may cause the same job to run again. Use the stable job identifier and a suitable result-update rule so that repetition does not create conflicting visible outcomes. Acknowledgement timing should reflect the actual persistence boundary, not merely receipt into memory. Likewise, an in-process queue lost during a restart provides a different contract from durable broker storage. The architecture should state what survives each failure and which component owns recovery, rather than treating every queue icon as equivalent.
