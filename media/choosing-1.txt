Choosing a data store
Part 2 • Synthetic narration

Documents, search and wide-column stores

Different storage models make different questions inexpensive. We will compare text retrieval with time-ordered sensor data and make the lookup steps explicit. The useful choice follows the operation, including how derived structures are kept up to date. A museum stores exhibit descriptions as documents. For keyword search, an inverted index might map “bronze” to documents {4, 9, 12} and “river” to {9, 15}. Their intersection returns document 9 for a query requiring both words. This explains retrieval mechanics, but ranking and language handling need additional rules. Updating the document also requires updating its searchable representation. For temperature readings, a different design uses sensor_id and day as the partition key and observation_time as the within-partition ordering key. This supports one sensor’s daily range query while bounding partition growth. Searching every sensor for one interval may need another access path. A search index can lag its source, and a telemetry partition can become hot. Neither a document shape nor a key-value interface removes these workload and consistency questions.


Caches and memory data structures

A cache is part of a data flow, not merely a faster machine. Explain where its values come from, how they become stale and how they recover. Our recreation-centre example separates a helpful display from an authoritative booking decision. A recreation centre shows a cached count of available places on its home page. The count can be briefly stale, but the booking operation checks the authoritative reservation store. This separates a fast informational view from the decision that commits scarce capacity. A time-to-live limits how long one cached value remains eligible; it does not make that value current at every instant. For a weekly activity ranking, a sorted-set abstraction can update one participant’s score without rewriting the entire ranking. Before adopting it, decide whether the ranking can be rebuilt from durable events and what happens after eviction or restart. Also plan how simultaneous cache misses avoid overwhelming the origin. A reverse-proxy cache of a whole public page sits at a different layer from these application-managed values, even when both reduce repeated work.


Files, objects and final selection

Files, objects and blocks expose different operations to applications. Choose the interface by following a real workflow, including partial failure. A wildlife recording archive helps us connect storage selection with the responsibilities that appear between two independent services. A wildlife archive stores short audio recordings as objects and keeps their searchable metadata in a database. Clients request a recording by an object identifier rather than mounting the archive as a disk. A legacy analysis program that expects directories and file operations may instead need a filesystem interface. A block volume provides lower-level storage on which a filesystem can be created; it is not itself a shared file service. The recording and its metadata form a cross-system workflow. If an upload succeeds but the metadata write fails, the archive needs a cleanup or retry rule so abandoned objects do not accumulate. If metadata is published before upload completion, users may receive broken links. Draw these failure paths before adding stores. The final architecture should identify ownership, identifiers, access control, recovery and the reason each separate abstraction is necessary.
