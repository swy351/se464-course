Secure Microservices: Boundaries, Tokens and Response

Week 12 · November 23

Protect service boundaries with verified identities, scoped access, isolation and incident response.

Source: [Week11]secure_micro_services.pptx. Generated companion; original source unchanged.

Protect the exposed service boundary

Source slides 1–10

A microservice system has more communication paths and administrative surfaces than one isolated process. Begin by identifying which routes clients actually need. An API gateway can expose those routes, apply common checks and direct requests to internal services. Restricting direct access reduces opportunities to bypass those checks, but the gateway is one control rather than a reason to trust everything behind it.

Client application credentials and user identity answer different questions. A secret embedded in a distributed browser or mobile application cannot be assumed confidential. Apply request limits and protect the infrastructure control plane, while planning gateway capacity and failure behavior. Include outbound dependencies in the trust model: an internal service may call an external endpoint that supplies malicious data or receives sensitive information. Draw both directions of traffic before deciding where checks belong.

Predict: If only the gateway is publicly reachable, can an internal billing service skip authorization?

No. A compromised internal caller or a mistaken route can still reach it. Enforce resource permissions at a trustworthy boundary that cannot be bypassed.

Verify peers and protect channels

Source slides 11–15

Encryption is useful only when the connection reaches the intended peer. Certificate verification links a presented key to a trusted identity under the client’s policy. Accepting every certificate removes that assurance. A self-signed certificate can be deliberately trusted through an authenticated provisioning process; simply accepting any self-signed certificate does not establish the correct peer. Verification includes the intended service identity, not merely a recognizable issuer.

TLS protects data while it crosses the established channel. In mutual TLS, both sides authenticate with certificates; this identifies a workload or client credential, not automatically a human user or permission to perform every operation. Protect private keys and plan issuance, renewal and compromise response. Pinning narrows accepted credentials but adds rotation and recovery responsibilities. Keep authentication, confidentiality and application authorization distinct in the architecture diagram.

Predict: If a client encrypts traffic but accepts any certificate, has it authenticated the intended server?

No. It may establish an encrypted channel to an impostor; identity verification is essential.

Contain compromise inside the cluster

Source slides 16–22

An internal network should not imply unrestricted communication. List the connections each workload requires, then restrict both incoming and outgoing paths. Kubernetes namespaces organize resources but do not automatically isolate their network traffic. NetworkPolicy requires enforcement by the selected networking implementation. Separate intended policy from demonstrated behavior, and test whether an unrelated service can reach a protected dependency.

Outbound restrictions help reduce unwanted destinations and some SSRF consequences, but they complement rather than replace application validation. Runtime monitoring can report suspicious behavior; an alert is not necessarily a preventive control. Resource quotas bound aggregate namespace allocations, while workload requests and limits address individual resource behavior. These measures can reduce blast radius and resource contention without promising to eliminate denial of service. Define who investigates alerts and how a service is isolated without losing essential evidence.

Predict: Does placing billing and search in separate namespaces block search from contacting billing?

No. Namespaces alone do not impose that network boundary; enforced policies and the relevant selectors must establish it.

Token trust, validation and revocation

Source slides 23–31

A signed JWT carries claims plus a signature; its readable payload is not encrypted merely because it is signed. A service needs a validation policy: trusted issuer and keys, permitted algorithms, intended audience, token type and applicable time constraints. A valid signature alone does not establish that this token belongs at this API or that its subject may access the requested record.

Access and refresh tokens have different roles. Short access-token lifetimes limit exposure, while refresh-token rotation or sender constraints address renewal risk. Revoking a refresh token does not magically invalidate every already issued self-contained access token. Central issuance with local verification can reduce repeated authentication calls, but introduces key-distribution and revocation tradeoffs. OAuth concerns delegated authorization; OpenID Connect adds authentication conventions. Neither is synonymous with the JWT data format.

Predict: If a user’s refresh token is revoked, must a locally validated access token stop working immediately?

No. Immediate rejection requires an additional mechanism such as introspection or a revocation/version check; otherwise the access token may remain valid until expiry.

Harden each service and its data paths

Source slides 32–41

A service should expose only necessary interfaces and run with limited privileges. Non-root execution, reduced capabilities, a read-only filesystem where feasible and narrowly scoped workload credentials reduce consequences of compromise. Secrets should be managed with explicit access, rotation and revocation rather than hardcoded in source. Environment variables and mounted files each have exposure tradeoffs; a secret store still needs authentication and authorization.

Input handling must match the destination. Parameterized database operations separate data from SQL, contextual output encoding protects HTML contexts, and destination validation plus network controls help constrain outbound URL requests. An ORM can still execute unsafe raw queries. Error handling should avoid disclosing internal details while retaining useful protected diagnostics. Trust forwarded identity or IP information only from configured trusted intermediaries, and order middleware so identity and permission decisions occur before protected work.

Predict: Can a service trust X-Forwarded-For simply because the request contains that header?

No. Clients can supply headers. The trusted proxy path must overwrite or validate forwarded information, and network address still does not prove user permission.

Practice incident response with bounded simulations

Source slides 42–53

The supplied Uber case distinguishes tabletop exercises, red-team operations and smaller repeatable simulations. These methods test different things: decision-making and escalation, broader adversary behavior, or focused detection and response. The historical example should not be treated as a statement of Uber’s current procedures. For this course, a tabletop preserves the architectural learning without running intrusion tools or accessing real credentials.

Assign roles for triage, service ownership, communications and decision authority. Introduce synthetic evidence in stages: suspicious token use, an unexpected outbound connection, then an unavailable dependency. Ask what evidence is needed, what can be contained and which users are affected. Record timing and assumptions, then conduct an after-action review with owners for improvements. Coverage mapped to ATT&CK techniques can reveal gaps, but a checked box does not prove that a control will detect every variation.

Predict: If a simulation triggers an alert, is the response process necessarily successful?

No. Someone must triage it, coordinate decisions, contain harm and recover; the exercise should test that complete chain.

Self-check

A gateway validates a JWT signature. Name two reasons a downstream grade service should still reject a request.

The token may target a different audience or be expired, and the authenticated subject may lack permission for the specific grade record. Validate the relevant claims and enforce object-level authorization.

Separate namespaces and ResourceQuota objects exist. Does that prove traffic isolation and denial-of-service prevention?

No. Network policies need supporting enforcement; quotas constrain aggregate allocations and do not stop all runtime exhaustion, request floods or dependency overload.

A service accepts an issuer’s valid signed JWT containing a readable email address. Does the signature make that claim confidential?

No. Signing protects integrity and issuer authenticity under proper verification; confidentiality requires separate encryption and handling controls.

Design exercise

Draw a course-registration architecture with gateway, identity provider, enrollment service and billing service. State permitted network paths and which identity each hop verifies. Explain token validation and withdrawal of instructor privileges. Then run a paper tabletop: a synthetic alert reports a billing token used from an unexpected workload. Choose triage, containment, evidence and recovery steps; do not interact with live systems.

Expose required gateway routes, restrict service/control-plane access and permit only needed ingress/egress. Verify workload identity on internal channels and user/token context at protected operations. Validate issuer, audience, signature and lifetime; enforce enrollment/billing permissions separately. State revocation latency for cached or self-contained tokens. In the tabletop preserve synthetic event records, confirm scope, isolate the affected credential/workload, rotate or revoke as appropriate, check dependent services, communicate impact and record owned improvements.

1. Signing-key rotation without accepting strangers

An identity provider rotates from signing key K1 to K2. A reporting service caches the provider’s trusted verification keys and has not refreshed them, so valid K2 tokens fail. An engineer suggests reading an arbitrary key URL from each token header and fetching that key whenever verification fails. Which response restores rotation support without allowing a token sender to choose its own trust authority?

  1. Fetch any URL the token advertises and trust its result.
  2. Disable signature checks until the next deployment.
  3. Refresh through the configured trusted issuer and retain normal claim validation.
  4. Accept unknown keys if the token has a plausible username.

Worked answer

Best answer: C.

Refresh keys only through the configured trusted issuer’s key-distribution mechanism, with controlled caching and bounded retry behavior. Allow planned overlap for K1 and K2 as the issuer’s policy requires, and verify issuer, audience, permitted algorithms and token lifetime in addition to the signature. Do not trust an arbitrary header-supplied URL as a new authority: a malicious sender could offer a key for its own signature or induce unwanted outbound requests. Unknown keys should fail closed if trusted refresh cannot resolve them. Rotation monitoring helps distinguish a rollout problem from malformed or hostile tokens.

The token may identify a key within a trusted set, but it must not redefine who is trusted. Rotation changes key material while preserving the trust anchor.

Check your work

  • Keep discovery anchored to trusted configuration.
  • Handle caching/overlap without bypassing validation.
  • Fail closed for unresolved untrusted keys.

2. Measuring the revocation window

An access token is issued at 14:00 and expires at 14:12. At 14:03 an operator revokes its refresh token after suspected theft. API workers verify access tokens locally and do not consult a revocation list. Assume synchronized clocks and no expiration grace. How much longer can the stolen access token be accepted, and what changes could shorten that window without pretending refresh-token revocation already solves it?

Worked answer

The existing access token can remain acceptable until 14:12, leaving nine minutes after the 14:03 action, assuming its other checks pass. Revoking the refresh token prevents authorized renewal through that credential but does not update a self-contained token already held by an attacker. Shorter access-token lifetimes reduce the maximum window. Introspection, a revocation list or a subject/session version check can support earlier rejection, with explicit propagation and cache freshness guarantees. These add dependencies and operational cost, so define their outage behavior. Rotating a shared signing key can invalidate many unrelated sessions and is not a precise per-session remedy.

The calculation exposes the tradeoff between offline verification and rapidly changing authority. A design must state revocation latency rather than simply claiming tokens are revocable.

Check your work

  • Calculate nine minutes.
  • Separate refresh and access-token effects.
  • Offer explicit early-rejection mechanisms and tradeoffs.

3. A useful URL-fetching feature

A media service accepts a customer-supplied image URL and fetches it to create a thumbnail. It runs inside a cluster with access to private administration endpoints. Product requirements need only HTTPS images from two partner domains, but the current implementation follows every redirect and allows any hostname. Design validation and network boundaries for this feature, including what must be rechecked after a redirect.

Worked answer

Allow only the required scheme, partner hostnames and expected ports, using a real URL parser and a defined normalization policy. Resolve and restrict destinations so private administration or metadata addresses are not reachable, accounting for resolution changes. Either disallow redirects or revalidate every redirected URL and resolved destination under the same policy. Enforce outbound network restrictions as a separate boundary, and give the fetching workload minimal internal authority. Bound response size, time and decoding resources, then verify the content is an acceptable image. Log safe diagnostic metadata without secrets. An allowlist check on only the first URL is insufficient.

The intended feature is a narrow outbound capability. Validation constrains logical destinations, while network and resource controls limit consequences if parsing or application logic fails.

Check your work

  • Validate every destination including redirects/resolution.
  • Combine application policy with egress/least privilege.
  • Bound fetch and image-processing resources.
