Stateless services, proxies & caches

[Week3.2]cache_proxie.pptx · 34 slides

Coverage

  • Slides 1–12: Where does state live?
  • Slides 13–21: Stateless workers with stateful data
  • Slides 22–28: Proxies and cache hits
  • Slides 29–34: Popularity, freshness and HTTP caching

Review findings

  • Slides 6, 7, 10, 13, 14: Stateless workers are equated with deterministic pure functions and no side effects. No durable per-client state is required in a particular worker between requests. Workers can read changing shared data, use randomness, and perform database writes; slide 6 conflicts with slide 7 on identical responses.
  • Slides 10, 21: Stateful requests always must go to the same handler; pushing state away removes coordination. Affinity is one solution; shared/replicated state is another. Coordination remains in storage, including atomic updates and concurrency control.
  • Slides 15, 16: Cookies are treated as uniformly sent to all later site requests. Cookie scope and attributes govern delivery. A cookie may hold an opaque session ID or signed claims. Signature verification is not encryption and revocation/expiry still need a design.
  • Slides 24: Proxy transparency and load-balancer capacity appear unconditional. A reverse proxy needs deployment configuration and can become a bottleneck or failure point; replication and health checks are separate design decisions.
  • Slides 31: Invalidation automatically creates coherence. Invalidation must reach relevant caches and be ordered correctly; races or delivery failures can leave stale copies.
  • Slides 32: Statelessness alone makes responses reusable; only GET may be cached. Reusability depends on method semantics, cache directives, freshness, and request variants. GET/HEAD are common; POST caching has explicit conditions. Distinguish no-cache (revalidate) from no-store (do not store), and private from public. Reference

Relational databases & scaling

[Week4]DB 1.pptx · 49 slides

Coverage

  • Slides 1–12: Why state moves into the database
  • Slides 13–19: Relational models and query execution
  • Slides 20–32: Indexes and their costs
  • Slides 33–42: Read scaling and failover
  • Slides 43–49: Sharding and fan-out

Review findings

  • Slides 6, 11: Hardware capacities/latencies and PCIe bandwidth are presented as universal. Label all figures illustrative historical values; do not reproduce them as current specifications.
  • Slides 23, 31: Binary trees described as typical disk indexes; primary key described as merely unique. Teach B-tree-family page-oriented indexes; a primary key is unique AND non-null, while unique-constraint NULL behavior depends on database. Reference
  • Slides 27, 29: Composite-index limitations and indexing rules too absolute. Leading-column predicates are generally most efficient for B-trees, but optimizer/index type matter; PostgreSQL can use skip scans. Measure selectivity and EXPLAIN rather than indexing every predicate. Reference
  • Slides 37, 38: N=R presented as optimal replica count. The algebra uses a simplified load model and does not divide total read rate across N replicas consistently. Omit universal optimum; model primary replication cost, per-replica apply cost and distributed reads explicitly.
  • Slides 41, 47: Primary-primary label for active/standby; sharding said to guarantee consistency or forbid SQL. Call it primary/standby failover. Sharding does not itself guarantee transaction consistency. SQL and sharding coexist; cross-shard behavior depends on the product.
  • Slides 44, 49: All SQL sharding must be hacked in application code. Present application-managed sharding as the illustrated architecture, not a definition of all relational databases.

Distributed data & consistency

[Week4]DB 2.pptx · 45 slides

Coverage

  • Slides 1–10: Data locality and denormalization
  • Slides 11–20: Hash partitioning
  • Slides 21–28: Replication and partitions
  • Slides 29–34: Session guarantees
  • Slides 35–40: Quorums and their limits
  • Slides 41–45: Stronger consistency and synthesis

Review findings

  • Slides 4, 10: NoSQL defined as no references, no schema, one table and one indexed key. Scope this to a teaching key-value model. NoSQL is a family; document/wide-column stores can have schemas, references, secondary indexes and richer queries. Do not define NoSQL by absent joins. Reference
  • Slides 11, 24: Hashing implies no bottlenecks and exact equal data/work distribution. Hash distribution is approximate; hot keys, value size, network, rebalancing and coordination constrain scaling. MD5 demonstration is not a security recommendation.
  • Slides 23, 25: Hexadecimal ranges have inconsistent digit widths and replication diagrams disagree. Use consistent 00000000–3fffffff,40000000–7fffffff,80000000–bfffffff,c0000000–ffffffff. Define replica ownership explicitly rather than transcribing conflicting ranges.
  • Slides 27, 28, 45: CAP pick two and centralized SQL as solution to both timeliness and consistency. State the trade-off specifically during network partitions. Centralization does not guarantee bounded latency or availability. Staleness from ordinary lag is not itself a network partition. Reference
  • Slides 33: MongoDB does not replicate. False: MongoDB replica sets replicate data and support primary election. Reference
  • Slides 35, 39: Quorum overlap with client timestamps treated as sufficient for consistency. State fixed replica-set, completed-write and version-order assumptions. Overlap alone is not a general linearizability proof; concurrent/incomplete writes and clock skew need protocols.
  • Slides 41, 45: Program-order preservation called linearizability; three session properties equated with it. Linearizability additionally respects real-time precedence across clients. Session guarantees are weaker; present them separately. Reference
  • Slides 44: HDFS, BigTable and S3 all described as DHT filesystems. Treat these as different distributed storage designs. Avoid asserting common hash routing or filesystem semantics without product-specific evidence.

Choosing a data store

Coverage

  • Slides 15–25: Documents, search and wide-column stores
  • Slides 26–31: Caches and memory data structures

Review findings

  • Slides 3: Repeats CAP/session guarantees errors. Apply the DB 2 corrections: CAP is conditional on partition, and session guarantees are not linearizability. Reference
  • Slides 5, 10, 32, 37: EBS listed as a network filesystem. EBS is block storage; EFS is file storage. Keep object, file and block abstractions distinct. Reference
  • Slides 6: SQL requires all writes on one master. Describe the single-primary relational design in the slides rather than every SQL system. SQL is a query language and relational data model does not dictate one write topology.
  • Slides 7: Gift-card transaction claims atomicity prevents double spend, but plain SELECT then overwrite races. Use SELECT ... FOR UPDATE with balance validation, or an atomic conditional UPDATE balance=balance-amount WHERE balance>=amount and check affected rows within the order transaction; handle rollback/retry. Reference
  • Slides 8, 9: Distributed transactions must lock all replicas; naive CAS spin lock offered without failure behavior. Present distributed transaction protocols as product-dependent. The sketch lacks leases, fencing, backoff and crash recovery and must not be offered as production code.
  • Slides 15, 17: _id always sharding key; journaling preserves document history. The shard key is configured and need not be _id. Journaling supports crash recovery, not application version history. Reference Reference
  • Slides 16, 17, 20, 24, 31: Ancient product/version and licensing tables presented as current. Label those tables historical and replace with durable design trade-offs. Do not repeat current licensing/protocol/feature claims without checking current vendor docs.
  • Slides 27, 28, 33: NoSQL always disk/persistent, caches always expiring, network filesystems obsolete. These are workload defaults rather than definitions. TTL/persistence/eviction are configurable product policies; file APIs remain appropriate when filesystem semantics are needed.

REST APIs & serialization

[week 7]REST API.pptx · 22 slides

Coverage

  • Slides 1–6: HTTP as an API contract
  • Slides 7–11: Retries and resource identity
  • Slides 12–19: Serialization and references
  • Slides 20–22: Choosing a protocol

Review findings

  • Slides 7: Every HTTP method except POST is idempotent; identical result is required. Idempotence concerns the intended server effect of repeated identical requests, not identical responses. Safe methods plus PUT and DELETE are idempotent; do not assume PATCH is. A retry of DELETE can return a different status. Reference
  • Slides 10, 11: Custom headers are frowned upon; verbs in paths define whether RESTful; PUT is always better. Teach noun-oriented resource naming as useful guidance, not the formal definition of REST. Standard headers are preferred when applicable; extension fields are legitimate. POST creation and PUT replacement fit different resource-ID ownership models.
  • Slides 10: API keys in query URLs are shown as ordinary authentication. Use HTTPS and an appropriate authorization header in teaching examples; query credentials can leak through logs and copied URLs.
  • Slides 14, 15, 16, 17: XML hometown tag is unclosed; HTML is asserted to be XML. Use <hometown city="Seattle"/> or an explicit matching end tag. HTML and XML have distinct syntax rules. Reference
  • Slides 14: HTML is an XML document. Ordinary HTML uses HTML syntax; an XML serialization is separately supported. Reference
  • Slides 17: Each UTF-8 character is one byte. The ASCII characters shown use one byte each; UTF-8 encodes Unicode code points using one to four bytes. Reference
  • Slides 19: JSON example includes a trailing comma after hometown_id. Remove the trailing comma; valid JSON does not allow it.
  • Slides 20, 21: Protocol Buffers is a network API transport that does not use HTTP. Protocol Buffers is a serialization format/schema system. gRPC commonly combines it with HTTP/2, so binary encoding does not imply avoiding HTTP. Reference
  • Slides 9: Live third-party demo endpoints may be stale. Use self-contained fictional examples instead of requiring Twitter or obsolete homework endpoints; do not claim these old links were verified.

Security: Trust, Identity and Access

[Week10]security.pptx · 79 slides

Coverage

  • Slides 1–20: Policies, threats and the guard
  • Slides 21–29: Security principles as architecture decisions
  • Slides 30–41: Passwords, hashes and protected transport
  • Slides 42–57: Sessions, cookies and phishing resistance
  • Slides 58–64: Authorization: lists, capabilities and labels
  • Slides 65–72: Impersonation, replay and trust
  • Slides 73–79: Browser isolation and the patching lifecycle

Review findings

  • Slides 2–7: Slides 2-7 extract only page numbers. No visual content was inferred; inspect original visuals before claiming full visual review.
  • Slides 21–24–26–28: Historical UNIX/root/wheel/SSH examples are stated as universal rules. Treat platform behavior as illustrative. Clarify existing-handle revocation semantics; SSH private keys, not public keys, need confidentiality and may need passphrase protection. Reference
  • Slides 34: TLS is said to make interception impossible and never authenticate clients. TLS protects an authenticated channel, not endpoints or logs. Client certificate authentication is supported; ordinary HTTPS commonly authenticates only the server. Reference
  • Slides 38–39–41: Generic hash length and slow_hash pseudocode can be mistaken for an implementation recipe. Use a maintained password-hashing implementation with unique salts and an appropriate work factor; do not select an algorithm solely by digest length. Reference
  • Slides 43–46: H(secret | message) is proposed as cookie protection. Replace the homegrown construction with standard HMAC or a vetted signature/session library; unkeyed hashes do not authenticate origin. Reference
  • Slides 47–51: HTTP cookies use plaintext URLs and credential query parameters are called reasonable. Use HTTPS and appropriate cookie protections; keep bearer credentials out of URLs and logs. Distinguish cookie transport from the authentication mechanism. Reference Reference
  • Slides 50: AWS access key identifiers are treated like bearer API tokens. Separate public identifiers, secret signing credentials and bearer tokens; do not teach them as interchangeable. Prefer scoped, expiring credentials and explicit rotation.
  • Slides 52–54: Hashing password plus challenge is claimed to prevent phishing and password recovery. This simple construction permits offline guessing of weak passwords and may permit real-time relay. It is not a phishing-resistant authentication protocol. Reference
  • Slides 55: Email/SMS are described as trusted interchangeable second factors. Account recovery can weaken login assurance. NIST does not allow email as an out-of-band authenticator; PSTN use is restricted, and phishing resistance requires a suitable protocol. Reference
  • Slides 56: All auth tokens are described as random server-stored strings. Opaque sessions fit that model; signed self-contained tokens are another model and require claim validation and revocation planning. Reference
  • Slides 73–79: The Chrome and Safe Browsing details are presented without dates. Label this as a historical case. Modern site isolation and privacy-preserving real-time lookups go beyond the old two-process/local-list explanation. Reference Reference
