A scalable publishing system: the NGVM case

Evaluate a historical publishing-system design through caching, storage, cost and scaling tradeoffs.

Read the case architecture and its interfaces

Source slides 1–6

The National Gun Violence Memorial case is a historical publishing-system example. A servlet application renders public pages, supports contributions and provides volunteer administration. The architecture connects a SQL database, object storage, CDN, scraper, email and payment services. Follow one read and one write through those responsibilities to explain the design before proposing additional infrastructure. The supplied picture describes the teaching case, not a verified current deployment.

The endpoint examples use action-oriented names and HTML forms. Rewriting a deletion as DELETE /victim/{id} makes the resource-oriented intention clearer, but an API style cannot be assessed from spelling alone. Authentication and authorization must still protect administrative actions. The schema captures records, photographs, comments, moderation, sessions and editing history; indexes and uniqueness constraints reveal important access patterns and integrity rules that should survive a redesign.

Worked walkthrough

Use a hypothetical city history archive to practise reading a deployment diagram. A visitor requests a public exhibit page. The application reads descriptive records from a relational database, renders the page, and includes image URLs delivered through a media service. A curator uploading a replacement image follows a different path: authenticate the curator, check editing permission, store the object, and update its metadata. One diagram contains both paths, but their failure and permission requirements differ.

Mark every crossing with the information it carries. The object store receives bytes, while the database receives identifiers, captions and relationships. The browser receives a presentation rather than unrestricted database access. If image storage succeeds but the metadata update fails, an unreferenced object can remain; if the metadata points at a missing object, the public page breaks. This small example makes interfaces concrete and exposes coordination questions before introducing more servers. Naming an endpoint after a resource helps readers, but does not settle these consistency or access-control obligations.

Place media, caching and operating cost in context

Source slides 7–10

The case stores original images, thumbnails and archived pages in object storage while retaining relational metadata in SQL. Separate representations support different display sizes and allow a CDN to serve repeated media requests. Randomized object names may reduce easy guessing, but do not create authorization. Public access is a permission choice; private or restricted content needs an explicit access policy and appropriate delivery mechanism.

The deck reports April 2020 traffic and operating expenses to connect workload characteristics to infrastructure cost. Those values are historical measurements, not a current quotation for the same service. Cost depends on storage, compute, requests and transfer patterns, while caching changes both origin load and where delivery is charged. Use the figures to reason about the original tradeoff, and obtain fresh prices and workload assumptions before estimating a new deployment.

Worked walkthrough

An archive has a two-megabyte photograph but displays a small preview in its search results. If one thousand searches each download the original, that is about two gigabytes of image transfer before protocol overhead. A forty-kilobyte preview reduces the same illustrative workload to roughly forty megabytes. Storing multiple representations spends some storage and processing to reduce repeated transfer. The relational record can identify each representation while object storage holds the bytes.

Next distinguish a cache hit from an origin fetch. A media cache can reduce repeated origin work, but total cost still depends on the charging model for storage, requests and delivery. Build a worksheet with quantities first and insert current prices only when preparing an actual estimate. A historical cloud bill is evidence about one workload and configuration, not a promise for the archive. Private images also need a permission design: an unpredictable filename alone does not establish who may fetch an object.

Scale the read path deliberately

Source slides 11–15

The proposed 200-fold traffic increase motivates changes in several places. Read replicas distribute eligible database reads, larger instances increase individual capacity and multiple stateless application instances accept requests through a load balancer. These changes solve different constraints. A replica does not automatically absorb writes to the primary, and adding application instances does not remove a database bottleneck or inconsistent local state.

Caching HTML and media can avoid origin work entirely when users can share responses and tolerate suitable freshness. Define cache keys, invalidation and exclusions for administration or personalized content. Read replicas may lag their source, so classify operations by whether stale reads are acceptable. The final design remains a monolithic application distributed across instances: scaling deployment does not require dividing business logic into independently managed microservices.

Worked walkthrough

Suppose a public archive receives one thousand page requests per second. If a shared cache answers eighty percent, two hundred requests reach the application. If each remaining page needs three database reads, the uncached read workload is approximately six hundred reads per second. These are deliberately simplified assumptions, but they show why cache effectiveness must be applied before sizing the database. Adding application workers changes application capacity; it does not by itself change those six hundred reads.

Classify the remaining requests before distributing them across replicas. A visitor reading an old exhibit may tolerate a short delay, while a curator checking an edit immediately after saving expects the new state. The first path can use a lagging replica if the product permits it; the second may require a primary read or another explicit consistency mechanism. A scalable diagram therefore needs routing rules as well as boxes. Measure the hit rate and query count under a representative mix rather than assuming every request benefits equally.

Evaluate scaling claims with workload evidence

Source slides 16–19

The source estimates eighty million monthly write-related events after scaling, or roughly thirty per second when averaged over 2.6 million seconds. That arithmetic is a starting point, not a peak-load model. One user action may cause several physical I/O operations or a transaction, while indexes, logging, batching and caching influence the cost. CPU counts and storage IOPS cannot be translated directly into proportional application throughput.

The case is comparatively cache-friendly because most traffic reads shared pages, visitors are not personalized and some visible effects can be delayed. Memorial records grow differently from page views, so traffic growth need not multiply dataset size. These are workload properties to verify rather than universal facts about publishing sites. Use measurements, service demands, peak scenarios and failure cases to evaluate capacity, and preserve integrity even when writes do not need complex cross-record business transactions.

Worked walkthrough

An illustrative service records twenty-six million updates over a thirty-day month. Dividing by approximately 2.6 million seconds gives ten updates per second on average. That calculation is useful for checking magnitude, but it conceals timing. If a news event produces one hundred updates per second for several minutes, a system sized only for the average can accumulate a backlog or reject requests despite apparently modest monthly traffic.

Also expand the meaning of an update. One user action may write a primary row, update indexes and append an audit record inside a transaction. Those actions do not map to a fixed number of physical disk operations because buffering, logging and storage behaviour intervene. Test the complete transaction with realistic data, contention and burst duration. Report latency and error rate alongside throughput. The decision to retain one primary should follow those measurements and consistency needs, rather than a direct comparison between user events and a device's advertised operations per second.

Self-check

Why are public shared pages favorable for CDN caching?

The same representation can serve many users, subject to freshness and correct cache keys.

What does eighty million events over 2.6 million seconds imply?

About 30.77 events/s on average; it says nothing by itself about peaks or physical database I/O.

Can a monolith run behind a load balancer?

Yes. Multiple application instances can share authoritative state and serve requests without requiring microservice decomposition.

Design exercise

Design the read and write paths for a 200-fold increase. State what can be cached and how a volunteer sees a just-completed edit.

Public shared pages and media can use CDN caches; authenticated administration bypasses shared caches. Stateless app instances use load balancing. Eligible stale-tolerant reads use replicas, while immediate read-after-write uses an appropriate primary/consistency path. Invalidate or version edited cache entries and test peak workload before sizing.

1. The hidden duplicate scraper

A publishing site scales its stateless application from one instance to four behind a load balancer. Each instance also starts the same hourly import timer. After rollout, the editor finds four copies of every imported story. Readers are distributed correctly, and session state is externalized. The import must run once per scheduled interval, but failed work must be recoverable. Which change most directly addresses the defect?

  1. Enable session affinity so each timer always uses its own instance
  2. Create uniquely identified scheduled jobs and idempotent imports outside each request instance’s timer
  3. Increase database capacity so four imports finish faster
  4. Disable health checks so only the original instance stays active

Worked answer

Best answer: B.

Separate scheduling from the replicated request-serving instances and represent each import interval as a uniquely identified durable job. Let a worker claim it with an appropriate coordination mechanism, and make story insertion idempotent using the source’s stable identifier. A lease or scheduler alone is not enough because a crash can occur after insertion but before completion is recorded. The other application instances can remain behind the load balancer. This preserves recoverability without allowing replicated timers to multiply authoritative content.

Stateless request handling does not make background side effects unique. Scheduling ownership and repeat-safe work require explicit design.

Check your work

  • Identifies replicated background scheduling
  • Separates durable job ownership from request balancing
  • Adds idempotent import effects for retries

2. Two independent cache layers

A public exhibit page is requested 3,600 times per second during a campaign. Its CDN serves 92% of requests without contacting the origin. For the remainder, an application cache serves 75% without a database query; each application-cache miss issues two database reads. Assume the hit rates are independent and stable. Compute origin requests and database reads per second, then explain what capacity test is missing before trusting this steady-state estimate.

Worked answer

The CDN miss rate is 8%, so the origin receives 3,600 × 0.08 = 288 requests per second. One quarter of those miss the application cache: 288 × 0.25 = 72. At two reads each, the database receives 144 reads per second. Test cold-start and synchronized-expiry behavior: if both caches are empty, the same demand could create 7,200 reads per second. Staggered expiry, request coalescing and controlled warming can reduce the surge, but their effectiveness and failure behavior need measurement.

Multiplying steady-state hit rates gives a useful average. It can conceal a much larger origin surge when cache misses are correlated.

Check your work

  • Computes 288 origin requests and 144 DB reads per second
  • Identifies 7200 DB reads/s in the stated all-miss case
  • Proposes a concrete cold-cache or expiry test

3. The withdrawn photograph remains visible

An editor removes a public photograph after a consent complaint. The database now marks it withdrawn, but the old object URL remains public and the CDN retains it for twenty-four hours. The site has generated three thumbnail sizes with different URLs. Design a withdrawal procedure that handles these copies and explain the limitation of promising that all previously downloaded copies disappear. Do not assume deleting a database row revokes object access.

Worked answer

Record withdrawal authoritatively, stop rendering new links, restrict or remove the original and each thumbnail at the object layer, and request CDN invalidation for their cache keys. Track invalidation results and retry failures; ensure the rendering and image-generation pipeline does not recreate withdrawn representations. Where stronger future-access control is required, use an authorization-aware delivery design with appropriately short-lived credentials and cache policy. These actions reduce future delivery from controlled systems, but cannot erase copies already downloaded or retained by external recipients.

Content ownership spans metadata, objects and delivery caches. Revocation must reach each controlled representation and be stated with realistic boundaries.

Check your work

  • Covers original, thumbnails and CDN variants
  • Includes retry/verification and prevention of regeneration
  • Acknowledges previously downloaded copies cannot be recalled
