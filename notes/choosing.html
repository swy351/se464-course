Choose storage by workload and correctness requirements, from transactions to analytics, search, documents, and objects.

Start with workload and invariants

Source slides 1–6

Choose storage by describing the application’s operations before choosing a product. Record the shape and size of the data, lookup keys, range queries, joins, update rates and required guarantees. Course registration needs to protect seat counts; lecture recordings need efficient delivery of large objects; course notes may need ranked text search. One application can have several distinct storage workloads.

A product category is a starting point, not a complete decision. Relational schemas can evolve, document stores can validate fields, and many systems combine capabilities. Evaluate the operations that must be atomic, the acceptable staleness and the team’s operational constraints. Using several stores is useful only when their ownership and update paths are clear enough to maintain.

Worked walkthrough

A community workshop needs to reserve machines, search project descriptions and serve tutorial photographs. Reservations must not overlap for the same machine. Search can tolerate a short indexing delay, while photographs are large immutable objects once published. These are three access patterns within one product; the shared user interface does not imply identical storage requirements.

Begin with a relational reservation store and object storage for photographs, then evaluate whether its existing text-search capability is sufficient. A separate search service becomes worthwhile only when requirements justify its indexing pipeline and recovery work. Record expected request rates, acceptable staleness, atomic operations and who operates each component. A technically capable store may still be a poor choice if the team cannot back it up, diagnose failures or restore it within the required time.

Transactions and concurrency

Source slides 7–9

A checkout updates several related facts: the order, its line items and the remaining gift-card balance. Atomicity means these changes commit together or roll back together. It does not, by itself, make a read-then-write sequence safe from another checkout. Two transactions can read the same balance and compute competing replacements unless the chosen isolation or update protocol prevents it.

One approach locks the gift-card row before checking and changing the balance. Another performs a conditional decrement that succeeds only when sufficient balance remains, checks the affected-row result and keeps the order changes in the same transaction. The application must handle conflicts and rollback. A hand-written distributed spin lock is not a substitute: it also needs ownership, expiry and crash-recovery semantics.

Worked walkthrough

A makerspace has one spare projector. Two requests each read available_count equal to one and both attempt a booking. Wrapping each request’s statements in a transaction gives all-or-nothing changes, but does not by itself specify isolation strong enough to prevent both from making the same decision. The read-and-update interaction needs deliberate concurrency control.

One approach conditionally decrements the count only when it is positive, checks whether exactly one row changed, and creates the reservation in the same transaction. The database’s supported atomic update semantics must ensure competing updates are evaluated safely. The losing request reports unavailability rather than inserting a booking. If creating the reservation fails, the decrement rolls back. Retried requests also need a way to recognize an already committed booking rather than silently creating a second one.

Storage models and analytics

Source slides 10–14

Operational transaction processing usually consists of many small reads and writes, such as fetching a student’s enrolments or reserving a seat. Analytics may scan years of records to compare enrolment trends. A column-oriented layout can read just the relevant columns and compress similar values effectively, making it attractive for broad aggregations over large datasets.

This distinction concerns workloads, not an absolute ban on indexes or a requirement that every analytical query use many machines. Analytical copies may be refreshed through ingestion pipelines and lag behind operational state. Explain that freshness before using a dashboard for an immediate decision. Running aggregation near storage also avoids sending every raw row to the application merely to calculate a small result.

Worked walkthrough

A delivery dashboard computes average journey time by district from 120 million events. It needs district, duration and date, but not the driver’s notes or the full delivery address. A column-oriented representation can read a smaller relevant subset and compress repeated values. The final result may contain only a few dozen rows, so aggregation near storage avoids transferring the entire event collection.

The operational service instead checks and updates one delivery’s state repeatedly throughout the day. That is a different access pattern, even if both stores accept SQL. If analytics imports events every fifteen minutes, a dashboard can omit recent completed deliveries without either database being broken. Display the data’s freshness and use the operational source for decisions that require current state. Benchmark representative queries rather than assuming a storage layout makes every query faster.

Documents, search and wide-column stores

Source slides 15–25

A document store can keep a nested profile as one aggregate, with a configured shard key controlling distribution. A search engine serves another need: locating documents by terms and relevance. An inverted index maps each term to matching document identifiers. A query for Watertown AND gift intersects those posting lists instead of scanning every document’s text.

Wide-column and key-value designs are often shaped around known partition keys and within-partition ordering. Sensor readings might group by device and a bounded time interval, then order by timestamp. A good design considers partition size and hot devices as well as lookup convenience. Product feature lists in the source are historical; the durable lesson is to align the storage abstraction with the actual query.

Worked walkthrough

A museum stores exhibit descriptions as documents. For keyword search, an inverted index might map “bronze” to documents {4, 9, 12} and “river” to {9, 15}. Their intersection returns document 9 for a query requiring both words. This explains retrieval mechanics, but ranking and language handling need additional rules. Updating the document also requires updating its searchable representation.

For temperature readings, a different design uses sensor_id and day as the partition key and observation_time as the within-partition ordering key. This supports one sensor’s daily range query while bounding partition growth. Searching every sensor for one interval may need another access path. A search index can lag its source, and a telemetry partition can become hot. Neither a document shape nor a key-value interface removes these workload and consistency questions.

Caches and memory data structures

Source slides 26–31

An application cache stores values that help construct responses, such as a leaderboard or precomputed summary. An HTTP reverse-proxy cache stores reusable responses at a different layer. These may coexist: an uncached personalized page can still reuse a cached shared fragment. Define which store owns the authoritative data and how cached copies expire or are invalidated.

In-memory systems can expose structures such as sets, counters and sorted sets, reducing the work required to update a small part of a value. Persistence, expiry and eviction depend on configuration; they are not determined solely by calling a product a cache. A rebuildable cache and a durable database have different recovery requirements even when they use the same software.

Worked walkthrough

A recreation centre shows a cached count of available places on its home page. The count can be briefly stale, but the booking operation checks the authoritative reservation store. This separates a fast informational view from the decision that commits scarce capacity. A time-to-live limits how long one cached value remains eligible; it does not make that value current at every instant.

For a weekly activity ranking, a sorted-set abstraction can update one participant’s score without rewriting the entire ranking. Before adopting it, decide whether the ranking can be rebuilt from durable events and what happens after eviction or restart. Also plan how simultaneous cache misses avoid overwhelming the origin. A reverse-proxy cache of a whole public page sits at a different layer from these application-managed values, even when both reduce repeated work.

Files, objects and final selection

Source slides 32–37

A mounted network filesystem provides a file interface that existing applications can use. Block storage instead exposes volumes on which a filesystem may be built; object storage exposes named objects through service APIs. These are distinct abstractions. EFS is file storage, while EBS is block storage. Object storage is a natural fit for lecture media addressed through delivery URLs.

Distributed processing historically benefits from moving computation close to data, as illustrated by HDFS. Other designs separate compute and object storage, so locality is one consideration rather than a universal requirement. Finish the selection with a small architecture: identify the owner of each dataset, the access path, consistency needs and recovery process, then explain why a simpler arrangement would or would not suffice.

Worked walkthrough

A wildlife archive stores short audio recordings as objects and keeps their searchable metadata in a database. Clients request a recording by an object identifier rather than mounting the archive as a disk. A legacy analysis program that expects directories and file operations may instead need a filesystem interface. A block volume provides lower-level storage on which a filesystem can be created; it is not itself a shared file service.

The recording and its metadata form a cross-system workflow. If an upload succeeds but the metadata write fails, the archive needs a cleanup or retry rule so abandoned objects do not accumulate. If metadata is published before upload completion, users may receive broken links. Draw these failure paths before adding stores. The final architecture should identify ownership, identifiers, access control, recovery and the reason each separate abstraction is necessary.

Self-check

Why does START TRANSACTION plus reading a balance into a variable not by itself prevent two checkouts from overspending?

Atomicity does not guarantee the required isolation. Both may read the same value; use locking or an atomic conditional decrement with balance checks and rollback behavior.

How can a search index answer Watertown AND gift?

Store a posting list of document IDs for each term, then intersect the two lists; index analysis and normalization determine token matching.

Choose stores for lecture videos, seat reservations and full-text notes search. Explain one reason for each.

Object storage for large media objects; a transactional database for seat-count invariants; a search engine/inverted index for text retrieval. Integrate them with explicit ownership and update propagation.

Design exercise

Choose storage roles for an online course service with enrolments, uploaded videos, text search, and yearly analytics. Explain how derived stores stay synchronized without becoming independent sources of truth.

Use a transactional source for enrolment invariants, object storage for large media, a search index for text retrieval, and an analytical store when broad scans justify one. These are workload-based candidates rather than mandatory products. Define authoritative ownership, change propagation, rebuildability, freshness, access control, and failure recovery for derived indexes and reports.

Additional practice

Questions-only worksheet · Worked answer sheet

1. A schema is not a deployment topology

A small legal-document team has twelve analysts, strongly related case records and frequent ad hoc joins. Its existing relational database meets measured latency and capacity targets. A proposal says to migrate everything to a document store because all SQL databases accept writes on only one machine and therefore cannot scale. No additional workload forecast or product limitation is provided. Which architectural response is best supported by this evidence?

  1. Migrate immediately because a flexible document schema guarantees higher throughput
  2. Remove joins by duplicating every record without an update strategy
  3. Add a search index and use it as the only authoritative case database
  4. Retain the current fit and require workload-specific evidence before choosing a migration

Worked answer

Best answer: D.

Retain the working relational design while investigating a concrete bottleneck or growth requirement. The existing joins and relationships fit its workload, and the proposal’s claim about all SQL systems is false: a relational interface does not universally dictate a single write topology. A document model might still help a particular aggregate-oriented workload, but that needs evidence and a migration cost analysis. Compare candidate products on actual query patterns, integrity guarantees, operational complexity and growth forecasts rather than treating the SQL/NoSQL label as a capacity measurement.

A storage migration is justified by requirements and measured limitations, not an absolute claim about an entire database family.

Check your work

  • Separates SQL/data model from topology
  • Uses measured requirements to evaluate migration
  • Recognizes operational and integrity costs

2. The lost cache must not lose the fact

A museum uses an in-memory store for a popularity leaderboard that can be rebuilt nightly. A developer proposes also storing the only copy of accepted artifact-loan agreements there because writes are fast. The configured policy evicts least-used keys at its memory limit, and disk persistence can lag. Design storage roles for both workloads and describe what should happen after a total cache loss. Keep your answer about guarantees rather than brand names.

Worked answer

Keep authoritative loan agreements in a durable transactional store with the required acknowledgement and backup/recovery policy. Use the in-memory store for a derived leaderboard, and rebuild it from durable visit or vote records after loss. If fresh rankings matter, replay changes since the latest checkpoint rather than waiting for the next night. Do not rely on eviction-prone, asynchronously persisted keys as the sole accepted agreement record. The same software might support stronger configurations, but the stated configuration does not meet this workload’s durability requirement.

The decision follows the role and configuration of a store. Fast reads, persistence options and authoritative durability are not interchangeable promises.

Check your work

  • Separates authoritative agreements from derived rankings
  • Explains a rebuild/replay path
  • Evaluates the stated eviction and persistence behavior

3. Columns and bytes actually scanned

An operations report scans 18 million equipment records. Each full row occupies 240 uncompressed bytes, but the report needs only a 4-byte site code and an 8-byte energy value. Assume a column-oriented layout can read exactly those columns and compress them by 3:1; ignore metadata, indexes and caching. Calculate bytes read for each layout and the reduction factor. Then explain why those figures alone do not prove that the transactional database should be replaced.

Worked answer

The row scan reads 18,000,000 × 240 = 4,320,000,000 bytes, or 4.32 GB in decimal units. The selected columns total 12 bytes per record; after 3:1 compression the scan reads 18,000,000 × 12 / 3 = 72,000,000 bytes, or 72 MB. The ideal read-volume reduction is 60-fold. Actual runtime also depends on decompression, execution, parallelism and storage. An analytical copy may deliver this benefit while the transactional source retains update and integrity responsibilities; freshness and ingestion costs must also be considered.

Reduced scan volume is a strong workload-specific reason for columnar analytics, not a universal replacement argument.

Check your work

  • Computes 4.32 GB and 72 MB correctly
  • Computes the 60-fold reduction
  • Distinguishes scan efficiency from transactional and freshness requirements
