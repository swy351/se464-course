Read scaling and failover

Replication introduces two separate architectural questions: where reads can run, and which machine is authorized to accept writes. We can scale the first without automatically solving the second. Start by classifying the promises made to each reader. A tutoring service updates a student’s appointment time on the primary database. A replica that has not yet applied the change still returns the old time. The write can have succeeded even though an immediately refreshed page looks unchanged. Historical appointment reports may tolerate this delay; the confirmation shown to the student should follow a path that satisfies the promised freshness. Imagine one primary handling 400 writes and 3,000 reads per second. Moving 2,400 eligible reads to three replicas leaves roughly 600 reads on the primary, but each replica must still apply the write stream. This is a workload sketch, not a capacity guarantee. If the primary fails, promoting a standby requires establishing a single writer and understanding which acknowledged writes it contains. A timeout alone does not establish that the previous writer has stopped.

Sharding and fan-out

Sharding distributes different records rather than making full copies. Its benefit depends on keeping common operations local. Let us follow a customer query, then compare it with a global report using a deliberately simple capacity model. A maintenance platform shards equipment records by customer. Fetching one customer’s inspection history stays on a single shard, while a report across all customers contacts several shards and merges their results. Placing customers evenly by count can still overload a shard containing a huge customer; traffic and record size matter as well as the routing rule. In a simplified balanced model, eight shards each provide 500 equal-cost operations per second. Requests touching one shard have an upper bound near 4,000 requests per second. If each request touches four shards, the bound drops to about 1,000. If it touches all eight, it drops to 500. Parallel requests may finish sooner than serial requests, but each still consumes cluster work. Cross-shard updates additionally need an explicit atomicity or reconciliation strategy.
