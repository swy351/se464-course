Data locality and denormalization

Source slides 1–10

Think of a relational dataset as a graph: rows are vertices and references are edges. Partitioning tries to balance the data while cutting few frequently traversed edges. An even row count is not enough if one row is exceptionally popular or a relationship triggers many downstream reads. Access frequency and query shape belong in the partitioning decision alongside storage size.

Denormalization duplicates or embeds data so a common query can retrieve an aggregate locally. A profile document can contain its positions and education rather than requiring a chain of lookups. The cost appears during updates: a shared label copied into many documents must be changed consistently if that is required. NoSQL does not universally forbid references; embedding is a modeling choice with trade-offs.

Worked walkthrough

A campsite booking page needs a reservation, its selected facilities and a short site description. Embedding a snapshot of the booked facilities can make that page a single aggregate read. Keeping the current site description separately avoids rewriting thousands of reservations whenever the description changes. The correct boundary depends on whether the page promises historical booking details or the latest catalogue information.

Suppose 2,000 reservations contain a copied access instruction. A correction now requires updating many copies or accepting mixed versions during propagation. By contrast, a historical price agreed at booking should usually remain a snapshot. Denormalization is therefore a choice about update ownership and meaning, as well as query speed. List each embedded field, its authoritative source and the rule for changing it before celebrating fewer network lookups.

Hash partitioning

Source slides 11–20

A deterministic hash maps a key to a value in a fixed hash space. Partition owners can divide that space into ranges; a client or routing layer hashes a requested key and selects its owner. This separates routing from the original key’s spelling or numeric value. The simplified model gives direct access to a key without consulting every machine.

Hash partitioning does not automatically balance traffic. Thousands of different keys may distribute well while one famous profile attracts most reads. Equal ranges also need not contain equal-sized values. Hash indexes suit equality access but discard the original ordering needed for efficient ranges. Use the key-value model to understand partitioning, while remembering that real database families can add secondary indexes and richer query operations.

Worked walkthrough

Consider a toy hash space with values zero through ninety-nine, divided into four equal ranges. A parcel identifier hashing to sixty-two is routed to the owner of the fifty-through-seventy-four range. The client needs the current ownership map as well as the hash function. When ownership changes, migration and routing must agree so requests do not silently read the wrong place.

Evenly distributed identifiers do not imply evenly distributed traffic. If one parcel receives half the tracking requests, its owner can remain overloaded while other owners are idle. Adding machines does not split that individual key’s requests automatically. Similarly, hashes scatter nearby timestamps, so a query for all parcels created between two times cannot simply walk adjacent hash values. Separate point lookup, range lookup and hot-key mitigation when evaluating the design.

Replication and partitions

Source slides 21–28

Partitioning spreads different data across machines; replication stores multiple copies of each partition. Replication allows a system to keep a copy when a machine fails, but a change reaches replicas at different times. A read may therefore see an older version unless the system coordinates the read with the required writes. Network partitions make this coordination problem more severe.

During a partition, a distributed service cannot guarantee both linearizable operations and a successful response to every request at non-failing nodes. A majority side may continue while a minority refuses certain operations. Alternatively both sides may accept operations and require reconciliation. This is a conditional trade-off about partition behavior, not a claim that all distributed systems permanently choose any two desirable features.

Worked walkthrough

A tool-rental service keeps three copies of an availability record. A network break isolates one copy from the other two. If both sides independently confirm rental of the final drill, later reconciliation cannot make both promises physically possible. A design protecting that single-item invariant may require the isolated side to refuse or delay the booking while the majority continues.

A less critical observation, such as a customer’s preferred display colour, may be accepted on both sides and reconciled later. This illustrates the CAP trade-off during a partition: linearizable behavior and a successful response to every request at non-failing nodes cannot both be guaranteed. It does not say replication is always unavailable or always inconsistent. State the operation, its invariant and the failure condition rather than assigning one slogan to the entire application.

Session guarantees

Source slides 29–34

Session guarantees describe what one client should experience. Monotonic reads prevent that client from moving back to an older version. Read-your-writes requires later reads to include its completed writes or subsequent changes. Monotonic writes preserve the order of that client’s writes. These promises are useful even when the system does not provide a single globally consistent view to everyone.

Routing a session to one up-to-date replica can help, but failure or movement to another replica can break the assumption. More robust designs carry a version or progress token and wait for a replica that has reached it. Arbitrarily sleeping is not a correctness guarantee because propagation delay has no fixed bound. State the promised property explicitly and test the failure transition.

Worked walkthrough

A field technician saves inspection version twelve and then reads the report through another replica that has reached only version eleven. Returning eleven violates read-your-writes. Later, after the technician has seen version thirteen, returning twelve violates monotonic reads even if twelve includes the technician’s own earlier change. These guarantees protect different parts of the user’s experience.

One design attaches a progress token to the session. A chosen replica serves the read only after reaching the required progress, or the request moves to a suitable replica. In this simplified single-record example the token can be a version; multi-partition systems need richer tracking. Pinning a session can reduce switches but does not by itself handle replica failure. Waiting a fixed number of milliseconds is also insufficient because replication delay is not bounded by that timer.

Quorums and their limits

Source slides 35–40

For one key replicated N times, a write may wait for W acknowledgements and a read for R responses. If R+W>N, the selected sets overlap. With three replicas and two acknowledgements for both operations, a read quorum intersects a completed write quorum. This is the useful intuition behind quorum diagrams, but the reader must still interpret versions correctly.

Overlap alone does not prove linearizability under concurrent writes, incomplete operations, changing membership or clock skew. The protocol must resolve those cases. Quorum sizes also affect availability: with one of three replicas unavailable, two-of-three reads and writes can still obtain enough responses, while a write requiring all three cannot. A large cluster remains scalable by using a bounded replica set per key.

Worked walkthrough

A record has five designated replicas. A write waits for acknowledgements from three, and a read obtains responses from three. Every possible pair of those sets overlaps because three plus three exceeds five. If two replicas are unreachable, the remaining three can still supply the required responses, assuming they are mutually reachable and the protocol’s other conditions hold.

Changing the policy to five write acknowledgements and one read response also creates overlap, but now one unavailable replica prevents writes. Neither arithmetic rule alone specifies how a reader handles different versions, concurrent writes or a write that reached some replicas before its client timed out. Those require protocol rules. Apply the calculation to the replica set for this record, not to the total number of machines in a large partitioned cluster.

Stronger consistency and synthesis

Source slides 41–45

Linearizability makes each operation appear to take effect at one instant between its invocation and completion. Its operation order must respect real-time precedence: when one operation finishes before another begins, the later operation cannot be placed before it. Concurrent operations can be ordered either way when the result remains legal for the object being modeled.

Preserving each client’s local sequence is weaker than preserving this cross-client real-time relationship. Monotonic reads, monotonic writes and read-your-writes are valuable session guarantees, but their combination is not a definition of linearizability. For an architectural decision, start with the invariant: a collaborative counter, seat reservation and activity feed may need different guarantees, even if each uses replication.

Worked walkthrough

A depot changes a gate code from A to B. The update completes before a different operator begins a read. For a linearizable register with no intervening write, that read must return B. If the read overlapped the update, returning either value might be legal, depending on where the operations take effect within their execution intervals.

Now let both operators remain on separate replicas. Each may see an internally sensible sequence while the second operator still reads A after the completed update. Preserving each client’s order does not enforce this cross-client real-time relationship. A linearizable read also cannot guarantee that a later, separate action uses current data: another write can occur between them. Protecting a combined business operation may require a suitable transaction or conditional update in addition to clear read semantics.

Self-check

With N=3, R=2 and W=2, why must a read quorum overlap a completed write quorum?

Two subsets of size two drawn from three replicas share at least one replica. This gives intersection, but correct version/protocol behavior is still needed.

A client reads version 8 then version 7 after switching replicas. Which session property fails?

Monotonic reads. If version 8 was that client's own completed write, read-your-writes also fails.

Does preserving each client's own write order prove linearizability?

No. Linearizability also requires a single legal operation order consistent with real-time precedence across clients.

Design exercise

A key has three replicas. Compare R=2,W=2 with R=1,W=3 when one replica becomes unreachable. State what you can and cannot conclude about consistency.

Both choices satisfy R+W>N, so successful read and write quorums overlap in the simple fixed-replica model. With one unreachable replica, R=2,W=2 can still meet both quorums; R=1,W=3 can read but cannot complete its configured write quorum. Overlap alone is not a proof of linearizability. Discuss version ordering, concurrent writes, repair, and the failure assumptions.

1. The isolated inventory desk

A five-node inventory service normally provides linearizable reservations for the last item of a product. A network partition separates two nodes in a remote shop from the other three. The application forbids promising the same item to two customers. The isolated shop can still accept local HTTP requests, but cannot communicate with the majority. Under these constraints, which behavior is the strongest defensible choice for a new reservation?

  1. Confirm locally because HTTP requests still reach the shop
  2. Confirm on both sides and call the service linearizable because each node is sequential
  3. Defer or reject confirmation on the isolated side while preserving the consistency contract
  4. Add a read cache and assume it can decide exclusive ownership

Worked answer

Best answer: C.

The isolated shop should decline or defer confirmation and clearly report that the reservation is not yet committed. During this partition, the service cannot both guarantee linearizable reservations and successfully complete every request on both sides. It may offer a nonbinding expression of interest, but must not label that a confirmed reservation. The majority can continue only through the system’s valid coordination protocol. This is a partition-specific trade-off; it does not mean the service must sacrifice availability during ordinary healthy operation.

The application requires one authoritative decision about a scarce item. Local acknowledgement without coordination would weaken that promise.

Check your work

  • Rejects independent confirmation on the minority
  • States the trade-off specifically during partition
  • Distinguishes deferred interest from committed reservation

2. Read latency after an unfinished write

A replicated key initially holds version 10 on nodes A, B and C. A writer sends version 11, which reaches A only, then crashes before completing its write protocol. Reader R1 consults A and B and returns 11. Later reader R2 consults B and C and returns 10; no intervening write occurred. Both readers used two responses. Explain why a quorum-intersection argument alone fails to justify these results, and identify the missing kind of protocol work.

Worked answer

The usual completed-write overlap argument does not apply to version 11 because that write never reached its required completion condition. R1 nonetheless exposed it, and the subsequent return to 10 violates a linearizable register history: once 11 is observed, the pending write must be placed before R1, so R2 cannot then return 10. A complete protocol must handle incomplete writes, for example through version validation and read-back/write-back stabilization under its specified algorithm. Merely choosing the largest value among two replies does not supply that proof.

Intersecting response sets are useful structure, but safe handling of partially completed operations is essential to the actual consistency guarantee.

Check your work

  • Recognizes that version 11 was an incomplete write
  • Explains why R1 then R2 cannot be linearized
  • Names protocol stabilization/validation rather than more arbitrary waiting

3. Denormalized names with repair

A directory embeds each laboratory’s display name into 40,000 researcher profiles to make profile reads local. The lab rename operation updates the authoritative laboratory record immediately, then asynchronously changes embedded copies. Product requirements allow names to take five minutes to converge, but an older retry must never overwrite the new name. Design the update metadata, consumer rule and repair process. Explain what this choice gains and what it does not guarantee.

Worked answer

Assign a monotonically increasing version to each laboratory name change and store that laboratory version beside each embedded name. Consumers apply a change only when its version is newer than the stored version; equal versions are safe duplicates and older versions are ignored. Track propagation progress and periodically reconcile profiles against the authoritative record to repair missed events. Alert or rebuild when the five-minute objective is exceeded. Profiles retain local reads at the cost of fan-out and temporary inconsistency; the design does not make every reader immediately see the rename.

Version-aware propagation addresses reordering, while reconciliation addresses loss. These are different failure modes of a derived copy.

Check your work

  • Uses per-laboratory versions and conditional application
  • Includes reconciliation and a measurable convergence objective
  • States local-read benefit and temporary staleness
