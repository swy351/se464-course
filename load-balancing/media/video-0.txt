Load balancing
Illustrated lesson · Part 1 · Synthetic narration

One service, many workers — One interface hides many workers

To a client, a load-balanced service can look like one powerful server: it has one familiar interface and accepts requests at a stable entry point. Behind that interface, a balancer selects one of several application workers and relays the exchange. The workers perform the expensive application work; the balancer mainly distributes and forwards it. This example makes the apparent single service expand into three workers without changing the client's request format. This is useful only if the selected worker can handle that request. If a session or unfinished operation lives exclusively in another worker's memory, routing to a healthy replica may still produce an incorrect or incomplete result.

One service, many workers — Equal counts hide unequal cost

Distributing equal numbers of requests does not necessarily distribute equal work. Suppose round robin sends one short metadata lookup to worker A, one large export to worker B, and another lookup to worker C. Each has received one request, but B may remain occupied long after the others finish. This example assigns different costs to equal request counts. Alternatives such as least-connections or weighted routing use other signals, but those signals are still approximations of useful available capacity. A persistent connection can carry very different amounts of work. Choose a policy based on the service's workload and observe completion latency, queueing, and utilization rather than congratulating the system merely for even counts.

Local routing: L4 and L7 — Keep a connection on its worker

A layer-four balancer makes routing decisions from transport information such as addresses, ports, and connection state. In a NAT-based implementation, it rewrites addressing information and preserves a mapping so packets belonging to a connection continue to the chosen worker. The return path uses that mapping to make the response appear to come from the public service. Follow one connection through the address translation instead of pretending that every packet is independently assigned to an arbitrary worker. This approach can support protocols beyond HTTP because it does not need to understand application resource names. NAT is one implementation technique, however, not the definition of every layer-four load balancer.

Local routing: L4 and L7 — Inspect HTTP after TLS termination

An HTTP-aware reverse proxy operates at a different boundary. It can inspect a request path and route image requests to one pool while sending account requests to another. For encrypted HTTP traffic, the proxy must terminate the incoming TLS connection before it can inspect the HTTP message; it may then establish a separate encrypted connection to the selected upstream. In this example, notice the path-based decision after TLS termination, with two possible destinations. That extra understanding enables features such as application routing, compression, and eligible response caching, but also creates configuration and processing work. The proxy must preserve the intended authentication, forwarding, and cache behavior across the boundary.
