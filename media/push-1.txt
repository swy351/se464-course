WebSockets, long polling and alternatives

A workshop dashboard polls every ten seconds for a changed machine status. With changes occurring at arbitrary times, the average wait until the next poll is about five seconds, ignoring request latency. Reducing the interval lowers that wait but increases the number of requests even when nothing changes. A WebSocket keeps a bidirectional channel open, while long polling lets the server hold a request until data or a timeout becomes available. The connection does not eliminate state recovery. If a browser loses its network for thirty seconds, it may miss several transitions regardless of the chosen live transport. On reconnect, retrieve the current authoritative status or resume from a position supported by the application protocol. Distinguish a dashboard that needs only the latest temperature from an audit screen that needs every transition. That requirement determines how much history must be retained. Compare latency, idle connection resources and reconnect behaviour, rather than choosing a protocol solely because it is described as real time.


Routing to the correct connection

An account has two browser tabs, one connected to notification worker A and another to worker B. An appointment service running elsewhere generates an update. Sending the update to an arbitrary notification worker is insufficient: only the worker holding a particular live connection can write to it. A registration directory maps the logical recipient to connection identifiers and their owners, allowing the notification layer to route to both tabs. Close one tab just after the directory lookup. The route can become stale between lookup and send, so lookup success cannot guarantee delivery. Clean up failed destinations and let reconnecting clients establish fresh registrations. Keep transport failures separate from the underlying appointment change, which remains stored independently. If the design promises recovery of missed updates, retain an appropriate event history or provide a fresh-state read. Trace a worker restart as well as a normal send; this reveals why connection ownership, authoritative data and notification progress are different kinds of state.
