Load balancing

Week 7 · October 19

One service, many workers

The interface stays the same

Imagine a course registration service. A browser sends GET /courses to one hostname. A load balancer forwards the request to one of several equivalent application servers, then relays the response. The client does not need the list of workers.

Replicas add processing capacity only while another shared resource, such as the database, is not the bottleneck. The load balancer itself has finite capacity and needs a redundancy strategy.

What makes workers interchangeable?

With stateless application workers, any healthy replica can handle the next request. Persistent data still exists, but lives outside a particular worker, for example in a shared database or session store. If a shopping cart exists only in worker A’s memory, routing the next request to B may appear to lose the cart.

Sticky sessions can keep a client on the same worker. They complicate balancing and do not recover the session if that worker fails. Stateless workers simplify replacement, but the shared storage system must also meet availability and capacity requirements.

Choosing a worker

Round robin rotates through eligible workers. It is easy to understand, but equal request counts do not guarantee equal work. Least connections selects a worker with fewer active connections. Connection count is still only a proxy for workload. Weighted policies account for unequal capacities.

Worked walkthrough

A public archive adds three application workers behind one service address. With round robin, six incoming requests can be distributed two per worker. That sounds balanced until one request generates a large export while the others read a small record. Equal request counts do not imply equal work or equal completion times. A routing policy uses observable signals, and those signals are only approximations of the capacity each worker has available.

Next ask whether workers are interchangeable. If an export’s progress exists only in worker A’s memory, sending a follow-up request to B may fail even though B is healthy. Durable progress in shared storage can allow replacement, but that storage now needs its own capacity and failure design. The balancer gives clients a stable entry point and can hide worker membership changes. It does not remove every dependency behind that entry point. Follow one request to storage and back before claiming that adding workers has multiplied end-to-end capacity.

Local routing: L4 and L7

Layer 4: transport information

A layer-4 balancer routes using transport and network information such as IP addresses, ports, and protocol. A NAT-based implementation rewrites addresses or ports and maintains mappings so return traffic reaches the client. Packets belonging to an established connection need consistent handling.

NAT is one implementation of L4 balancing, not its definition. L4 systems can also proxy TCP connections. Their available features depend on the implementation.

Layer 7: application information

An HTTP reverse proxy understands HTTP requests. It can route /images/ to one pool and /api/ to another, terminate TLS, and apply application policies. It may cache eligible responses or compress content.

Reverse proxies can stream data; they do not universally wait for an entire request or response. Buffering is configurable in systems such as NGINX. TLS termination at the proxy also does not require plaintext upstream traffic: the proxy can establish another TLS connection to the worker.

Worked walkthrough

The archive serves metadata and large scans through the same HTTPS hostname. If routing must distinguish /records from /scans, some component must inspect HTTP information. An ordinary IP-and-port decision cannot see that distinction inside encrypted application traffic. An HTTP-aware reverse proxy can terminate TLS, inspect the path and select an appropriate worker pool. It may establish a second encrypted connection upstream; termination does not require leaving the internal hop unprotected.

For a generic transport service, a layer-four balancer may be a better fit because it routes using connection information without interpreting HTTP resources. NAT is one implementation, not the definition of layer-four balancing. Likewise, a reverse proxy need not wait for an entire document before forwarding it: streaming and buffering depend on implementation and configuration. Compare designs using the features required by this workload, then benchmark realistic payloads, connections and security settings. Historical throughput examples should not become universal limits for either layer.

Failures and safe deployments

Health is observed, not known instantly

A periodic probe can detect an unhealthy worker. A timeout can mean a crash, overload, a network issue, or a dependency failure. Production policies often require several failed probes before removing a worker, and successful probes before restoring it.

Detection takes time. Requests may fail before removal. Readiness checks should reflect whether an instance can serve traffic, without making a shared dependency outage unnecessarily remove every replica. Design timeouts, retries, and retry budgets together. Blind retries can amplify overload; retrying a payment may duplicate an action unless it is made idempotent.

Rolling updates

  1. Remove one worker from eligibility for new requests.
  2. Let in-flight work drain, subject to a deadline.
  3. Deploy the new version and check readiness.
  4. Return it to service, then repeat.

Remaining workers need spare capacity. Old and new versions coexist, so APIs and database schema changes must remain compatible during the transition.

Switching between two pools

A blue-green deployment prepares a second pool, verifies it, then switches new traffic. It needs extra capacity and a rollback plan. Existing connections may remain on the old pool; a configuration change does not make every client switch at precisely the same instant. Database migrations can also make application rollback unsafe.

A single load balancer can fail too. Redundant balancers or a managed service address that risk. A second region addresses a different failure domain: losing a whole data center.

Worked walkthrough

The archive runs four workers, each measured to handle 100 requests per second for a specified workload. At 280 requests per second, removing one worker leaves a nominal capacity of 300. That small margin may be inadequate once request costs vary or a dependency slows. A rolling deployment needs spare capacity as well as a sequence of replacement steps. Stop new assignments, allow existing work to drain within a deadline, deploy, and verify readiness before returning the worker.

A failed health probe is evidence that the checked path did not respond acceptably; it is not proof of a process crash. Overload, network trouble or a dependency can produce the same observation. Failure thresholds reduce reactions to brief disturbances but delay removal, so some requests may fail before routing changes. Explain what clients may retry and with what limit. During a rolling update, old and new versions coexist, which makes API and storage compatibility part of deployment safety rather than an optional cleanup task.

DNS and global discovery

A directory with caches

A client normally asks a recursive resolver for a hostname’s address. The resolver can answer from its cache; otherwise it follows DNS referrals to obtain an authoritative answer. A service can publish multiple addresses or vary answers according to routing policy.

Many clients share resolvers. An answer can therefore influence a whole group of users. Multiple addresses do not guarantee equal per-request balancing: client selection, connection reuse, and caching all affect the result.

TTL and failover

The time to live (TTL) tells a cache how long a record may be reused under normal caching rules. Changing the authoritative answer does not immediately replace already cached answers. Existing TCP connections do not perform another DNS lookup for every request.

A lower TTL trades faster opportunity to refresh against more DNS queries. It is not an exact outage-duration guarantee: detection delays, client caching behavior, retries, and existing connections also matter.

Geographic steering

DNS can select a regional endpoint using location or latency information. The authoritative server often sees the recursive resolver’s address; EDNS Client Subnet can sometimes provide partial client-network information. Resolver location may not match the end user’s location.

A common architecture combines global DNS steering with a regional load balancer in front of stateless workers. Regional capacity, data replication, and failover policy still need explicit design.

Worked walkthrough

A resolver receives Region East with a 90-second TTL at time zero. At time 20, the authoritative policy switches new answers to Region West. Under the simplified ordinary-cache model, a lookup at time 50 can still receive East from the resolver’s cache; the answer becomes eligible for refresh at time 90. Updating the authority changes future answers, not every previously distributed copy at the same instant.

Existing connections add another layer: a client may continue using an established connection without repeating DNS for every request. Multiple clients may also share one resolver, so a single cached answer can direct a large group. Geographic steering often estimates location from the resolver or partial client-network information, rather than knowing each user’s precise position. Treat DNS as a discovery mechanism with caching behavior. Combine it with regional load balancing and an explicit data recovery strategy; changing a name-to-address answer does not by itself make another region ready to accept writes.

CDNs and anycast

Cache hits avoid origin work

The origin is the authoritative application or content server. An edge server acts as a caching proxy. On a fresh cache hit it can answer locally; on a miss it fetches from the origin and may store an eligible response. A stale entry may require validation or refetching.

For a simplified workload of 1,000 identical-size, cache-eligible requests per second and a 90% hit ratio, the origin receives about 100 fetches per second. This estimate ignores revalidation and other traffic. Personalized pages and writes need different treatment.

Reading Cache-Control carefully

DirectiveMeaning
public, max-age=60Allows shared caching; fresh for 60 seconds, subject to other caching rules.
private, max-age=60A private browser cache may store it. A shared CDN cache must not store the whole response.
no-cacheStorage can be allowed, but reuse requires successful validation.
no-storeThe cache must not store the response.

max-age=0 makes a response immediately stale. It does not mean “never store.” Durations are seconds: 86,400 is one day; 31,622,400 is 366 days. These are illustrative policies, not claims about the current headers of third-party sites.

One address, multiple sites

With IP anycast, multiple locations advertise reachability to the same IP prefix using BGP. Network routing selects a path. “Closest” means according to routing policy and topology, not necessarily geographic distance or lowest latency.

Anycast supports more than UDP DNS, but route changes can disrupt stateful connections if traffic shifts to a site without the connection’s state. Providers engineer routing stability and service behavior around this. Managed offerings can supply anycast without each customer operating an autonomous system.

DNS steering, anycast, and caching solve different problems and can appear together in one CDN. None removes origin, storage, capacity, or consistency constraints.

Worked walkthrough

The archive publishes a scanned map under an immutable versioned URL. If 2,000 eligible map requests arrive per second and edge caches serve 92 percent as fresh hits, a simplified model sends about 160 fetches per second toward origin. This estimate excludes validation and other traffic, but it shows the source of the benefit: saved content answers repeated reads near users. A private account page is a different object and cannot safely share the same reuse policy.

Anycast answers a different question: which network location receives traffic for an address advertised from several sites? Routing chooses a path using network policy and topology, not a guarantee of geographic nearness. A CDN can use anycast, DNS steering and caching together. Cache directives still determine whether an answer may be reused, and route changes still need handling for established connections. A private directive excludes shared-cache storage of the whole response; a long max-age does not override it. Distinguish traffic steering, content reuse and application correctness when reviewing an edge design.

Design review and self-check

Design exercise: course registration

Design a service for a registration opening that creates a sudden traffic burst. Static course images can be cached. Seat availability changes quickly. A student must never be charged twice or receive a seat that another transaction has already taken.

  1. Draw the path from DNS to an edge, a regional load balancer, workers, and storage. Distinguish cacheable reads from writes.
  2. Choose L4 or L7 for the regional entry point and justify the features you need.
  3. Explain worker failure detection, draining, and a rolling deployment.
  4. Explain regional failover while some DNS answers remain cached.
  5. Identify the data consistency problem that adding more workers does not solve.
Open a sample design discussion

Use DNS or a managed global routing service to choose a healthy regional entry point. Cache public, versioned static assets at the CDN. Route registration writes to the application through an HTTP L7 load balancer if path routing and HTTP policies are needed. Use stateless workers, with authentication/session state in a suitable shared service.

Make seat allocation atomic in the data layer and use an idempotency key for payment or registration retries. Protect the database with admission control or a queue if appropriate. A cross-region write strategy must define ownership and replication semantics; merely duplicating the application does not prevent overselling.

Drain and replace workers gradually while preserving version compatibility. Regional failover needs spare capacity, tested data recovery, and a policy for stale DNS answers and existing connections.

Suggested assessment rubric

10 points: request path and caching boundaries (2), layer choice (2), worker failure and deployment behavior (2), DNS/region failover limits (2), data consistency and retry safety (2). Alternative designs earn credit when their assumptions and tradeoffs are sound.

Worked walkthrough

Design an archive service for the morning a newly digitized collection opens. Public scans can use versioned URLs and edge caching, while requests to reserve the last available research-room seat must reach application logic and authoritative storage. Draw DNS discovery, the edge, a regional entry point, workers and storage. Label where a read may be answered without contacting origin and where a write must be checked against current state.

Now fail one worker during the surge and one region during a reservation. Explain the delay before health information changes, what happens to in-flight requests and which clients might still use cached DNS answers. A retry must not create two reservations, and a second worker must not allocate the same final seat concurrently. Those requirements need an explicit data and operation contract, not just another load balancer. A convincing design combines routing, capacity, freshness and recovery assumptions, then tests the failure cases that could violate them.
