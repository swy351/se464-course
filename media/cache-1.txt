Stateless services, proxies & caches
Illustrated lesson · Part 2 · Synthetic narration

Proxies and cache hits — A miss fills; a hit stops early

A proxy is an intermediary: it accepts the client's request, knows which upstream service can answer it, and relays the response. Add storage to that intermediary and it can remember reusable answers. On the first request for article A, the cache has no matching entry, so it forwards the request to the application. The application reads data and constructs the response; the proxy saves an eligible copy while returning it. A second equivalent request can be answered directly from that copy. In this example, notice the miss visiting origin and the hit stopping early. The performance gain comes from avoiding repeated work, not from making the original computation intrinsically faster.

Proxies and cache hits — LRU predicts the next reuse

Let us actually run the eviction policy. There is room for three equally sized items. After accessing A, then B, then C, the shelf reads A, B, C from oldest to newest. All three spaces are occupied. The question is not simply which objects are present. We also need to remember their recency. Now access A again. This is a hit, so we do not fetch another copy. But we do change the order. Move A to the newest end. The shelf now reads B, C, A. B has become the least recently used item. A hit changes the next eviction decision. Finally, D arrives. The shelf is full, so remove B and place D at the newest end. The result is C, A, D. LRU uses recent access as a prediction of future usefulness. That prediction often helps with temporal locality, but a scan of unrelated objects can still evict a valuable working set.

Popularity, freshness and HTTP caching — Popularity concentrates traffic

Why can a small cache remove a large fraction of service traffic? Requests are often unevenly distributed. A few popular articles receive repeated reads while many less popular articles form a long tail. If a cache stores the frequently requested subset, its fraction of all stored documents can be small even while its fraction of answered requests is large. For an illustrative workload of one thousand requests per second with a ninety percent hit ratio, only about one hundred misses per second reach origin, ignoring validation and other traffic. This example separates the hot set from the long tail rather than treating all documents as equally likely to be requested.

Popularity, freshness and HTTP caching — An edit does not refresh copies

The price of reuse appears when an authoritative value changes after a cached copy was saved. Suppose a public timetable response can remain fresh for sixty seconds. At time zero the proxy stores version one; at time twenty the origin publishes version two. An otherwise eligible request at time forty can still receive version one under that freshness policy. At expiry, the cache must refresh or validate before ordinary reuse. This example places the edit and expiry on separate paths to show why updating origin does not instantly update every copy. Select a freshness window from the application's tolerance for stale information, not only from the hit ratio you hope to achieve.
