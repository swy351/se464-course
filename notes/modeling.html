Choose what the architecture model must explain

Source slides 1–9

An architectural model records selected design decisions, not every fact about the program. Components, connectors, interfaces, configurations and rationale answer different stakeholder questions. The web-system examples show how a cache, application, database, object store and external services can be placed in a shared picture. The important question is what each element and edge means and which decision the picture helps evaluate.

Choose detail and formality according to the benefit of creating and maintaining the model. Include constraints on interaction, concurrency or behavior when those constraints matter. Static structure and runtime state are different perspectives, although a running system can also change topology through scaling or redeployment. Functional and quality concerns can both be modeled; “prints medical records” leaves speed and confidentiality unresolved until the description specifies relevant conditions and evidence.

Predict: Is a more detailed model always more useful?

No. Detail incurs maintenance and cognitive costs; select what answers consequential stakeholder questions.

Estimate before committing to implementation

Source slides 10–20

Performance modeling can reveal a costly design before a full system exists. Execution graphs estimate scenario work; queueing networks estimate contention; other approaches can use simulation or learned relationships. Models allow early comparison of alternatives and resource needs, but their answers remain conditional on assumptions about operations, infrastructure and workload. A plausible model is an engineering aid rather than a performance guarantee.

Execution models in this unit omit resource contention. Their service costs therefore provide a baseline, not the response a busy production system must achieve. Finding an unacceptable baseline is valuable because queueing will not rescue it. Passing that check does not prove adequate loaded performance. Combine early models with prototypes and subsequent measurements, revising parameters as evidence becomes available instead of treating modeling and testing as mutually exclusive stages.

Predict: If an execution graph predicts 100 ms without contention, is 100 ms guaranteed under concurrent users?

No. Queueing, interference and model omissions can increase response time.

Reduce execution graphs

Source slides 21–31

Execution graphs make a scenario’s control flow explicit. Basic nodes represent processing steps; expanded nodes refer to another graph. Repetition nodes specify loops, case nodes select alternatives, parallel-and-join nodes wait for all branches and division nodes start work that need not finish before continuation. These distinctions determine whether work contributes directly to the response being measured.

Reduce simple structures while preserving the chosen metric. Sequential times add, a fixed loop multiplies its body cost by the repetition count and a case uses the minimum, maximum or probability-weighted average according to the question. Parallel elapsed time can depend on the longest branch only under assumptions about available resources and synchronization. Keep best path separate from best resource conditions: an average path without contention is still not an average loaded response.

Predict: Two exclusive branches take 10 and 90 ms with probabilities .9 and .1. What is expected branch cost?

0.9×10+0.1×90=18 ms, plus any case-node overhead.

Translate software actions into resource demand

Source slides 32–37

A basic operation may request abstract software services such as server work, database access and messaging. An overhead matrix maps each service unit onto CPU instructions, disk operations and network messages. Multiplying requested service units by that matrix yields resource quantities, which are then converted into time using device-specific service costs. Carry units through every multiplication to avoid confusing instructions with thousands of instructions.

The authorization illustration combines 3,110 CPU units at .00001 seconds, fourteen disk operations at .02 seconds and one network operation at .01 seconds. The total no-contention service time is .3211 seconds, approximately .32 seconds. These costs can also become device demands for a later queueing model. Keep the per-device vector as well as the scalar sum, because equal total work can create very different bottlenecks on different resources.

Predict: Why retain separate CPU, disk and network demand after summing execution time?

A contention model needs each resource’s demand to identify utilization and bottlenecks; the scalar total loses that information.

Why does a division node differ from parallel-and-join?

Division starts work that need not all complete before continuation; a join waits for every attached branch.

What is missing when execution cost meets a latency target?

Evidence about contention, workload, model fidelity and measurement under relevant conditions.

1. Choose the correct critical path

A document preview request validates input for 12 ms, then starts two independent operations on separate unconstrained resources: image generation takes 45 ms and metadata extraction takes 20 ms. The response waits for both, then packages the result for 8 ms. Ignore launch overhead and contention. Which no-contention response estimate is correct, and what property of the graph determines it?

  1. 40 ms, because the first branch to finish determines the response.
  2. 45 ms, because validation and packaging overlap automatically.
  3. 85 ms, because all operation times must always be added.
  4. 65 ms, because validation and packaging surround the slower parallel branch.

Worked answer

Best answer: D.

The estimate is 12+max(45,20)+8=65 ms. Both branches are required, but they overlap on the explicitly separate resources. Adding all node times would measure accumulated work rather than this elapsed response path. Using the shorter branch would return before image generation completes. This estimate depends on the stated independent-resource and zero-overhead assumptions; if both operations contend for one resource or a synchronization cost exists, the graph or resource model must change before reusing the result.

A parallel join contributes its critical branch under the stipulated assumptions, not the sum of overlapping branch durations.

Check your work

  • Identifies the join and critical branch
  • States the resource assumption

2. An optimization that moves the bottleneck

Two implementations of an image-tagging request have equal no-contention total demand of 60 ms. A uses 50 ms CPU and 10 ms disk; B uses 20 ms CPU and 40 ms disk. The deployment has two CPU cores and one disk service station. Assume demands consume these resources exclusively, all requests follow the same path, and throughput is bounded by resource demand. Derive the ideal capacity bound for each design and explain why equal baseline times do not imply equal scalability.

Worked answer

For A, CPU capacity is 2/.050=40 requests/s and disk capacity is 1/.010=100 requests/s, so the ideal bound is 40 requests/s. For B, CPU allows 100 requests/s but disk allows only 25 requests/s, giving a bound of 25 requests/s. Both sum to 60 ms without contention, yet B concentrates work on the less-replicated resource. These are capacity bounds, not latency predictions or guaranteed sustainable operating points; scheduling, queueing and other overhead require further analysis and measurement.

Preserving the per-resource demand vector exposes bottlenecks that a single execution-time total hides.

Check your work

  • Derives resource-specific bounds
  • Chooses the correct limiting resource
  • Distinguishes capacity bound from measured throughput

3. Compare optimizations through a resource matrix

A weather bulletin executes two Encode actions sequentially, then either one Lookup (probability 0.8) or three Lookups (probability 0.2), then a fixed 3 ms finalization. The resource matrix is: Encode = 300 CPU units, 0 disk I/Os, 1 network message; Lookup = 100 CPU units, 2 disk I/Os, 0 messages. Costs are 0.02 ms/CPU unit, 3 ms/I/O and 1 ms/message. Assume all costs add, with no contention. Calculate expected bulletin time, then compare halving Encode CPU work against halving Lookup disk work.

Worked answer

Encode costs 300×.02+1×1=7 ms; Lookup costs 100×.02+2×3=8 ms. Expected Lookup count is .8×1+.2×3=1.4. Expected time is 2×7+1.4×8+3=28.2 ms. Halving Encode CPU work saves 2×(300×.02/2)=6 ms, giving 22.2 ms. Halving Lookup disk work saves 1.4×(2×3/2)=4.2 ms, giving 24 ms. Choose Encode optimization for this no-contention mean objective. This conclusion does not determine loaded response: disk contention could make reduced disk demand more valuable under concurrency. Both alternatives hold branch probabilities fixed and must preserve the same correct bulletin output.

The matrix reveals which resource contribution changes. A larger reduction in unloaded average execution time need not dominate after queueing is introduced.

Check your work

  • Converts matrix rows with correct units
  • Computes probability-weighted time and both savings
  • Distinguishes no-contention result from loaded performance
