Distributed data & consistency
Part 2 • Synthetic narration

Session guarantees

Session guarantees describe what one client may observe across requests. They are more precise than saying that data is eventually consistent. Follow one inspection report as its reader changes replicas, and name the guarantee broken at each step. A field technician saves inspection version twelve and then reads the report through another replica that has reached only version eleven. Returning eleven violates read-your-writes. Later, after the technician has seen version thirteen, returning twelve violates monotonic reads even if twelve includes the technician’s own earlier change. These guarantees protect different parts of the user’s experience. One design attaches a progress token to the session. A chosen replica serves the read only after reaching the required progress, or the request moves to a suitable replica. In this simplified single-record example the token can be a version; multi-partition systems need richer tracking. Pinning a session can reduce switches but does not by itself handle replica failure. Waiting a fixed number of milliseconds is also insufficient because replication delay is not bounded by that timer.


Quorums and their limits

Quorum diagrams help us reason about which copies must meet. The arithmetic is useful precisely when we keep its assumptions visible. Work through a five-replica example, then separate set intersection from the stronger guarantee we may want. A record has five designated replicas. A write waits for acknowledgements from three, and a read obtains responses from three. Every possible pair of those sets overlaps because three plus three exceeds five. If two replicas are unreachable, the remaining three can still supply the required responses, assuming they are mutually reachable and the protocol’s other conditions hold. Changing the policy to five write acknowledgements and one read response also creates overlap, but now one unavailable replica prevents writes. Neither arithmetic rule alone specifies how a reader handles different versions, concurrent writes or a write that reached some replicas before its client timed out. Those require protocol rules. Apply the calculation to the replica set for this record, not to the total number of machines in a large partitioned cluster.


Stronger consistency and synthesis

To evaluate a consistency claim, draw when each operation starts and finishes. A legal explanation must respect completed operations that precede later calls. This small history makes the difference between session behavior and linearizability visible without relying on slogans. A depot changes a gate code from A to B. The update completes before a different operator begins a read. For a linearizable register with no intervening write, that read must return B. If the read overlapped the update, returning either value might be legal, depending on where the operations take effect within their execution intervals. Now let both operators remain on separate replicas. Each may see an internally sensible sequence while the second operator still reads A after the completed update. Preserving each client’s order does not enforce this cross-client real-time relationship. A linearizable read also cannot guarantee that a later, separate action uses current data: another write can occur between them. Protecting a combined business operation may require a suitable transaction or conditional update in addition to clear read semantics.
