Read and write class diagrams

Source slides 1–19

A class diagram summarizes selected structural facts. Class boxes can show names, attributes and operations; visibility symbols communicate access, while inheritance and interface realization express different contracts. Associations describe relationships between instances, with multiplicity constraining how many may participate. The BankAccount and Student–Course examples connect these symbols to code so that notation supports an explanation rather than becoming a memorization exercise.

Read multiplicity from the relevant association end and distinguish capacity from actual participation. An array with thirty slots is not evidence that thirty courses are always assigned. Composition expresses strong ownership in the model, whereas an ordinary association need not imply a shared lifetime. Nested classes, dependencies and notes add detail when needed. Correct partial snippets before treating them as runnable implementations, and state conventions where the diagram omits information.

Predict: Does a Student containing a Course array of length thirty imply exactly thirty enrolled courses?

No. Storage capacity does not establish actual enrollment; multiplicity should express the intended domain constraint.

Patterns as reusable design knowledge

Source slides 20–28

UML can be used selectively to resolve a design question rather than to document every implementation detail. The cited industry study illustrates different usage patterns, not a universal adoption rate for every team. A diagram earns its place by helping collaborators reason. Design patterns likewise provide reusable language for a problem, a solution structure and the consequences that accompany it.

A pattern is not a mechanical recipe. Its forces and tradeoffs must fit the system, language and expected changes. The architectural-doorway example makes this concrete: the layout responds to patterns of movement rather than to an abstract preference for doors in corners. Composition delegates behavior through collaborating objects, while inheritance commits to a subtype relationship and its contracts. Prefer the mechanism that expresses the relationship and controls the intended variation.

Predict: Should every recurring code fragment be replaced by a named design pattern?

No. Use a pattern when its problem and tradeoffs match; adding structure without a need can reduce clarity.

Single responsibility and cohesion

Source slides 29–40

The single responsibility principle asks whether a class has one coherent reason to change. Responsibilities arise from the concerns and policies it serves, not simply the number of methods. A cohesion graph connecting methods that share fields can expose clusters, but shared state is only a clue. Methods can share a field while serving unrelated purposes, and a coherent responsibility can use several data structures.

The split-class exercise asks which changes should remain independent. Separating storage, formatting or domain calculations can reduce the number of clients affected by a change. The historical Date API example illustrates the long-lived cost of mixing concerns in a public library. Compatibility limits cleanup after release, so careful boundaries matter. Avoid splitting every method into its own object; the goal is a coherent model with understandable responsibilities and interfaces.

Predict: If every method touches the same field, has SRP been proved?

No. Shared fields suggest structural cohesion but do not establish a single policy or reason to change.

Design for extension

Source slides 41–48

The painter example initially knows how to draw each concrete shape. Adding a triangle requires another branch or loop in the painter, spreading the variation into a client. Introducing a Shape operation moves drawing behavior behind a shared contract. The painter can then iterate over shapes without naming every concrete type, making the supported extension point explicit.

Open–closed design protects stable behavior from selected kinds of change; it does not forbid editing code or demand inheritance for every extension. Composition, strategies and registration can serve the same purpose. Adding a shape may still require creation or configuration changes elsewhere. The key question is whether the abstraction matches the expected variation, and whether its contract is sufficient for new implementations to work without special cases in the client.

Predict: After introducing Shape.draw, must every file remain unchanged when Triangle is added?

No. The painting loop can remain stable, while Triangle and its creation or registration still need implementation.

Substitutability and contracts

Source slides 49–60

Substitutability concerns behavior visible to clients. If a client works under a supertype contract, replacing an object with a subtype should not invalidate those expectations. A subtype must not demand stronger preconditions or provide weaker guarantees. Phrase this through implications: every input accepted by the supertype must remain acceptable, and the subtype’s successful outcome must satisfy the supertype’s promised result.

The mutable Rectangle example promises independently adjustable width and height. Square breaks that promise by changing both dimensions in a setter, so a client expecting area fifty receives one hundred. This is a contract problem rather than a statement about geometry. The unmodifiable List example needs different care: Java documents optional mutators, so an exception can be permitted by the declared contract. A client requiring mutation needs a stronger capability guarantee.

Predict: Does the mathematical fact that every square is a rectangle prove mutable Square is a behavioral subtype?

No. The programming interface’s mutation promises, not just geometric membership, determine substitutability.

Client-focused interfaces and dependency inversion

Source slides 61–74

Interface segregation focuses on what each client needs to depend on. A broad interface can mix reading, writing and event handling even when many clients need only one role. Smaller role interfaces make capabilities clearer. An adapter with default no-op callbacks may reduce implementation effort, but it does not erase the conceptual breadth of the original interface.

Dependency inversion places policy behind stable abstractions instead of binding it directly to implementation details. JDBC illustrates application code using a database-facing API implemented by drivers. The boundary can localize many implementation changes, while behavioral differences and contract changes may still affect clients. Together, these principles encourage focused contracts owned by the needs of the caller, with concrete implementations replaceable only to the extent that they preserve those contracts.

Predict: Does adding an interface guarantee callers are unaffected by every implementation change?

No. Changes in observable behavior, contract or supported capabilities can still affect callers even when method signatures remain stable.

Self-check

A painter iterates over Shape objects and calls draw. What changes when Triangle is added?

Add a Triangle implementation and arrange its creation/registration; the generic painting loop can remain unchanged if the Shape contract suffices.

Why does Square fail the mutable Rectangle client that sets width=5 then height=10 and expects area=50?

Its setters change both dimensions, violating the client-visible contract that the dimensions can be changed independently.

Is UnsupportedOperationException from an unmodifiable List necessarily a violation of its documented List contract?

No. List specifies optional mutating operations; the client must require/support mutability explicitly. Separate read and write interfaces can make that requirement clearer.

Design exercise

A report class calculates grades, formats HTML, writes SQL, and sends email. Propose boundaries and interfaces, then explain one benefit and one cost. Show how adding a PDF renderer affects the design.

Separate grading policy, rendering, persistence, and delivery where they change for different reasons. Depend on narrow interfaces at the policy boundary. A PDF renderer can implement the rendering contract without changing grading logic. Do not create an interface for every trivial method: extra abstractions carry navigation and maintenance costs. Test behavior and substitutability.

1. A subtype that rejects a valid client

A scheduling library exposes Notifier.send(message), whose documented contract accepts any nonempty message up to 1,000 characters. A new SMSNotifier implementation rejects messages longer than 160 characters, although existing clients may send 500-character messages. Which redesign best preserves the stated client contract while making the SMS limitation explicit?

  1. Keep the implementation because clients should know SMS limitations.
  2. Silently truncate all long messages.
  3. Rename SMSNotifier to FastNotifier without changing behavior.
  4. Use a narrower SMS capability or an adapter that fulfills the original delivery contract.

Worked answer

Best answer: D.

The appropriate choice is to separate the SMS capability or introduce an adapter that genuinely fulfills the original contract. Merely throwing for messages above 160 characters strengthens the precondition and breaks valid existing clients. An adapter might split messages only if that behavior satisfies the documented delivery semantics; it must not silently truncate content. A narrower SMS interface can require clients to choose compatible behavior explicitly. Renaming the implementation or adding an exception comment does not repair substitutability under the original contract.

The problem is a mismatch between promised accepted inputs and the replacement implementation, not whether inheritance syntax compiles.

Check your work

  • Identifies strengthened precondition
  • Chooses a contract-preserving or explicitly narrower interface

2. Design an extension point with an exception

A shipping service chooses a price policy by destination region. Next quarter it must support promotional policies installed by another team. Compliance also requires a mandatory tax calculation that plugins must not bypass. Propose the responsibilities and narrow interfaces for this extension point. Explain where composition is useful and name one test that would detect a plugin violating the intended boundary.

Worked answer

Keep orchestration and mandatory tax application in trusted checkout policy. Give a pricing plugin only the information and operation needed to propose a pre-tax shipping price, with explicit currency and valid-range rules. Compose the chosen policy into the orchestrator rather than allowing subclasses to replace the entire workflow. Validate plugin results and apply tax afterward through the mandatory path. Test a plugin returning an invalid amount or attempting to claim a tax-inclusive result, and assert that checkout rejects it or still applies the documented tax rule.

Open extension points should protect stable policy; greater extensibility is not a reason to expose unrelated control.

Check your work

  • Separates optional pricing from mandatory tax policy
  • Defines a narrow validated contract
  • Tests the protected boundary

3. Model ownership and independent lifetimes

A museum Catalog references Artworks. Removing a Catalog must never delete an Artwork, because the same Artwork can appear in several catalogs. Each Catalog also owns layout Blocks that have no meaning outside that catalog. Describe UML relationships and multiplicities for both cases. Then explain one implementation risk if the team maps every association to cascading deletion in its database.

Worked answer

Use an ordinary many-to-many association between Catalog and Artwork, for example zero or more at both ends if empty catalogs and uncataloged artworks are permitted. Use composition from Catalog to Block when each block belongs to exactly one catalog and shares its modeled lifetime; a catalog may own zero or more blocks. A generic cascade rule could delete an artwork still referenced elsewhere, violating the domain rule. Implement artwork-link deletion separately from artwork deletion and verify persistence behavior rather than assuming UML notation enforces it.

Ownership and lifecycle are domain decisions. Similar-looking references do not imply identical deletion semantics.

Check your work

  • Models shared artworks without composite ownership
  • States block ownership and multiplicities
  • Connects deletion behavior to domain invariants
