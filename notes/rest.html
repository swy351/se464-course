REST APIs & serialization

Week 5 · October 7

Design resource operations with clear retry semantics, and turn data structures into valid network representations.

HTTP as an API contract

A network API plays the role of an interface between programs that do not share a process. The caller needs to know what operation is available, how to supply its inputs, and how to interpret success or failure. It should not need to know the implementation language or internal database schema. Consider a weather service: a client requests a forecast for a named location, and the service returns structured data with a documented meaning. The diagram distinguishes the resource identifier, request parameters, and response representation. These pieces form a contract that lets a browser application, a mobile application, or another backend use the same service independently of its implementation.

HTTP provides an existing envelope for that contract. A request selects a target and method, supplies fields such as authorization or accepted media types, and may carry a body. The service responds with an appropriate status and a representation whose content type tells the client how to decode it. For a forecast endpoint, a successful JSON response and an unknown-location error are different documented outcomes. The diagram branches on the service's result rather than assuming every response contains usable forecast data. A client that ignores status and attempts to parse every body as a forecast can turn a clear service error into a confusing application failure.

Design the interface around stable resource concepts and meaningful operations. Query parameters can select a location or filter a collection, while request content can describe a new or replacement representation. Put credentials in an appropriate authorization mechanism rather than exposing secrets in a URL that may be logged. Specify units, timestamps, missing values, validation failures, and authorization behavior in addition to field names. HTTP does not supply these domain meanings automatically. Its value is a common transport-level vocabulary and a large ecosystem of clients, servers, proxies, and diagnostics. The architecture boundary is useful only when callers can rely on both the message structure and the meaning of the result.

Predict: Is a JSON body alone enough to specify a reliable API contract?

No. Methods, resource identity, status/error behavior, authentication and data meaning also matter.

Retries and resource identity

A client sends a write and waits, but the connection fails before it receives a response. The server may have completed the write; the client simply cannot tell. Retrying can therefore repeat an operation that already happened. Compare two ways to create a document. A PUT to a client-chosen identifier replaces the representation at that identifier, so repeating the same intended operation has the same effect on that resource. A POST to a collection may ask the server to allocate a new identifier each time, creating two documents after a retry. The diagram follows the lost response, then contrasts the stable target with two newly allocated targets.

The important distinction is the intended effect, not whether repeated responses have identical bytes or status codes. Deleting an existing resource and deleting it again can leave the same final absence even if the second response reports that nothing was found. A safe read does not request a state change; an idempotent write can request a change whose repetition has the same intended effect. For an operation such as charging an account, the API can define an idempotency key and atomically associate that key with one accepted result. The illustration shows a repeated key returning the recorded result rather than initiating a second charge, provided the documented retention and parameter rules are satisfied.

Do not infer retry safety from a method name alone if the implementation violates its contract, and do not assume every method other than POST is automatically idempotent. PATCH, for example, depends on the patch operation. An idempotency mechanism must deal with concurrent duplicate requests, conflicting parameters, failures during execution, and expiration of remembered results. A client also needs a bounded retry policy and a deadline so retries do not amplify an outage. Write down the uncertainty window explicitly: the response is missing, but the effect may already exist. Then show how resource identity, conditional updates, or a deduplication record lets the client recover without creating an unintended second effect.

Predict: After a timeout, is retrying DELETE /posts/latest as safe as DELETE /posts/42?

No. Latest may now identify a different post, whereas 42 remains the same target.

Serialization and references

Objects in memory cannot simply be copied onto a network and expected to retain their meaning in another process. The receiver may use another language, object layout, or machine architecture. Serialization converts values into a defined representation, while deserialization reconstructs useful values from it. JSON works well for combinations of objects, arrays, strings, numbers, booleans, and null, but domain types still need conventions. The diagram shows two different client languages meeting at one wire representation. A timestamp needs a timezone convention, a large numeric identifier may need a string representation, and an absent field must have a meaning distinct from an explicitly supplied null when the API requires that distinction.

References make serialization more interesting than printing nested values. Suppose two people share one hometown object. Embedding the complete hometown under both people repeats data and can obscure that they refer to the same entity. A cycle is worse: if Alice references Ben and Ben references Alice, recursively expanding both objects never reaches a natural end. Assign stable identifiers and serialize a table of objects plus those identifiers as references. The diagram shows two people pointing to one shared city record. The receiver can create the records first, then resolve links, preserving sharing without duplicating the entire city or endlessly following a cyclic chain.

References exchange a simpler-looking nested document for additional coordination. Producers must collect referenced objects, choose identifiers, and ensure they are unique within the stated scope. Consumers must handle missing targets, forward references, and possibly more than one pass through the data. A resource identifier is not a raw memory address, and receiving one does not authorize unrestricted access to that resource. Decide whether the response contains a complete graph, a partial graph with external links, or a convenient snapshot with deliberate duplication. Also define schema evolution: new optional fields, removed fields, and incompatible type changes affect clients differently. Test realistic values and graph shapes rather than validating only a flat demonstration object.

Predict: What happens if Jess includes Tom, Tom includes Kate, and Kate includes a fully nested Jess?

Naive recursive serialization never terminates; IDs turn the cycle into finite references.

Choosing a protocol

Choosing HTTP-based APIs means adopting an ecosystem as well as a message format. Existing libraries handle connections, encryption, compression, and response parsing; established proxies and observability tools can inspect familiar exchanges. For a public catalogue API used by many independent clients, that shared vocabulary can matter more than shaving a few bytes from each response. The diagram connects different clients through one documented interface, with common operational tooling beside it. These benefits still require configuration and correct semantics. A cache does not become safe merely because the protocol supports caching, and encryption does not replace authentication or authorization. Reuse the infrastructure while explicitly defining the application's contract.

Now imagine a high-volume internal call with a stable schema and many generated clients. A schema-driven RPC approach can define operations and types once, generate language bindings, and use a compact representation on the wire. The illustration shows one schema producing two compatible client libraries and a server interface. This can reduce repetitive integration work and catch some mismatches earlier, but it introduces schema-evolution rules, generated artifacts, and tooling that every participant must manage. Serialization format and transport are separate decisions: Protocol Buffers does not itself prohibit HTTP, and an RPC system may use HTTP as its transport. Compare complete stacks instead of treating JSON, HTTP, and RPC as interchangeable categories.

The right choice follows the clients and workload. Consider whether third parties need an easily inspected interface, whether streaming or low-latency calls dominate, whether operations naturally map to resources, and whether the team can maintain compatible schemas over time. Measure payload size, encoding cost, connection behavior, and debugging effort under realistic traffic rather than assuming that binary always wins or that text is always adequate. A smaller message has little effect when database work dominates the response. Conversely, a heavily repeated internal exchange may justify tighter encoding and generated bindings. Document why the chosen protocol fits the boundary and what evidence would justify revisiting that choice later.

Predict: Does choosing Protocol Buffers imply that the service cannot use HTTP?

No. gRPC commonly uses Protocol Buffers over HTTP/2.

Self-check

Why can DELETE /posts/latest violate DELETE idempotence, and what endpoint fixes it?

After the first deletion, latest points to a different post. Retry may delete again. Use a stable identifier such as DELETE /posts/42.

A DELETE retry returns 404 after the first call returned 204. Does that prove non-idempotence?

No. The intended effect remains that the same resource is absent; response status need not stay identical.

How do you serialize Jess -> Tom -> Kate -> Jess without infinite nesting?

Emit each person once with a stable person_id and represent friendships with best_friend_id references; resolve IDs when reading.

Design exercise

Design creation and deletion operations for submissions so a client can safely retry after a timeout. Include resource identifiers, statuses, authentication, and valid JSON.

Use stable identifiers or an idempotency key with a defined deduplication lifetime. PUT to a client-chosen stable resource can support retry-safe creation if the semantics fit; POST can also support application-level idempotency. DELETE a stable submission ID, not a moving “latest” target. Define authorization and conflicts. Validate JSON without trailing commas and distinguish protocol semantics from payload format.

1. Two editors, one resource

Two librarians retrieve the same catalogue record with version tag v12. Mara saves a corrected title, producing v13. Noah then submits an edit based on v12 that changes the publication year but also contains the old title. The API currently replaces the entire record with PUT. Which contract change best prevents Noah from silently undoing Mara’s correction while preserving normal retries?

  1. Require If-Match with the observed version and reject a stale condition.
  2. Replace PUT with GET so repeated edits are safe.
  3. Keep PUT but tell clients never to retry.
  4. Use POST and accept whichever complete record arrives last.

Worked answer

Best answer: A.

Require a conditional update using the previously observed entity tag, for example If-Match with v12. After Mara’s update changes the tag, Noah’s stale request fails its precondition instead of replacing v13. The client retrieves the current representation and asks the user to merge or reconsider the change. Repeating a PUT can be idempotent in its intended effect while still overwriting another user’s work; idempotence alone does not provide concurrency control. The version check and write must be enforced atomically at the authoritative store.

The condition ties a write to the version the editor actually reviewed. Stable URLs and HTTP method choice do not by themselves detect intervening changes.

Check your work

  • Select conditional version checking.
  • Distinguish idempotence from concurrency control.
  • Require atomic check-and-write.

2. A representation that changes by locale

A museum API returns a public exhibit description from GET /exhibits/18. It selects English or French text from Accept-Language. A shared cache stores responses using only the URL, and visitors occasionally receive the wrong language. The team proposes changing GET to POST to bypass the cache. Design a better representation and caching contract, including how a client can discover what it received.

Worked answer

Keep retrieval semantics and make language selection part of the representation contract. One approach returns Vary: Accept-Language and Content-Language, with a documented language negotiation and fallback policy; the cache must honor the variant key. Another uses explicit language-specific URLs and ordinary public caching. Specify freshness and validation for translations independently if they change at different times. Switching to POST does not repair an unclear representation contract and needlessly sacrifices common GET infrastructure. Test alternating English and French requests through the actual configured cache, including unsupported-language fallback.

A cache may reuse a response only for compatible request variants. The defect lies in omitting a representation-selection input from the cache decision.

Check your work

  • Preserve retrieval semantics and define language selection.
  • Account for cache variants or explicit language URLs.
  • Include fallback and response-language observability.

3. Identifiers that survive serialization

A Java backend sends sensor IDs as JSON numbers. One ID is 9007199254740993, and a browser client parses numbers into ordinary JavaScript Number values, whose exact integer range ends at 9007199254740991. Two adjacent IDs are displayed as the same value and an update targets the wrong sensor. Redesign the API representation and migration contract without changing the underlying database identifiers.

Worked answer

Represent sensor identifiers as decimal strings and require clients to preserve them as opaque values. The database may continue using its existing integer type. Define the string format, validate it at the server boundary and avoid client-side numeric coercion when building URLs or map keys. Migrate with a versioned contract or an additive string field and a defined deprecation period so old clients do not silently misinterpret changed types. Test values beyond the exact-number boundary and round trips through every supported client. Changing only display formatting cannot recover precision already lost during parsing.

JSON text can carry the digits, but a receiving language’s number model may not preserve them. A cross-language contract must specify a representation with the required precision.

Check your work

  • Use exact string identifiers end to end.
  • Address compatibility during migration.
  • Test precision boundaries and URL/key use.
