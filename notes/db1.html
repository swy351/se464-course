Why state moves into the database

Source slides 1–12

Moving session and application state out of a web process makes that process easier to duplicate. The shared database now carries durable data and coordinates changes made by those copies. This is useful separation of concerns, but it also concentrates work. Trace a page request through the application to distinguish computation, database lookup and storage access before deciding where additional servers help.

Storage systems trade access latency against capacity. Caches and RAM keep frequently needed data close to computation; persistent storage retains the larger dataset. RAID can combine disks for capacity, throughput or redundancy, depending on configuration. More disks do not eliminate the CPU, memory bandwidth and I/O limits of the database server controlling them.

Worked walkthrough

A repair-booking service runs on six application servers. Each booking needs three database operations. If the database sustains 1,800 such operations per second, the idealized ceiling is 600 bookings per second, regardless of how many otherwise idle application servers are added. This estimate assumes equal operation costs and no competing workload; measurements must check those assumptions.

Now suppose a frequently read parts catalogue fits in the database buffer cache. Repeated reads may avoid storage access, but writes, locks and network transfers still consume resources. Adding disks could improve storage throughput without fixing a CPU-bound query or a contended record. Separate durable storage, coordination and query execution when explaining why the database remains busy after the web tier scales.

Relational models and query execution

Source slides 13–19

A relational schema describes tables, columns and relationships. A staff row can refer to one department, and a department can refer to one building. Keeping shared facts in their own tables avoids updating the department name separately for every employee. A JOIN reconstructs the information needed by a particular application view without requiring that view to dictate the storage layout.

The database contributes more than persistence. It can enforce keys and constraints, coordinate concurrent changes, index data and run filtering or aggregation near storage. Ordinary files provide naming, permissions and durable bytes, but application code must add many higher-level guarantees. Choose the abstraction by the behavior required, rather than assuming a file and a table are interchangeable.

Worked walkthrough

A bicycle library stores Bicycle, Branch and Loan tables. Each bicycle refers to its current branch, and each loan refers to one bicycle and one borrower. Renaming a branch changes one branch record rather than every bicycle description. A loan-history page joins those records to display useful information without storing a duplicate branch name in every loan.

For a query asking for one borrower’s active loans, the database can first identify a small set of matching loans and then look up their bicycles. Reading every bicycle before filtering could do much more work. The execution plan reveals the chosen access path; the schema alone does not guarantee it. Also decide whether the page should display the branch’s current name or preserve its historical name when the loan occurred.

Indexes and their costs

Source slides 20–32

An index stores an additional access path to rows. Without a suitable access path, a query may scan many rows to find a small result. Tree indexes organize keys for equality and ordered range access; hash indexes organize equality lookup. Real database indexes usually use page-oriented structures suited to storage, rather than the simple binary tree used to introduce the idea.

Every index consumes space and must be maintained when indexed data changes. A composite index also has an order: an index beginning with firstName generally favors predicates involving firstName. A lastName-only query may behave differently depending on optimizer and data. Examine the execution plan and measure the representative workload before adding an index, then check its effect on writes as well.

Worked walkthrough

A parcel service frequently asks for a particular depot’s shipments created during the last hour. An ordered index on (depot_id, created_at) groups one depot’s entries and then narrows the time interval. A query for all depots during that hour may need a different plan because its predicate omits the leading column. The optimizer and data distribution determine the actual access path.

Suppose that targeted query examines 240 index entries instead of scanning 800,000 shipment rows. That is a promising reduction in examined data, not a guaranteed latency ratio. Every inserted shipment must also update the index. Compare execution plans and measured response times before and after the change, including ingestion throughput, index size and unusually busy depots. An index is a maintained copy of ordering information, not free acceleration.

Read scaling and failover

Source slides 33–42

A primary database can stream changes to read replicas. Each replica maintains a copy of the dataset and can answer eligible reads, so many read requests no longer compete for the primary. Asynchronous replication creates lag: a successful write does not mean every replica already exposes it. A profile page that immediately reloads from a lagging replica may appear to lose the edit.

Read replicas do not automatically spread write execution or increase the capacity of an individual full copy. Cascading replication can reduce direct fan-out from the primary but adds propagation stages. A standby can improve recovery after failure, but safe promotion requires more than detecting a timeout: the system must decide authority and prevent competing primaries from accepting incompatible changes.

Worked walkthrough

A tutoring service updates a student’s appointment time on the primary database. A replica that has not yet applied the change still returns the old time. The write can have succeeded even though an immediately refreshed page looks unchanged. Historical appointment reports may tolerate this delay; the confirmation shown to the student should follow a path that satisfies the promised freshness.

Imagine one primary handling 400 writes and 3,000 reads per second. Moving 2,400 eligible reads to three replicas leaves roughly 600 reads on the primary, but each replica must still apply the write stream. This is a workload sketch, not a capacity guarantee. If the primary fails, promoting a standby requires establishing a single writer and understanding which acknowledged writes it contains. A timeout alone does not establish that the previous writer has stopped.

Sharding and fan-out

Source slides 43–49

Sharding assigns disjoint subsets of rows to different database partitions. A useful key places the data for a common operation together while distributing storage and traffic. With user_id modulo two, Steve’s profile and posts can live on one shard. That makes a single-user query local, but it does not make every query local: friends may belong to every partition.

A friends feed may request candidate posts from multiple shards and merge them into one ordered result. This costs network work and coordination. Under a balanced equal-cost model, N nodes each serving C operations per second support about NC/k requests when each request touches k nodes. A request touching every node eliminates that ideal throughput gain, although parallelism may still reduce one query’s latency.

Worked walkthrough

A maintenance platform shards equipment records by customer. Fetching one customer’s inspection history stays on a single shard, while a report across all customers contacts several shards and merges their results. Placing customers evenly by count can still overload a shard containing a huge customer; traffic and record size matter as well as the routing rule.

In a simplified balanced model, eight shards each provide 500 equal-cost operations per second. Requests touching one shard have an upper bound near 4,000 requests per second. If each request touches four shards, the bound drops to about 1,000. If it touches all eight, it drops to 500. Parallel requests may finish sooner than serial requests, but each still consumes cluster work. Cross-shard updates additionally need an explicit atomicity or reconciliation strategy.

Self-check

A table has indexes on SSN and (firstName,lastName). Which is the natural index for an SSN equality lookup, and why is lastName-only lookup less predictable?

SSN index targets that equality directly. A B-tree composite index generally favors its leading firstName column; lastName-only efficiency depends on optimizer and data.

Why can read replicas make a recently saved profile appear to revert?

The write is on the primary while an asynchronous read replica may still hold the older version. Use a suitable primary/session-consistent read policy.

With 8 nodes at 200 requests/s each and 2 node operations per request, what is ideal throughput? What if every request reaches every node?

Balanced equal-cost model: 8×200/2 = 800 requests/s. Fan-out to all 8 gives 200 requests/s; network, skew and coordination can lower both.

Design exercise

A social feed shards data by user ID. Compare fetching one user’s posts with fetching the latest ten posts from all their friends. Explain the role of indexes and read replicas.

A user’s own posts can be located in one shard and filtered with a suitable index. Friends may span many shards, requiring parallel queries and a merge of candidate results. The shard key trades locality against balance. Read replicas share read load but may lag and do not inherently distribute writes or increase per-replica data capacity.

1. The expensive status index

A repair shop records equipment readings in a relational table. A proposed status index reduces one hourly diagnostic query from eight seconds to one second, but tests show every insert takes 0.4 milliseconds longer. The system receives 2,000 inserts per second, and its write path is already near saturation. The diagnostic query has a thirty-second deadline. Which next step best fits these requirements?

  1. Keep the index off the write path and evaluate an analytical copy or measured alternative
  2. Add the index because every faster query improves overall capacity
  3. Add read replicas and assume they eliminate primary index maintenance
  4. Replace SQL with NoSQL because NoSQL indexes have no update cost

Worked answer

Best answer: A.

Keep the index out of the saturated production write path for now and evaluate a separate analytical copy or another measured query improvement. The existing eight-second query already meets its thirty-second deadline, while 2,000 inserts each adding 0.4 milliseconds require 800 milliseconds of additional aggregate insert work per second. That is not automatically eighty percentage points of CPU utilization, because the delay may include other resources, but it is material write-path overhead. Reassess if diagnostics become more frequent or their deadline changes.

An index is a workload trade-off, not a universally free optimization. A measured improvement to a rare query can be outweighed by maintenance on frequent writes.

Check your work

  • Recognizes that the current query meets its deadline
  • Accounts for continuous index maintenance
  • Avoids interpreting elapsed insert delay as directly measured CPU demand

2. A hot tenant hides inside balanced storage

A field-service database uses four equal-capacity shards, each able to process 900 requests per second. Storage occupies the same number of bytes on every shard. At peak, tenant A generates 1,200 requests per second and all other tenants together generate 600, spread evenly across the remaining three shards. Records are placed by tenant ID. Diagnose the overload and propose a migration that preserves efficient tenant queries without assuming every tenant can remain on one shard.

Worked answer

The tenant-A shard receives 1,200 requests per second against a 900-request limit, while each other shard receives only 200. Aggregate nominal capacity is 3,600, but spare capacity elsewhere cannot serve data owned only by A’s shard. Split A using a second key, such as equipment group, while retaining tenant-local placement for smaller tenants. Route group-specific requests directly and fan out only queries that need all of A. Migrate with explicit ownership, verification and a cutover plan; copying bytes alone does not safely move concurrent writes.

Even data size does not imply even request load. A composite placement rule can trade some tenant-wide query locality for better load distribution.

Check your work

  • Calculates 1200 versus 900 and 200 on other shards
  • Proposes targeted partitioning of the hot tenant
  • Addresses routing and safe ownership during migration

3. One report, two replication positions

A warehouse transfer commits two changes in one primary transaction: remove twelve units from shelf A and add twelve to shelf B. A reporting service reads A from replica East and B from replica West. Each replica applies complete transactions, but East has applied this transfer and West has not. The report adds the two shelf quantities and raises a stock-loss alarm. Explain the anomaly and design a read strategy for this report.

Worked answer

The report combines two different transaction positions: the decrease is visible but its matching increase is not, so it invents a twelve-unit loss. No replica necessarily exposed a partial transaction. Run both reads in one consistent snapshot on a single replica, or execute the aggregate as one snapshot-consistent query. If the report must include this newly committed transfer, first require a replication progress token or use an appropriate primary read. A same-replica route alone is insufficient when separate statements can observe changing snapshots without a transaction.

Replica self-consistency does not imply consistency across a multi-request report. Snapshot selection and minimum freshness are separate requirements.

Check your work

  • Identifies cross-replica version mixing
  • Specifies one consistent snapshot
  • Separates snapshot consistency from inclusion of the latest transfer
