Request processing and HTTP

Follow a catalogue request through an arrival queue, application handling and a response. When all workers are busy, another request waits rather than receiving an immediate worker. If arrivals remain faster than completions, the queue grows. A bigger queue may absorb a short burst, but it does not create processing capacity. Bounded queues make overload explicit and let the service reject or defer work instead of allowing unlimited memory growth and increasingly late answers. The client sends an HTTP method, target and fields, with optional content; the service returns a status, fields and optional content. A framework translates that contract into application calls and manages network activity. It might use threads, processes or asynchronous handlers. Those choices affect how waits are managed, but they do not change the meaning of GET or a response status. In a design review, draw both the public request contract and the internal queues: one explains interoperability, while the other explains what users experience during a burst.

A Wikipedia request, end to end

Apply the chapter’s rendering pipeline to a different service: a museum collection page. A browser requests an exhibit; the application reads its description from durable storage, formats the description, adds navigation and returns HTML. The database owns saved content, while the application constructs a representation for a reader. Labelling these responsibilities makes the architecture diagram useful: each arrow should identify a request or data transfer, rather than simply connecting boxes. Now compare two visitors reading the same exhibit. They can share the description and public image, but one visitor’s private saved-list indicator must not become the other visitor’s answer. This observation identifies possible reuse boundaries before choosing a cache. Trace a second request after an exhibit description changes, and explain which component must observe that update. The point of the historical diagram is this method of reasoning about repeated computation, durable state and personalized output; its component names are not a prescription for a modern deployment.
