HTTP as an API contract

Source slides 1–6

An API specifies how another program requests work and interprets results. HTTP-based APIs use methods, targets, fields, status codes and optional bodies. The weather example combines a location parameter with a JSON response. A useful contract documents units, missing values and errors as well as the successful payload.

Choose methods according to their semantics: GET retrieves a representation, PUT creates or replaces state at a known target, POST asks a resource to process supplied content, and DELETE removes the target association. Status codes help clients distinguish success, missing resources, forbidden access and server failure. HTTPS protects transport; avoid putting credential examples in URLs that may be logged or copied.

Worked walkthrough

A maintenance service exposes GET /tickets/731. A successful response includes a ticket identifier, a status and an estimated duration. The JSON shape alone is insufficient: clients need to know whether duration means minutes or seconds, whether a missing estimate is null or omitted, and what happens when a ticket is unavailable. An API contract therefore includes meaning and failure behavior as well as a syntactically valid example.

Choose the method before inventing an endpoint name. A read should not close the ticket as a side effect. A replacement request to a known ticket target differs from submitting a new work request for the service to process. Document authorization failures and absent resources so clients can react appropriately. Use HTTPS for transport protection, and avoid placing access tokens in example query strings that might appear in logs. These decisions help separate an interoperable service boundary from a collection of loosely specified network calls.

Retries and resource identity

Source slides 7–11

Retries are normal when a client cannot tell whether an operation completed. Idempotence means repeating an identical request has the same intended server effect as sending it once. It does not require the same response status. Deleting an already removed resource may report that it is missing without deleting anything else.

The delete-latest example fails this requirement because the target changes after the first deletion. A stable post identifier lets retries refer to the same item. Similarly, a PUT to a chosen document ID replaces that target, while POST creation may allocate a fresh ID each time unless the application provides deduplication. Resource-oriented naming helps communicate intent, but nouns alone do not define the REST architectural style.

Worked walkthrough

A client submits a repair request and loses its connection before receiving the response. It cannot tell whether the server committed the work. Retrying is therefore an uncertainty problem, not proof that the first attempt failed. A stable target helps: repeating a request to set ticket 731 to the same intended state can be designed to have the same intended effect as one attempt. That does not require identical response bytes or status codes.

Contrast this with an operation that closes whichever ticket is currently oldest. After the first success, a retry could close a different ticket. The resource identity moves, so repetition changes the intended effect. Use an explicit ticket identifier for that operation. For creation through POST, define a deduplication mechanism if retries must not create another request. PUT and DELETE have idempotent method semantics; POST and PATCH are not generally guaranteed idempotent. The implementation must honor the chosen contract rather than relying on the method name to repair unsafe behavior.

Serialization and references

Source slides 12–19

Serialization turns structured values into bytes that can cross a network or be stored. JSON provides objects, arrays, strings, numbers, booleans and null. XML uses elements and attributes with well-formed syntax. Correct examples matter: JSON forbids trailing commas, and an empty XML element must close explicitly or use self-closing syntax.

An in-memory graph is not always a simple nested tree. Repeating shared objects wastes space, and recursively nesting a cycle never ends. Emit each object once with an identifier, then encode relationships using those identifiers. Readers resolve references under an agreed schema. The byte dump illustrates ASCII-compatible UTF-8 text; characters beyond ASCII may require multiple bytes, so character count and byte count can differ.

Worked walkthrough

Two maintenance tickets refer to the same building, and that building record refers to its active tickets. Naively nesting the entire building inside each ticket duplicates data. Following the building’s ticket references recursively can also create an endless cycle. The in-memory structure is a graph, while ordinary nested JSON values form a tree. Serialization must decide how to represent identity and relationships instead of blindly walking every pointer.

One representation emits building B9 once, emits tickets T1 and T2 once, and links each ticket with buildingId B9. The client resolves those identifiers using the agreed response structure or additional API requests. This reduces duplication but requires a rule for missing references and for when related objects become available. Also distinguish text length from byte length: a title containing accented characters can occupy more UTF-8 bytes than its character count. Schema choices, reference rules and encoding all belong to the data exchange contract.

Choosing a protocol

Source slides 20–22

HTTP offers widely available clients, servers, status semantics and caching infrastructure. HTTPS adds encrypted transport. Reuse can lower implementation effort, but API authors must understand caching and retry semantics instead of treating HTTP as an arbitrary message tube. Framework capabilities differ, so database pooling or deployment security should not be assumed automatically.

Separate architectural style, serialization and transport. REST describes architectural constraints; JSON and Protocol Buffers encode data; gRPC is an RPC framework that commonly uses Protocol Buffers with HTTP/2. Binary encoding therefore does not imply avoiding HTTP. Choose based on interoperability, tooling, streaming, payload size and measured performance requirements. Smaller messages alone do not settle the architecture decision.

Worked walkthrough

The maintenance team supports a browser dashboard and an internal batch client. It first lists requirements: available client libraries, message sizes, streaming needs, debugging tools and expected compatibility. A familiar HTTP and JSON interface may make integration easy, while a schema-driven binary representation may be useful for another workload. The decision should compare complete systems under realistic requests, not assume that a smaller encoded message automatically makes the service faster.

Keep the design layers visible. REST describes architectural constraints, HTTP defines protocol semantics, and JSON or Protocol Buffers encode data. An RPC framework supplies another set of conventions and tools; binary serialization can still travel over HTTP, as in common gRPC deployments. Reusing HTTP infrastructure also means respecting its caching and retry rules. Before changing formats, measure where time is spent: if most latency is a database wait, saving a few bytes may have little effect. Select an interface that meets the operational and compatibility needs you actually have.

Self-check

Why can DELETE /posts/latest violate DELETE idempotence, and what endpoint fixes it?

After the first deletion, latest points to a different post. Retry may delete again. Use a stable identifier such as DELETE /posts/42.

A DELETE retry returns 404 after the first call returned 204. Does that prove non-idempotence?

No. The intended effect remains that the same resource is absent; response status need not stay identical.

How do you serialize Jess -> Tom -> Kate -> Jess without infinite nesting?

Emit each person once with a stable person_id and represent friendships with best_friend_id references; resolve IDs when reading.

Design exercise

Design creation and deletion operations for submissions so a client can safely retry after a timeout. Include resource identifiers, statuses, authentication, and valid JSON.

Use stable identifiers or an idempotency key with a defined deduplication lifetime. PUT to a client-chosen stable resource can support retry-safe creation if the semantics fit; POST can also support application-level idempotency. DELETE a stable submission ID, not a moving “latest” target. Define authorization and conflicts. Validate JSON without trailing commas and distinguish protocol semantics from payload format.

1. Two editors, one resource

Two librarians retrieve the same catalogue record with version tag v12. Mara saves a corrected title, producing v13. Noah then submits an edit based on v12 that changes the publication year but also contains the old title. The API currently replaces the entire record with PUT. Which contract change best prevents Noah from silently undoing Mara’s correction while preserving normal retries?

  1. Require If-Match with the observed version and reject a stale condition.
  2. Replace PUT with GET so repeated edits are safe.
  3. Keep PUT but tell clients never to retry.
  4. Use POST and accept whichever complete record arrives last.

Worked answer

Best answer: A.

Require a conditional update using the previously observed entity tag, for example If-Match with v12. After Mara’s update changes the tag, Noah’s stale request fails its precondition instead of replacing v13. The client retrieves the current representation and asks the user to merge or reconsider the change. Repeating a PUT can be idempotent in its intended effect while still overwriting another user’s work; idempotence alone does not provide concurrency control. The version check and write must be enforced atomically at the authoritative store.

The condition ties a write to the version the editor actually reviewed. Stable URLs and HTTP method choice do not by themselves detect intervening changes.

Check your work

  • Select conditional version checking.
  • Distinguish idempotence from concurrency control.
  • Require atomic check-and-write.

2. A representation that changes by locale

A museum API returns a public exhibit description from GET /exhibits/18. It selects English or French text from Accept-Language. A shared cache stores responses using only the URL, and visitors occasionally receive the wrong language. The team proposes changing GET to POST to bypass the cache. Design a better representation and caching contract, including how a client can discover what it received.

Worked answer

Keep retrieval semantics and make language selection part of the representation contract. One approach returns Vary: Accept-Language and Content-Language, with a documented language negotiation and fallback policy; the cache must honor the variant key. Another uses explicit language-specific URLs and ordinary public caching. Specify freshness and validation for translations independently if they change at different times. Switching to POST does not repair an unclear representation contract and needlessly sacrifices common GET infrastructure. Test alternating English and French requests through the actual configured cache, including unsupported-language fallback.

A cache may reuse a response only for compatible request variants. The defect lies in omitting a representation-selection input from the cache decision.

Check your work

  • Preserve retrieval semantics and define language selection.
  • Account for cache variants or explicit language URLs.
  • Include fallback and response-language observability.

3. Identifiers that survive serialization

A Java backend sends sensor IDs as JSON numbers. One ID is 9007199254740993, and a browser client parses numbers into ordinary JavaScript Number values, whose exact integer range ends at 9007199254740991. Two adjacent IDs are displayed as the same value and an update targets the wrong sensor. Redesign the API representation and migration contract without changing the underlying database identifiers.

Worked answer

Represent sensor identifiers as decimal strings and require clients to preserve them as opaque values. The database may continue using its existing integer type. Define the string format, validate it at the server boundary and avoid client-side numeric coercion when building URLs or map keys. Migrate with a versioned contract or an additive string field and a defined deprecation period so old clients do not silently misinterpret changed types. Test values beyond the exact-number boundary and round trips through every supported client. Changing only display formatting cannot recover precision already lost during parsing.

JSON text can carry the digits, but a receiving language’s number model may not preserve them. A cross-language contract must specify a representation with the required precision.

Check your work

  • Use exact string identifiers end to end.
  • Address compatibility during migration.
  • Test precision boundaries and URL/key use.
