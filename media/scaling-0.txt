From programs to services

A museum catalogue runs a fast image lookup in isolation. During a school booking event, however, 600 visitors arrive together and compete for the same database connections. The lookup algorithm has not changed, but its operating conditions have. A service must keep accepting work over time, share finite resources among requests, and respond acceptably while arrivals overlap. A successful single-user demonstration therefore does not establish service capacity. Begin the capacity discussion with a workload: which operations arrive, how often, and with what acceptable latency and error rate? Suppose browsing costs much less than exporting a collection. Two tests at 200 requests per second can produce very different results if their operation mixes differ. Record both completed throughput and response-time distributions, including slow requests. Then increase arrivals until waiting or errors rise. This experiment distinguishes an audience-size claim from evidence that the architecture can support a particular demand.

Scaling up and scaling out

The museum first considers a larger machine and then a second application replica. If image processing consumes all available CPU, more cores may help when the work can run in parallel. If every request waits on the same database lock, another application machine can simply create more waiting. Vertical and horizontal scaling are changes to resource allocation; whether either helps depends on the resource or coordination point currently limiting useful work. Consider a worker that spends 10 milliseconds computing and 40 milliseconds waiting for a remote response. On one core, another request can use CPU during that wait, so concurrency can improve utilization without making the first computation faster. This is not a promise of a fivefold speedup: network limits, scheduling and shared dependencies still matter. Before choosing larger machines or additional replicas, measure CPU use, waiting time and contention. After changing capacity, repeat the same workload test to see whether the bottleneck moved elsewhere.
