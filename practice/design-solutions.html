1. A subtype that rejects a valid client

A scheduling library exposes Notifier.send(message), whose documented contract accepts any nonempty message up to 1,000 characters. A new SMSNotifier implementation rejects messages longer than 160 characters, although existing clients may send 500-character messages. Which redesign best preserves the stated client contract while making the SMS limitation explicit?

  1. Keep the implementation because clients should know SMS limitations.
  2. Silently truncate all long messages.
  3. Rename SMSNotifier to FastNotifier without changing behavior.
  4. Use a narrower SMS capability or an adapter that fulfills the original delivery contract.

Worked answer

Best answer: D.

The appropriate choice is to separate the SMS capability or introduce an adapter that genuinely fulfills the original contract. Merely throwing for messages above 160 characters strengthens the precondition and breaks valid existing clients. An adapter might split messages only if that behavior satisfies the documented delivery semantics; it must not silently truncate content. A narrower SMS interface can require clients to choose compatible behavior explicitly. Renaming the implementation or adding an exception comment does not repair substitutability under the original contract.

The problem is a mismatch between promised accepted inputs and the replacement implementation, not whether inheritance syntax compiles.

Check your work

  • Identifies strengthened precondition
  • Chooses a contract-preserving or explicitly narrower interface

2. Design an extension point with an exception

A shipping service chooses a price policy by destination region. Next quarter it must support promotional policies installed by another team. Compliance also requires a mandatory tax calculation that plugins must not bypass. Propose the responsibilities and narrow interfaces for this extension point. Explain where composition is useful and name one test that would detect a plugin violating the intended boundary.

Worked answer

Keep orchestration and mandatory tax application in trusted checkout policy. Give a pricing plugin only the information and operation needed to propose a pre-tax shipping price, with explicit currency and valid-range rules. Compose the chosen policy into the orchestrator rather than allowing subclasses to replace the entire workflow. Validate plugin results and apply tax afterward through the mandatory path. Test a plugin returning an invalid amount or attempting to claim a tax-inclusive result, and assert that checkout rejects it or still applies the documented tax rule.

Open extension points should protect stable policy; greater extensibility is not a reason to expose unrelated control.

Check your work

  • Separates optional pricing from mandatory tax policy
  • Defines a narrow validated contract
  • Tests the protected boundary

3. Model ownership and independent lifetimes

A museum Catalog references Artworks. Removing a Catalog must never delete an Artwork, because the same Artwork can appear in several catalogs. Each Catalog also owns layout Blocks that have no meaning outside that catalog. Describe UML relationships and multiplicities for both cases. Then explain one implementation risk if the team maps every association to cascading deletion in its database.

Worked answer

Use an ordinary many-to-many association between Catalog and Artwork, for example zero or more at both ends if empty catalogs and uncataloged artworks are permitted. Use composition from Catalog to Block when each block belongs to exactly one catalog and shares its modeled lifetime; a catalog may own zero or more blocks. A generic cascade rule could delete an artwork still referenced elsewhere, violating the domain rule. Implement artwork-link deletion separately from artwork deletion and verify persistence behavior rather than assuming UML notation enforces it.

Ownership and lifecycle are domain decisions. Similar-looking references do not imply identical deletion semantics.

Check your work

  • Models shared artworks without composite ownership
  • States block ownership and multiplicities
  • Connects deletion behavior to domain invariants
