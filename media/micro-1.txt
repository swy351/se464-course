Teams, mocks and multiple clients

The scheduling team supplies a mock API while the real service is under construction. The dashboard team can now build a booking screen, but an always-successful mock teaches the wrong assumptions. Include unavailable slots, invalid input and delayed responses in the contract. Then run the same expectations against the real implementation. A mock accelerates collaboration because it makes assumptions executable; it does not prove that the dependency behaves that way in production. The same scheduling API can serve a browser dashboard and a technician’s mobile app. The browser may receive server-rendered HTML or construct its interface from API responses; a hybrid is also possible. In either case, the backend must enforce authorization and validate requested changes. Hiding an unavailable action in a button does not prevent a different client from sending that request. Review one complete workflow across both clients and check that resource identities, validation failures and permission rules mean the same thing on the shared service boundary.
