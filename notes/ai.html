AI generation and engineering judgment

Source slides 20–23,62–63

AI-generated software can run before a team has developed a reliable model of its behavior. The slides distinguish technical debt in the implementation, cognitive debt in understanding and intent debt in missing rationale. The Startup Studio account illustrates a reported experience in which early progress later exposed change and debugging difficulties; treat it as contextual evidence, not a universal result about AI.

Engineering judgment remains necessary to define what the system should promise, determine whether it fulfills that promise and plan how it will change. Architecture makes important assumptions and dependencies visible to both human collaborators and generated implementations. A useful review asks the team to explain a decision, identify a failure mode and show evidence. Attractive interfaces, passing happy-path tests and clean-looking code are helpful observations but do not settle those questions.

Predict: Can clean-looking generated code still leave the team with cognitive debt?

Yes. Readability alone does not ensure a shared understanding of behavior, dependencies or failure recovery.

Define the submission promise

Source slides 64–68

The case begins at 23:59: a student uploads an assignment, the page keeps spinning and no confirmation appears after refresh. The uncertainty is the problem to solve. A student wants evidence of receipt; an instructor needs access and timing; support staff need diagnostic evidence. The teaching model is inspired by LEARN, but its internal architecture is hypothetical.

Define the boundary and responsibilities before choosing deployment units. A submission handler, access check, file storage, authoritative record and notification responsibility must cooperate, yet these boxes do not automatically represent independent services. Ask where a student can check authoritative status and what that status promises. Concurrent users, interrupted uploads and authorization failures are part of the required reasoning, even when the basic happy path already passes its tests.

Predict: Does drawing a notification responsibility require deploying a notification microservice?

No. A responsibility can be implemented inside a process, module or separate service; the diagram must distinguish those choices.

Reliable receipt and retry semantics

Source slides 69–71

Confirmation timing defines a user-visible guarantee. Acknowledging a request on arrival is fast but can precede persistence. Waiting for an email couples receipt to an additional dependency. The selected teaching design confirms after the file and authoritative submission record are durable, while notification may complete later. The receipt therefore represents saved work rather than simply accepted work.

Lost responses make retries unavoidable. Preserve a stable request identity and recorded result so another app instance can return the same logical outcome. Concurrent duplicates and partial persistence failures require explicit handling; separate writes do not automatically form one atomic action. Pending notification work must also survive failures. This design supports an idempotent user outcome, not a blanket promise that every underlying operation executes exactly once.

Predict: The server saves the submission and crashes before sending a response. Should a retry create a new submission?

No. With the same valid request identity, it should recover and return the recorded result; durable shared identity and result storage make that possible.

Use four views to explain one outcome

Source slides 72–74

One diagram cannot answer every question about submission. A logical view names Student, Assignment and Submission relationships. A process view describes concurrent request handlers accessing shared state and an independent worker processing notifications. Their arrows have different meanings, so each picture needs a clear legend and should avoid implying a mapping that has not been decided.

The development view identifies modules and their dependencies; the physical view places software and data on deployment nodes. A retry that reaches another app instance is the connecting scenario. Trace how that instance finds the same request identity and result, how it respects authorization and how notification proceeds without changing the receipt guarantee. A coherent architecture allows all four perspectives to explain the same outcome while exposing different implementation questions.

Predict: If a retry reaches another instance, is an instance-local in-memory request table sufficient?

No. The new instance needs access to authoritative durable identity and result information, consistent with the promised recovery behavior.

Review and recover the architecture

Source slides 75–77

Architecture review compares an intended promise with implementation evidence. In the case, the intended rule permits confirmation only after file and record persistence. A new bulk-upload path that responds before saving violates that rule, even if ordinary uploads still work. A new route that follows the same rules but is undocumented instead illustrates drift. Classify the change by the actual decision affected.

Recovery depends on the evidence available to each observer. Students see receipts, errors and timing; support teams may see integration configuration and permitted logs; vendor engineers may inspect code, schemas and deployment. These perspectives support different strengths of claim. Mark observations, inferences and unknowns explicitly. A useful conclusion states what was demonstrated, what remains uncertain and which additional observation or test would resolve the uncertainty.

Predict: Can an external observer infer the full internal architecture from a successful upload?

No. Visible behavior supports limited observations; internal structure remains inferred or unknown without additional evidence.

Self-check

The file and authoritative record are saved but the response is lost. What should a retry using the same request identity do?

Return the recorded submission result without creating another logical submission; the identity/result must be durably shared across app instances.

Why choose save-first, notify-later rather than waiting for email before confirming?

It makes the receipt depend on durable submission state and avoids email delays blocking confirmation; it requires durable pending work, retries and status handling.

A new bulk-upload path confirms when requests enter memory, before persistence. What evidence and classification apply?

Compare runtime behavior/code with the intended save-before-confirm rule. It is erosion because the implementation violates that rule; record what is observed versus inferred.

Design exercise

A generated bulk-upload endpoint returns success as soon as a job enters memory. Redesign the receipt protocol for a student who retries after losing the response. Explain how notifications can fail without losing the submission.

Use a stable request identifier, persist the file and authoritative record before acknowledging completion, and recover the recorded result on retry. Make pending notification work durable and retry it separately. Coordinate file and record persistence, define partial-failure recovery, and test crashes between each step. This is a LEARN-inspired model, not a claim about the actual service.

Additional practice

Questions-only worksheet · Worked answer sheet

1. What evidence supports the diagram?

An AI assistant generates a deployment diagram for a campus equipment-loan service. It draws separate reservation, payment and notification services. The team has only browser access and observes that reservation and notification fail together during an outage. Which review response is best supported by this evidence, before anyone has inspected source code or deployment configuration?

  1. Label the boundaries unverified and seek traces or deployment evidence.
  2. Replace all three services with one process because the failures coincide.
  3. Accept the diagram because independent services can fail together.
  4. Infer a shared database and mark that inference as confirmed.

Worked answer

Best answer: A.

The best response is to mark the service boundaries as unverified and propose further evidence. Two features failing together could share a process, storage dependency, network path or identity provider. Browser observations establish the visible failure pattern, not its cause. Keep the generated diagram as a hypothesis, label the observed behavior separately and ask for permitted traces or deployment configuration that can distinguish the alternatives. A polished diagram does not increase the strength of the underlying evidence.

Architecture recovery must distinguish observation from inference; several different implementations can produce the same visible result.

Check your work

  • Separates observed behavior from inferred topology
  • Identifies evidence that distinguishes competing explanations

2. Review a generated reconciliation change

A rental platform promises that one physical bicycle cannot be assigned to two active rentals. An AI-generated optimization checks availability in a read replica, then writes a rental to the primary. Sequential tests pass. Write a short architecture review: identify the promise at risk, propose a concurrent test, and describe a design constraint that would protect it. Do not assume the replica is current or that an extra pre-check is atomic.

Worked answer

The invariant is at most one active rental per bicycle. Start two requests for the same bicycle behind a test barrier so both availability checks complete before either write proceeds; introduce replica lag if needed. Assert that at most one request commits a rental. Enforce the invariant at the authoritative write boundary through an atomic conditional operation or suitable transaction and uniqueness mechanism. A second check outside that boundary still races. Record why the optimization was rejected or constrained and add the concurrent scenario to verification.

Architecture review evaluates a generated change against a system promise, rather than treating passing sequential tests as sufficient.

Check your work

  • States the cross-request invariant
  • Constructs a controlled concurrent failure test
  • Places enforcement at an authoritative atomic boundary

3. Recover missing decision rationale

A team inherits an AI-assisted document-conversion service with a twenty-megabyte upload limit. Nobody remembers why the limit exists. Product wants to raise it to two gigabytes tomorrow. Propose an evidence-gathering plan and a minimal decision record. Explain how you would distinguish an intentional architectural constraint from an arbitrary generated default without asserting that either explanation is already true.

Worked answer

Inspect configuration history, tickets, provider limits and permitted operational measurements, then trace how upload size affects buffering, conversion memory, duration and temporary storage. Run bounded experiments at increasing sizes and check cancellation and partial-file cleanup. The limit may protect a resource, satisfy a dependency or simply be a default; label these as hypotheses until evidence distinguishes them. Record the user need, alternatives, measured constraints, chosen limit and review trigger. A larger limit should follow an explicit streaming or resource-management decision if whole-file processing is unsafe.

This task addresses intent debt by reconstructing rationale and making the next decision auditable, rather than inventing a reason for existing code.

Check your work

  • Collects multiple relevant evidence types
  • Keeps hypotheses distinct from findings
  • Records tradeoffs and a verification plan
