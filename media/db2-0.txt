Distributed data & consistency
Illustrated lesson · Part 1 · Synthetic narration

Data locality and denormalization — A join crosses storage boundaries

Imagine drawing a normalized database as a graph. Each row is a node, and each foreign-key reference is an edge. Placing rows on storage machines becomes a partitioning problem: keep related rows together while keeping the machines reasonably balanced. An edge crossing a partition boundary suggests a network lookup during a join. Some graphs divide naturally, such as independent accounts with their own orders. Social relationships and shared reference data are harder because many users connect across any boundary we choose. Even an excellent placement cannot remove every crossing. Counting rows alone misses the workload: a frequently followed edge can matter more than thousands of rarely used references.

Data locality and denormalization — Copying trades reads for updates

Denormalization changes that problem by copying information into the aggregate that needs it. A profile document can contain the region name, employment entries and education entries instead of requiring a separate lookup for each item. Fetching the profile then requires one bounded access path, which is easier to distribute by user identifier. The cost appears when shared information changes. A region rename that once modified one row may now require updates to many profiles, and intermediate states can disagree. Follow the arrows from one shared region to two copied profiles: duplication removes read-time communication but creates write-time maintenance. It moves work and responsibility rather than making them disappear.

Hash partitioning — Compute a destination locally

A local hash table turns a key into a storage location. A distributed hash table extends that idea by assigning ranges of hash values to different machines. Suppose a teaching example uses hashes from zero through ninety-nine: node A owns zero through thirty-two, B owns thirty-three through sixty-five, and C owns the remainder. A client hashes an account key, finds the containing range in its routing map and contacts the responsible node. The same key must produce the same hash for all clients using that configuration. No central dispatcher needs to execute every data request, which helps different clients make progress independently as the cluster grows.

Hash partitioning — Balance keys, then inspect traffic

Hashing deliberately scatters nearby input keys. That is useful for distributing many distinct keys, but it removes the original key order. Asking for one known account is easy; asking for every account between two identifiers cannot generally be answered by scanning one contiguous hash interval. Nor does a uniform distribution of keys imply uniform traffic: one extremely popular key still maps to one replica group. In the diagram, distinguish the key-to-hash calculation from the routing map. The first is deterministic computation; the second is shared configuration that can change. A correct hash calculation with an obsolete ownership map can still send a request to the wrong machine.

Replication and partitions — Replicate each key, not the whole cluster

A cluster containing many machines should expect individual failures. If every key has only one copy, losing a node makes that node's range unavailable and may lose data permanently. Replication stores each key on several nodes so another copy can survive. Keep the distinction between cluster size and replication factor clear: a cluster might contain hundreds of machines while each key has three replicas. A write to all replicas of one key then involves three destinations, not every machine in the cluster. This bounded redundancy preserves the basic scaling idea while improving durability and recovery options, provided the replicas do not all share the same failure boundary.

Replication and partitions — An update arrives at different times

Replication introduces a new timing problem. Initially A, B and C store x equal to one. A client writes x equal to two, and A receives the update before B and C. During this interval, different replicas can answer the same read differently even though no disk has failed. Network delays, queueing and scheduling make simultaneous arrival unrealistic. Now imagine that the network separates A from the other copies. If both sides must answer immediately, they cannot always know whether an unseen write has occurred elsewhere. If they must preserve a single real-time-consistent history, some requests must wait or fail. The partition makes this choice unavoidable; it is not solved by drawing more replica arrows.
