One deployable application

A repair platform contains ticketing, technician scheduling and customer notifications in one deployable application. Running four copies behind a load balancer creates four replicas of that application. It does not create four business services. Each replica can still execute all three responsibilities, and a release typically deploys the same application package. A database and cache outside that package do not, on their own, establish independent application boundaries. This arrangement can be useful for a small team: developers run one application locally, follow a request through one process and use a local database transaction for related changes. Trouble may appear when unrelated modules force coordinated releases or compete for very different resources. First ask whether clearer modules inside the application would address the problem. A network boundary adds deployment and failure concerns, so justify it using an observed need for independent change or operation rather than the visual appeal of additional boxes.

Choosing service boundaries

Suppose technician scheduling becomes a separate service because its optimization workload and release cadence differ from ticket management. The boundary now has a contract: ticket management requests a slot, scheduling accepts or rejects it, and both agree on identifiers and outcomes. This can allow independent implementation, but independence is weakened if every schema change still forces both services to release together. A meaningful boundary contains change as well as code. Now scheduling accepts a slot but the reply is lost. Ticket management sees a timeout while scheduling has already changed state. A local rollback in ticket management cannot undo a remote commitment automatically. The design needs a way to discover the outcome, avoid duplicate reservations and recover from abandoned work. Trace this failure before celebrating a successful normal-path demo. Smaller services can make focused tests easier, while cross-service behavior requires contract tests, observability and explicit recovery policies. Compare these costs with the independence that motivated the split.
