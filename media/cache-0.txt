Stateless services, proxies & caches
Illustrated lesson · Part 1 · Synthetic narration

Where does state live? — A conversation accumulates state

A useful way to discover state is to interrupt a conversation halfway through it and move the next message to a fresh worker. Consider an email submission dialogue: earlier commands establish the sender and recipients, while a later command supplies the message body. A worker that sees only the final body cannot reconstruct the complete operation. It needs information retained from the earlier messages. In this example, notice these pieces accumulating in one conversation context. State is therefore not simply data in a database; it includes any remembered information that later processing depends on, including process variables, an open connection's context, or a partially completed user interaction.

Where does state live? — Identical code, different memory

HTTP requests are designed to carry the information needed to interpret each individual exchange, but an HTTP application can still introduce a dependency on a particular worker. Imagine worker A storing an unfinished game only in its own memory. The next request contains the game identifier but reaches worker B, whose dictionary has no corresponding entry. Identical code does not make these workers interchangeable because they have different histories. This example follows the identifier to the wrong memory store and exposes the missing information. Before adding replicas, ask whether another worker can complete the request using the request itself and explicitly shared services, without consulting the original worker's private history.

Stateless workers with stateful data — Move authority out of workers

Start with a chess application that keeps a dictionary of active games inside one process. Cloning that process creates several independent dictionaries, so each game becomes tied to the worker holding it. Instead, put the authoritative game record in shared storage and include its identifier in each request. A worker loads the board, validates the requested move, saves the result, and returns the updated representation. A replacement worker can now continue after the original process disappears. In this example, notice two interchangeable application workers converging on one game record. We have removed a placement constraint from the application tier, but we have deliberately created a shared dependency that needs its own capacity and availability design.

Stateless workers with stateful data — Reject a stale move

Externalizing state does not automatically make concurrent updates correct. Suppose two requests both read game version twelve. The first valid move updates the record to version thirteen. If the second request blindly writes its earlier view, it can erase the accepted change or apply a move to an obsolete board. A conditional update that succeeds only while the version is still twelve lets exactly one of these competing updates win. The second request must reload and reconsider its action. Notice the two reads and the rejected stale write; it makes clear that a common storage location and a correct update protocol solve different problems.
