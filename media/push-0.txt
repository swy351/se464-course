Push notifications and connected clients
Illustrated lesson · Part 1 · Synthetic narration

Why the server cannot simply call the phone — An event without a click

Imagine a passenger waiting for a car with the ride application in the background. The driver reaches the pickup point and sends an arrival update. The passenger has not clicked anything, so there is no fresh request waiting for a response. Draw the event starting at the driver, entering the ride service, and then needing to reach the passenger. An auction ending is even clearer: a timer can create the event while every participant is idle. Ordinary request and response handles a user asking for information; this requirement adds a path for information to arrive because something elsewhere changed. The notification should point to the saved ride state, so losing the alert does not lose the arrival itself.

Why the server cannot simply call the phone — Why an inbound request fails

Suppose the passenger moves from home Wi-Fi to a mobile network. An address remembered a minute ago may no longer locate the phone. Even a current address may belong to a shared router that does not accept unsolicited inbound traffic. A firewall may block the connection, and the operating system may have suspended the application to save resources. These are separate obstacles; solving only address discovery does not wake a stopped application. Reverse the connection setup instead: the device establishes an outbound path to infrastructure that stays reachable. When connectivity disappears, the path disappears too. Therefore delivery also needs a retention and expiry policy, and the application must refresh authoritative state when it returns.

Registration and mobile delivery — Register a route before sending

Follow the registration triangle before attempting a notification. First the installed application asks the platform service for a routing identifier, subject to the relevant notification permissions. Next it sends that identifier to its own backend over an authenticated connection. The backend associates the installation with the account. Later a domain event identifies the account, the backend retrieves its registered destinations, and the provider delivers through its connection to the device. The provider identifier is a route to an installation, not a substitute for the account identity. A person may have a tablet and phone, while reinstalling an application may change the route. This is why the registration table must support updates and multiple destinations.

Registration and mobile delivery — One connection serves many apps

Now compare one hundred applications each maintaining their own connection with one operating-system connection serving them all. Keeping a network path alive requires periodic activity, and reconnecting costs work when the device changes networks. Sharing that responsibility avoids repeating the same machinery for every app. The application backend submits a notification to the platform, which handles the device-facing connection. But a successful submission only establishes that the provider accepted the request. It does not prove that the phone was online, that a banner appeared, or that the person read it. For a ride arrival, keep the current ride status on the backend and let opening the app retrieve it. Treat the notification as a timely prompt to inspect that state.
