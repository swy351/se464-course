Case study: Uber’s real-time push platform

Week 12 · November 25

Study a historical push platform through delivery priorities, expiry and connection ownership.

From polling to separated responsibilities

The historical Uber case begins with rider and driver applications polling for changing trip state. The slides report that polling dominated gateway traffic and that startup requests competed on weak mobile networks. RAMEN separates the decision to send an update from creating its content and delivering it. This division targets both operational efficiency and the difficulty of migrating many existing features.

Fireball reacts to domain events and determines recipients and message types. The API gateway assembles payloads using domain services, reusing logic associated with earlier pull APIs. A delivery system then owns connections and retries. These are case-study responsibilities, not mandatory product names for every architecture. In a course system, enrolment events, timetable composition and device delivery can be separated in the same way.

Predict: Should the connection server also decide every business rule about when a ride update is needed?

Separating that decision reduces coupling between domain evolution and delivery infrastructure.

Priority, expiry and resumable delivery

RAMEN attaches delivery policy to payloads: priority determines which pending updates matter first, expiry limits how long an update remains useful, and replacement can retain the latest state instead of every intermediate version. The historical SSE protocol adds sequence numbers, reconnect cursors and separate acknowledgements. These application mechanisms supply recovery behavior that a persistent transport alone cannot guarantee to the user.

A lost acknowledgement is ambiguous: the client may have processed a message even though the server retries it. Consumers must therefore tolerate duplicates. Expiry also bounds the delivery promise: an offline device cannot receive a timely update indefinitely. Distinguish coalescing state snapshots from deduplicating identical messages; replacing an old location with a new location is reasonable, but dropping an independent payment event is different.

Predict: If the client processes sequence 3 but its acknowledgement is lost, may sequence 3 arrive again?

Yes. Retry can produce duplicates; the client needs safe repeat processing or message-ID tracking.

Scaling connection ownership

The slides describe an early RAMEN implementation using sharded connections and Redis, followed by a redesign separating connection handling, routing and cluster management. Treat the throughput and connection counts as reported historical observations. They illustrate why topology convergence and overloaded event loops can become important even when each individual message is small and the application’s business logic appears straightforward.

In the redesigned case, Streamgate handles protocol and storage work while a frontend routes requests to the appropriate worker. Helix and ZooKeeper manage topology-related responsibilities, and the cache and durable storage layers serve different purposes. The architectural lesson is ownership: changing a worker assignment must be coordinated with routing and recovery. More workers cannot help if clients or producers continue using stale ownership information.

Predict: Can doubling connection workers help if routing still sends all requests to the old owner?

Not reliably. Membership and routing convergence are part of the scaling design.

Protocol evolution and the reliability boundary

The case identifies long-tail delivery problems involving acknowledgement loss, inconsistent client behavior and limitations of the earlier unidirectional stream. Its later protocol work explores bidirectional communication and more standardized client support. Separate the enduring requirement from a particular transport choice: the service needs feedback about progress, recoverable state and a clear policy for clients whose networks disappear for extended periods.

Bidirectional streaming can carry acknowledgements promptly, but it does not turn a network failure into certainty about application effects. Define exactly what each acknowledgement means and which state survives a worker restart. The source’s reported server-side reliability is not an end-to-end guarantee that a person received or acted on an alert. Evaluate transport changes by measured recovery behavior and implementation consistency.

Predict: Does changing from SSE to a bidirectional RPC stream automatically create exactly-once application processing?

No. Durable state, acknowledgement meaning and duplicate handling still determine application effects.

Self-check

What are the three separated responsibilities in the RAMEN case?

Deciding when/who to notify, composing the payload, and delivering it over client connections.

Why can replacing queued location updates save bandwidth?

The latest location snapshot may supersede earlier snapshots, whereas independent business events generally cannot be discarded that way.

Why should historical server-side reliability not be read as human notification receipt?

It measures a particular server boundary; device connectivity, application processing and user attention are separate.

Design exercise

Adapt RAMEN responsibilities to a course waitlist. Which updates can be replaced and which require durable handling?

An event trigger identifies affected students; a composition layer builds the current offer; delivery tracks destinations and acknowledgements. A refreshed queue-position snapshot can replace an older one; a seat offer with expiry needs durable state, explicit acceptance and safe retries.

1. Which queued update may replace another?

A courier platform queues two types of messages for an offline driver: complete route-location snapshots and signed proof-of-delivery records for different parcels. Storage is under pressure. The latest snapshot contains all location state needed by the map, while every proof record is independently required for audit. Which compaction policy preserves the stated semantics without assuming every notification is replaceable?

  1. Keep every location snapshot but combine unrelated proof records into one arbitrary record.
  2. Keep only the last message for the driver, regardless of type.
  3. Discard all proofs because the provider accepted their notification requests.
  4. Keep the newest scoped location snapshot and preserve each required proof record.

Worked answer

Best answer: D.

Coalesce older route-location snapshots into the newest complete snapshot for the same scope, but preserve each distinct proof-of-delivery record in durable authoritative storage. A notification about a proof may be retried or regenerated from that record, rather than making the transient delivery queue its only copy. Define snapshot version and scope so unrelated routes are not collapsed together. Expiry can make an old location snapshot unhelpful, but it does not authorize deleting audit evidence. The policy follows business meaning: message arrival order or a shared destination alone does not establish that one payload supersedes another.

Compaction is valid only when the retained information replaces everything the discarded message was required to convey. Business-event durability belongs beyond a best-effort push queue.

Check your work

  • Coalesce only scoped superseding snapshots.
  • Preserve independent audit records durably.
  • Separate notification transport from authoritative evidence.

2. A burst with an expiry budget

A real-time delivery tier receives a burst of 18,000 independent advisory messages at time zero. It can transmit 600 messages per second at a constant rate, has no other traffic and serves FIFO. Every message expires 20 seconds after creation. In a fluid approximation, how many can be sent before expiry and how many become stale? Propose a response that distinguishes operational alerts from guaranteed business actions.

Worked answer

The tier can transmit 600 × 20 = 12,000 messages within the window, leaving 6,000 stale messages in this approximation. Draining all 18,000 would take 30 seconds, so sending the remaining third later would violate the stated freshness policy. Discard or suppress expired advisories and record their outcome; prioritize only if the contract permits it. Add capacity or reduce admitted advisory work when the expected burst exceeds the freshness budget. If some messages represent essential business actions, persist those actions separately and expose authoritative status or recovery rather than treating an expired notification as cancellation of the action.

A queue smooths a burst only within its capacity and freshness constraints. Delivery acceptance and durable business completion are different reliability boundaries.

Check your work

  • Compute 12,000 sent, 6,000 stale and 30-second drain time.
  • Respect expiry rather than blindly drain.
  • Separate advisory freshness from business durability.

3. Acknowledgement lost after application

A warehouse handheld receives message M77 instructing it to display a task confirmation already committed in the backend. The device records M77 and updates its screen, but its acknowledgement is lost during a disconnect. The delivery tier replays M77 after reconnection. Design the device and server state needed for safe replay, and explain why provider acceptance, device receipt and a worker reading the confirmation are different milestones.

Worked answer

Give messages stable IDs and define an acknowledgement as a specific processing milestone. The device records M77’s processed status durably enough for the promised replay window and applies any local effect idempotently, then acknowledges duplicates without repeating that effect. Coordinate local recording and application so a crash does not create an ambiguous half-completion, or rebuild the view from authoritative backend state. The server retains replay state until acknowledgement or its documented expiry and does not interpret provider acceptance as device processing. A displayed confirmation still does not prove a human saw or acted on it; that requires a separate explicit interaction.

A lost acknowledgement makes duplicate delivery normal. End-to-end effects need deduplication or idempotency at the consumer, and each reported success must name its actual boundary.

Check your work

  • Use stable IDs and consumer replay-safe effects.
  • Define retention/expiry and crash behavior.
  • Separate transport, device and human milestones.
