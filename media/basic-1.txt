A scalable publishing system: the NGVM case
Part 2 • Synthetic narration

Scale the read path deliberately

Suppose a public archive receives one thousand page requests per second. If a shared cache answers eighty percent, two hundred requests reach the application. If each remaining page needs three database reads, the uncached read workload is approximately six hundred reads per second. These are deliberately simplified assumptions, but they show why cache effectiveness must be applied before sizing the database. Adding application workers changes application capacity; it does not by itself change those six hundred reads. Classify the remaining requests before distributing them across replicas. A visitor reading an old exhibit may tolerate a short delay, while a curator checking an edit immediately after saving expects the new state. The first path can use a lagging replica if the product permits it; the second may require a primary read or another explicit consistency mechanism. A scalable diagram therefore needs routing rules as well as boxes. Measure the hit rate and query count under a representative mix rather than assuming every request benefits equally.


Evaluate scaling claims with workload evidence

An illustrative service records twenty-six million updates over a thirty-day month. Dividing by approximately 2.6 million seconds gives ten updates per second on average. That calculation is useful for checking magnitude, but it conceals timing. If a news event produces one hundred updates per second for several minutes, a system sized only for the average can accumulate a backlog or reject requests despite apparently modest monthly traffic. Also expand the meaning of an update. One user action may write a primary row, update indexes and append an audit record inside a transaction. Those actions do not map to a fixed number of physical disk operations because buffering, logging and storage behaviour intervene. Test the complete transaction with realistic data, contention and burst duration. Report latency and error rate alongside throughput. The decision to retain one primary should follow those measurements and consistency needs, rather than a direct comparison between user events and a device's advertised operations per second.
