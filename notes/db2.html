Distributed data & consistency

Week 4–5 · September 30; October 5

Follow keys through a distributed store and reason about replication, partitions, consistency, and quorum availability.

Data locality and denormalization

Imagine drawing a normalized database as a graph. Each row is a node, and each foreign-key reference is an edge. Placing rows on storage machines becomes a partitioning problem: keep related rows together while keeping the machines reasonably balanced. An edge crossing a partition boundary suggests a network lookup during a join. Some graphs divide naturally, such as independent accounts with their own orders. Social relationships and shared reference data are harder because many users connect across any boundary we choose. Even an excellent placement cannot remove every crossing. Counting rows alone misses the workload: a frequently followed edge can matter more than thousands of rarely used references.

Denormalization changes that problem by copying information into the aggregate that needs it. A profile document can contain the region name, employment entries and education entries instead of requiring a separate lookup for each item. Fetching the profile then requires one bounded access path, which is easier to distribute by user identifier. The cost appears when shared information changes. A region rename that once modified one row may now require updates to many profiles, and intermediate states can disagree. Follow the arrows from one shared region to two copied profiles: duplication removes read-time communication but creates write-time maintenance. It moves work and responsibility rather than making them disappear.

A key-value interface does not physically prevent storing references. You can place a region identifier inside a user value and issue another get for that region. However, repeatedly doing this reconstructs application-managed joins, often as serial network round trips. Referential integrity may also become the application's responsibility. The simplified distributed key-value model is useful for understanding this tradeoff, but it is not a complete description of every database sold as NoSQL. Many products provide additional query and transaction features. Judge the chosen model by a specific request: which values must be fetched, whether they can be fetched together, what is duplicated, and how a partially completed update is repaired. Locality is valuable only when its maintenance costs fit the workload.

Predict: Will copying an industry name into every profile make renaming the industry easier?

No. It can make profile reads local, but the rename now affects many copies or requires accepting temporary disagreement.

Hash partitioning

A local hash table turns a key into a storage location. A distributed hash table extends that idea by assigning ranges of hash values to different machines. Suppose a teaching example uses hashes from zero through ninety-nine: node A owns zero through thirty-two, B owns thirty-three through sixty-five, and C owns the remainder. A client hashes an account key, finds the containing range in its routing map and contacts the responsible node. The same key must produce the same hash for all clients using that configuration. No central dispatcher needs to execute every data request, which helps different clients make progress independently as the cluster grows.

Hashing deliberately scatters nearby input keys. That is useful for distributing many distinct keys, but it removes the original key order. Asking for one known account is easy; asking for every account between two identifiers cannot generally be answered by scanning one contiguous hash interval. Nor does a uniform distribution of keys imply uniform traffic: one extremely popular key still maps to one replica group. In the diagram, distinguish the key-to-hash calculation from the routing map. The first is deterministic computation; the second is shared configuration that can change. A correct hash calculation with an obsolete ownership map can still send a request to the wrong machine.

Membership changes expose the coordination that the simple picture hides. When a node joins, leaves or fails, clients and servers must discover current ownership, move or reconstruct data and handle requests during the transition. Virtual partitions or consistent-hashing techniques can limit movement, but they do not replace the migration protocol. Replication also means that one key maps to a bounded group rather than necessarily one physical copy. The scalability argument is therefore conditional: ordinary operations should contact a small number of nodes, work should be balanced, and membership management should not become the dominant cost. Explain these assumptions whenever claiming that capacity grows with node count. A useful test changes both the number of keys and the skew of requests, because the two stress different parts of the design.

Predict: If one key receives half of all requests, will a better hash spread those requests?

No. All requests for that key still map to its owner or replica set unless the application introduces another distribution or caching strategy.

Replication and partitions

A cluster containing many machines should expect individual failures. If every key has only one copy, losing a node makes that node's range unavailable and may lose data permanently. Replication stores each key on several nodes so another copy can survive. Keep the distinction between cluster size and replication factor clear: a cluster might contain hundreds of machines while each key has three replicas. A write to all replicas of one key then involves three destinations, not every machine in the cluster. This bounded redundancy preserves the basic scaling idea while improving durability and recovery options, provided the replicas do not all share the same failure boundary.

Replication introduces a new timing problem. Initially A, B and C store x equal to one. A client writes x equal to two, and A receives the update before B and C. During this interval, different replicas can answer the same read differently even though no disk has failed. Network delays, queueing and scheduling make simultaneous arrival unrealistic. Now imagine that the network separates A from the other copies. If both sides must answer immediately, they cannot always know whether an unseen write has occurred elsewhere. If they must preserve a single real-time-consistent history, some requests must wait or fail. The partition makes this choice unavoidable; it is not solved by drawing more replica arrows.

This is the useful reading of CAP: during a network partition, the system cannot guarantee both linearizable behavior and availability for every request to a nonfailed node. It is not a menu that permits eliminating network failures by selecting two letters, and availability here has a precise meaning beyond an uptime percentage. Designs can make different choices for different operations. A social counter might tolerate a delayed view, while a scarce-item reservation may refuse a decision without the required coordination. Document what counts as a completed write, which failures are tolerated and how replicas converge after communication returns. Redundancy alone says little about the values clients are permitted to observe.

Predict: Can both sides of a 2+1 split independently accept arbitrary writes while guaranteeing one real-time order?

Not while also remaining available for every request; they cannot coordinate the conflicting decisions across the partition.

Session guarantees

Consistency becomes easier to discuss when we describe an actual user's sequence of operations. Monotonic reads means that after a session observes a version, a later read does not go backward to an older version. Read-your-writes means that after the session completes an update, its later reads include that update or a later one. These promises are different. A user who has never written anything can still suffer a nonmonotonic read when requests alternate between a current replica and a lagging one. A user who saves a profile can fail to read their own write even if every subsequent read consistently returns the same old version.

Draw two read arrows from one client: the first reaches A at version eight, and the second reaches B at version seven. That is a monotonic-read violation. Then replace the first arrow with a completed write of version eight: the same stale second response violates read-your-writes. Routing the session to one sufficiently current node can help, but the promise must survive reconnection and failover. A session can carry a minimum version or replication position that a new node must satisfy. Waiting until that position is applied preserves the promise at the cost of delay; accepting an older response preserves immediate availability at the cost of the promise. The system needs to choose deliberately.

Monotonic writes preserves a session's write order. If a client completes an update and then issues another, delayed delivery must not make the earlier operation overwrite the later one. Sequence information and an ordering protocol can prevent that reversal. Wall-clock timestamps are not a universal solution because clocks differ and concurrent operations need a defined conflict rule. These session guarantees constrain a client's experience; together they still do not establish every property of global linearizability. Test them with histories containing replica switching, retries and failure, rather than only a successful single-node run. For each API operation, decide which ordering information travels with the request and what the service does when it cannot yet honor that information.

Predict: A client reads version 8 and then version 7 after failover. Which guarantee is broken?

Monotonic reads. Read-your-writes is also broken if version 8 represented that client’s own completed write.

Quorums and their limits

A quorum is a threshold of replica responses required before an operation is treated as complete. With three replicas, consider writes acknowledged by two and reads answered using two. If A and B acknowledged a completed write, any set of two read responders must contain A or B. The overlap is the essential arithmetic: R plus W greater than N guarantees intersection between the selected read set and the acknowledged write set, under a stable replica membership. It does not mean the two read values must be identical. A read can receive one older value and one newer value, so the system still needs meaningful version information and a reconciliation rule.

Change the thresholds to see the workload tradeoff. With W equal to three and R equal to one, a completed write has reached every replica, allowing a subsequent read to use a single response under the model's assumptions. But the write must wait for the slowest required participant, and one unavailable replica prevents completion. With W and R both equal to two, one unavailable replica can still leave enough responders for both kinds of operation. This is a latency and failure-policy choice, not just a consistency switch. The relevant replicas belong to this key; another key may have a different replica group and remain unaffected by the same failed machine.

Quorum intersection alone does not implement linearizability. Concurrent writes, partially completed operations, membership changes and version ordering all require a protocol. A timestamp can be useful metadata without being an infallible global clock. A timed-out write may have reached some replicas, so retry handling must account for an uncertain outcome. Distinguish a durable acknowledgment from a response that merely accepted work into volatile memory. When presenting a quorum design, state the failure model, which versions can be returned, how conflicts are resolved and what happens during repair. An excellent exercise enumerates every two-member subset of three replicas, proves the intersection property, and then constructs a concurrent-write history to show what that small proof does not establish.

Predict: For N=3, R=1 and W=3, what stops when one replica fails?

New writes cannot obtain all three acknowledgements. Reads may still obtain one response, subject to the system’s consistency and failure rules.

Stronger consistency and synthesis

Begin with an observable history rather than a product label. A user completes an update to a shared register and then another user starts a read. Linearizability requires that read to behave consistently with a single order in which each operation takes effect at one instant between its invocation and response. Real-time precedence matters: an operation completed before another began must appear earlier in that order. Operations that overlap may admit more than one order. This is stronger than merely preserving each client's own sequence. A diagram should therefore show request and response intervals, not just a list of values with no indication of when clients were told an operation had finished.

Compare that promise with a replicated social display. One session may always read its own updates and never move backward, while another session still sees a previous version. Those session guarantees can make the interface understandable without creating a globally linearizable object. Conversely, a linearizable single-key operation does not automatically make a transaction spanning several keys serializable. The design question is which unit of state needs which guarantee. For a shared reservation count, ordering updates may be essential; for a cached display of recent activity, bounded or eventual freshness may be acceptable. Naming the guarantee prevents students from treating every successful quorum read as proof of the strongest possible model.

Synthesize the data architecture in three separate decisions. Partitioning assigns keys to bounded groups and divides work. Replication supplies redundant copies and creates synchronization questions. Consistency protocols specify when operations complete and which histories clients may observe. These decisions interact but are not synonyms. The final design should identify the key, replica group, acknowledgment rule, conflict behavior and failure response for a concrete operation. Then walk through a normal request, a delayed message and a failed replica. If the explanation cannot say what the client sees in each case, the architecture is incomplete even if its component diagram includes all the expected database boxes. Stronger guarantees can be valuable, but their coordination and availability costs must support an actual application requirement.

Predict: A write finishes before another client starts a read. May a linearizable read return the prior value?

No, unless a later intervening operation legally restored that value; the completed write must precede the later read.

Self-check

With N=3, R=2 and W=2, why must a read quorum overlap a completed write quorum?

Two subsets of size two drawn from three replicas share at least one replica. This gives intersection, but correct version/protocol behavior is still needed.

A client reads version 8 then version 7 after switching replicas. Which session property fails?

Monotonic reads. If version 8 was that client's own completed write, read-your-writes also fails.

Does preserving each client's own write order prove linearizability?

No. Linearizability also requires a single legal operation order consistent with real-time precedence across clients.

Design exercise

A key has three replicas. Compare R=2,W=2 with R=1,W=3 when one replica becomes unreachable. State what you can and cannot conclude about consistency.

Both choices satisfy R+W>N, so successful read and write quorums overlap in the simple fixed-replica model. With one unreachable replica, R=2,W=2 can still meet both quorums; R=1,W=3 can read but cannot complete its configured write quorum. Overlap alone is not a proof of linearizability. Discuss version ordering, concurrent writes, repair, and the failure assumptions.

1. The isolated inventory desk

A five-node inventory service normally provides linearizable reservations for the last item of a product. A network partition separates two nodes in a remote shop from the other three. The application forbids promising the same item to two customers. The isolated shop can still accept local HTTP requests, but cannot communicate with the majority. Under these constraints, which behavior is the strongest defensible choice for a new reservation?

  1. Confirm locally because HTTP requests still reach the shop
  2. Confirm on both sides and call the service linearizable because each node is sequential
  3. Defer or reject confirmation on the isolated side while preserving the consistency contract
  4. Add a read cache and assume it can decide exclusive ownership

Worked answer

Best answer: C.

The isolated shop should decline or defer confirmation and clearly report that the reservation is not yet committed. During this partition, the service cannot both guarantee linearizable reservations and successfully complete every request on both sides. It may offer a nonbinding expression of interest, but must not label that a confirmed reservation. The majority can continue only through the system’s valid coordination protocol. This is a partition-specific trade-off; it does not mean the service must sacrifice availability during ordinary healthy operation.

The application requires one authoritative decision about a scarce item. Local acknowledgement without coordination would weaken that promise.

Check your work

  • Rejects independent confirmation on the minority
  • States the trade-off specifically during partition
  • Distinguishes deferred interest from committed reservation

2. Read latency after an unfinished write

A replicated key initially holds version 10 on nodes A, B and C. A writer sends version 11, which reaches A only, then crashes before completing its write protocol. Reader R1 consults A and B and returns 11. Later reader R2 consults B and C and returns 10; no intervening write occurred. Both readers used two responses. Explain why a quorum-intersection argument alone fails to justify these results, and identify the missing kind of protocol work.

Worked answer

The usual completed-write overlap argument does not apply to version 11 because that write never reached its required completion condition. R1 nonetheless exposed it, and the subsequent return to 10 violates a linearizable register history: once 11 is observed, the pending write must be placed before R1, so R2 cannot then return 10. A complete protocol must handle incomplete writes, for example through version validation and read-back/write-back stabilization under its specified algorithm. Merely choosing the largest value among two replies does not supply that proof.

Intersecting response sets are useful structure, but safe handling of partially completed operations is essential to the actual consistency guarantee.

Check your work

  • Recognizes that version 11 was an incomplete write
  • Explains why R1 then R2 cannot be linearized
  • Names protocol stabilization/validation rather than more arbitrary waiting

3. Denormalized names with repair

A directory embeds each laboratory’s display name into 40,000 researcher profiles to make profile reads local. The lab rename operation updates the authoritative laboratory record immediately, then asynchronously changes embedded copies. Product requirements allow names to take five minutes to converge, but an older retry must never overwrite the new name. Design the update metadata, consumer rule and repair process. Explain what this choice gains and what it does not guarantee.

Worked answer

Assign a monotonically increasing version to each laboratory name change and store that laboratory version beside each embedded name. Consumers apply a change only when its version is newer than the stored version; equal versions are safe duplicates and older versions are ignored. Track propagation progress and periodically reconcile profiles against the authoritative record to repair missed events. Alert or rebuild when the five-minute objective is exceeded. Profiles retain local reads at the cost of fan-out and temporary inconsistency; the design does not make every reader immediately see the rename.

Version-aware propagation addresses reordering, while reconciliation addresses loss. These are different failure modes of a derived copy.

Check your work

  • Uses per-laboratory versions and conditional application
  • Includes reconciliation and a measurable convergence objective
  • States local-read benefit and temporary staleness
