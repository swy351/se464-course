1. Connection count hides the work

A reverse proxy selects the backend with the fewest open connections. Backend A has one HTTP/2 connection carrying 80 active requests, while backend B has ten connections carrying one active request each. All requests require similar CPU time and the machines have equal capacity. The proxy repeatedly sends new work to A. Which observation most directly explains why the policy is making a poor choice?

  1. DNS always sends clients to the wrong continent.
  2. A has less work because it has fewer connections.
  3. One connection can carry many requests, so connection count understates A’s load.
  4. B must be unhealthy because it has more connections.

Worked answer

Best answer: C.

Connection count is a poor load proxy when one connection multiplexes many requests. A has fewer connections but more active application work in this scenario. Consider an implementation that accounts for active requests, measured outstanding work or another suitable load signal, and verify behavior with the actual protocol configuration. Simply reversing least-connections into most-connections would also be brittle: connection lifetimes, idle connections and request cost can change. CPU and queue metrics may help, but each has reporting delay and overhead. The correct policy follows the workload rather than a universal ranking of algorithms.

HTTP/2 breaks an assumed one-connection-to-one-request relationship. Equal hardware does not rescue a metric that measures the wrong unit of work.

Check your work

  • Recognize multiplexing mismatch.
  • Choose a workload-relevant metric.
  • Avoid claiming one routing algorithm is universally best.

2. Capacity while draining

A video-metadata service has six identical stateless workers. Each sustains 180 requests per second while meeting the latency target. Peak incoming traffic is 780 requests per second. Operations want to drain two workers simultaneously for an upgrade and retain 20% capacity headroom on the remaining workers. Using a simple additive-capacity model, determine whether this plan meets the target and how many workers must remain active.

Worked answer

Four remaining workers provide 4 × 180 = 720 requests per second, already below the 780 arrival rate. With 20% headroom, the usable budget is only 0.8 × 720 = 576. The requirement is n × 180 × 0.8 ≥ 780, so n ≥ 5.417 and at least six workers must remain active. Under this model, the current fleet cannot drain even one worker while preserving that headroom. Add temporary capacity, reduce admitted traffic or schedule the change below peak. Confirm the shared database and balancer can support the plan; additive worker capacity is an assumption, not a measurement.

Headroom is a constraint on capacity during maintenance, not merely on the normal fleet. Draining also needs a policy for in-flight requests and a deadline.

Check your work

  • Calculate four-worker deficit and 576 budget.
  • Derive at least six active workers.
  • State a feasible maintenance adjustment and model limitations.

3. Diagnosing a faraway edge

Customers in Oslo sometimes reach a CDN edge in London rather than an available Stockholm edge. The hostname may use DNS steering, and some published addresses are anycast. Support concludes that the CDN is broken because Stockholm is geographically closer. Propose measurements that distinguish resolver-based steering, route selection and cache/origin latency before deciding whether the service is actually worse.

Worked answer

Compare DNS answers and TTLs from affected clients and their actual recursive resolvers, noting whether steering has client-network information. Identify the selected edge using provider diagnostics, and measure connection and application timings over repeated samples rather than assuming physical proximity predicts latency. For anycast addresses, inspect routing observations where available, while recognizing a path trace alone is not a complete performance explanation. Separate fresh cache hits from misses or revalidations that contact the origin. Compare latency, errors and load at both candidate paths. A London edge may perform better because of peering, capacity or policy even when it is farther away.

DNS chooses an address under a policy; anycast routing selects a path to an advertisement; the response may then require an origin fetch. Each stage can explain latency.

Check your work

  • Measure resolver/answer and edge selection separately.
  • Distinguish anycast policy from distance.
  • Separate hit/miss origin effects and compare observed outcomes.
