Secure Microservices: Boundaries, Tokens and Response
Worked answers

SE464 · Newly authored scenarios · Three exercises

1. Signing-key rotation without accepting strangers

An identity provider rotates from signing key K1 to K2. A reporting service caches the provider’s trusted verification keys and has not refreshed them, so valid K2 tokens fail. An engineer suggests reading an arbitrary key URL from each token header and fetching that key whenever verification fails. Which response restores rotation support without allowing a token sender to choose its own trust authority?

  1. Fetch any URL the token advertises and trust its result.
  2. Disable signature checks until the next deployment.
  3. Refresh through the configured trusted issuer and retain normal claim validation.
  4. Accept unknown keys if the token has a plausible username.

Worked answer

Best answer: C.

Refresh keys only through the configured trusted issuer’s key-distribution mechanism, with controlled caching and bounded retry behavior. Allow planned overlap for K1 and K2 as the issuer’s policy requires, and verify issuer, audience, permitted algorithms and token lifetime in addition to the signature. Do not trust an arbitrary header-supplied URL as a new authority: a malicious sender could offer a key for its own signature or induce unwanted outbound requests. Unknown keys should fail closed if trusted refresh cannot resolve them. Rotation monitoring helps distinguish a rollout problem from malformed or hostile tokens.

The token may identify a key within a trusted set, but it must not redefine who is trusted. Rotation changes key material while preserving the trust anchor.

Check your work

  • Keep discovery anchored to trusted configuration.
  • Handle caching/overlap without bypassing validation.
  • Fail closed for unresolved untrusted keys.

2. Measuring the revocation window

An access token is issued at 14:00 and expires at 14:12. At 14:03 an operator revokes its refresh token after suspected theft. API workers verify access tokens locally and do not consult a revocation list. Assume synchronized clocks and no expiration grace. How much longer can the stolen access token be accepted, and what changes could shorten that window without pretending refresh-token revocation already solves it?

Worked answer

The existing access token can remain acceptable until 14:12, leaving nine minutes after the 14:03 action, assuming its other checks pass. Revoking the refresh token prevents authorized renewal through that credential but does not update a self-contained token already held by an attacker. Shorter access-token lifetimes reduce the maximum window. Introspection, a revocation list or a subject/session version check can support earlier rejection, with explicit propagation and cache freshness guarantees. These add dependencies and operational cost, so define their outage behavior. Rotating a shared signing key can invalidate many unrelated sessions and is not a precise per-session remedy.

The calculation exposes the tradeoff between offline verification and rapidly changing authority. A design must state revocation latency rather than simply claiming tokens are revocable.

Check your work

  • Calculate nine minutes.
  • Separate refresh and access-token effects.
  • Offer explicit early-rejection mechanisms and tradeoffs.

3. A useful URL-fetching feature

A media service accepts a customer-supplied image URL and fetches it to create a thumbnail. It runs inside a cluster with access to private administration endpoints. Product requirements need only HTTPS images from two partner domains, but the current implementation follows every redirect and allows any hostname. Design validation and network boundaries for this feature, including what must be rechecked after a redirect.

Worked answer

Allow only the required scheme, partner hostnames and expected ports, using a real URL parser and a defined normalization policy. Resolve and restrict destinations so private administration or metadata addresses are not reachable, accounting for resolution changes. Either disallow redirects or revalidate every redirected URL and resolved destination under the same policy. Enforce outbound network restrictions as a separate boundary, and give the fetching workload minimal internal authority. Bound response size, time and decoding resources, then verify the content is an acceptable image. Log safe diagnostic metadata without secrets. An allowlist check on only the first URL is insufficient.

The intended feature is a narrow outbound capability. Validation constrains logical destinations, while network and resource controls limit consequences if parsing or application logic fails.

Check your work

  • Validate every destination including redirects/resolution.
  • Combine application policy with egress/least privilege.
  • Bound fetch and image-processing resources.
