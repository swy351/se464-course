One deployable application

Source slides 1–6

A monolith is one application deployment boundary, even when many identical instances run behind a load balancer. The MediaWiki example makes this clear: two hundred interchangeable replicas improve capacity without dividing business responsibilities into distinct services. External databases and caches do not by themselves change that application boundary.

A monolith can simplify local execution, integration and transactions. Its challenges can include coordinating many contributors and deploying a large application for a small change. These are tradeoffs rather than inevitable defects: strong module boundaries can support a maintainable monolith. Evaluate the team, change patterns and operational needs before introducing network boundaries simply to make a diagram look more distributed.

Worked walkthrough

A repair platform contains ticketing, technician scheduling and customer notifications in one deployable application. Running four copies behind a load balancer creates four replicas of that application. It does not create four business services. Each replica can still execute all three responsibilities, and a release typically deploys the same application package. A database and cache outside that package do not, on their own, establish independent application boundaries.

This arrangement can be useful for a small team: developers run one application locally, follow a request through one process and use a local database transaction for related changes. Trouble may appear when unrelated modules force coordinated releases or compete for very different resources. First ask whether clearer modules inside the application would address the problem. A network boundary adds deployment and failure concerns, so justify it using an observed need for independent change or operation rather than the visual appeal of additional boxes.

Choosing service boundaries

Source slides 7–10

Service boundaries assign responsibilities to separate deployable applications. Each exposes a contract that clients can use without knowing its implementation language. This can enable specialized scaling and independent development, but only when changes can actually occur independently. A set of services that must always release together retains strong coupling.

Network boundaries introduce latency and partial failures. A successful payment with a failed inventory update cannot automatically be undone by a local database rollback. Designs need explicit retry, idempotence and recovery behavior. Debugging also crosses process boundaries. Smaller units may simplify focused tests while increasing the importance of contracts, observability and integration testing. Use business responsibilities and consistency requirements to justify a split.

Worked walkthrough

Suppose technician scheduling becomes a separate service because its optimization workload and release cadence differ from ticket management. The boundary now has a contract: ticket management requests a slot, scheduling accepts or rejects it, and both agree on identifiers and outcomes. This can allow independent implementation, but independence is weakened if every schema change still forces both services to release together. A meaningful boundary contains change as well as code.

Now scheduling accepts a slot but the reply is lost. Ticket management sees a timeout while scheduling has already changed state. A local rollback in ticket management cannot undo a remote commitment automatically. The design needs a way to discover the outcome, avoid duplicate reservations and recover from abandoned work. Trace this failure before celebrating a successful normal-path demo. Smaller services can make focused tests easier, while cross-service behavior requires contract tests, observability and explicit recovery policies. Compare these costs with the independence that motivated the split.

Teams, mocks and multiple clients

Source slides 11–14

Teams can agree on an API before implementing each side. A mock dependency lets client work proceed, but a mock represents assumptions rather than proof of compatibility. Define inputs, outputs, status behavior and error cases, then test those expectations against the real service. Instant, always-successful mocks hide timeouts and failures that matter in production.

The same backend API can support a browser, mobile app and desktop app. In a server-rendered design the backend prepares HTML; in an SPA much presentation logic runs in the browser and obtains data through APIs. Real applications can combine both approaches. Separating clients from services helps reuse, while authorization and validation must still be enforced by the server for every client type.

Worked walkthrough

The scheduling team supplies a mock API while the real service is under construction. The dashboard team can now build a booking screen, but an always-successful mock teaches the wrong assumptions. Include unavailable slots, invalid input and delayed responses in the contract. Then run the same expectations against the real implementation. A mock accelerates collaboration because it makes assumptions executable; it does not prove that the dependency behaves that way in production.

The same scheduling API can serve a browser dashboard and a technician’s mobile app. The browser may receive server-rendered HTML or construct its interface from API responses; a hybrid is also possible. In either case, the backend must enforce authorization and validate requested changes. Hiding an unavailable action in a button does not prevent a different client from sending that request. Review one complete workflow across both clients and check that resource identities, validation failures and permission rules mean the same thing on the shared service boundary.

Self-check

A deployment has 200 interchangeable app replicas behind a load balancer. Is it necessarily a microservice architecture?

No. Replicas of the same deployable application provide scale; microservices divide responsibilities across independently deployable services.

Checkout calls separate inventory and payment services. Why is failure handling harder than a single-database transaction?

One service may succeed while another fails or times out. A cross-service workflow needs explicit consistency and recovery choices, such as idempotent retries and compensating actions.

A mock service returns correct JSON but always succeeds immediately. What important tests are missing?

Contract edge cases, error/status behavior, timeouts, latency, version compatibility and integration with the real implementation.

Design exercise

A small team plans a new course-registration application. Compare a modular monolith with separate registration, payment, and notification services. Choose a starting design and define evidence that would justify changing it.

A modular monolith can keep local transactions and deployment simple while enforcing internal boundaries. Independent services may be justified by distinct ownership, scaling, or release needs, but require network contracts, observability, and partial-failure handling. Payment and registration coordination must be explicit. State team constraints and measure actual bottlenecks before treating distribution as an automatic improvement.

1. A release that must coexist

A parcel platform has independently deployed tracking and customer-support services. Tracking plans to replace the response field deliveryStatus with a richer object named progress. Support upgrades weekly, while tracking deploys daily. The old field remains inexpensive to produce for one month. Which release plan best preserves independent deployment without requiring every consumer to upgrade at the same moment?

  1. Rename the field immediately because services hide implementation details.
  2. Keep both fields temporarily, test compatibility and retire the old one after migration.
  3. Require both services to deploy in one atomic release forever.
  4. Change only the mock service because production clients will adapt automatically.

Worked answer

Best answer: B.

Publish the new progress field while retaining deliveryStatus with its existing meaning during a documented transition. Test both contracts, measure or inventory consumer adoption, and remove the old field only after the compatibility policy permits it. Consumers should tolerate additive fields where the contract allows. This separates deployment timing from a breaking interface change without maintaining duplicate behavior indefinitely. Coordinated releases can sometimes be justified, but they undermine the claimed independent-deployment benefit here. Renaming the field immediately or relying on mocks alone does not protect the still-running old support service.

Expand-then-contract evolution creates a compatibility interval across independently deployed components; the removal step still requires evidence and ownership.

Check your work

  • Choose additive compatible evolution.
  • Include evidence before removal.
  • Recognize independent deployment needs contract discipline.

2. Parallel calls do not remove every dependency

A dashboard endpoint first checks access in 20 ms, then fetches warehouse inventory in 90 ms and carrier status in 140 ms. The last two reads are independent and can run concurrently. Rendering takes 15 ms after both return. Ignore network variability and queueing. Calculate sequential and parallel response times, then propose behavior when the carrier call takes two seconds but warehouse data remains useful.

Worked answer

Sequential execution takes 20 + 90 + 140 + 15 = 265 ms. Running the independent reads together takes 20 + max(90, 140) + 15 = 175 ms, a 90 ms reduction under the stated assumptions. Parallelism does not remove the slowest dependency. Set a carrier deadline consistent with the page budget and return clearly marked partial or cached carrier information only if product requirements permit it. Preserve the access check before exposing either dataset. Bound outstanding calls and retries so a slow carrier does not accumulate unbounded work across dashboard requests.

This calculation concerns a dependency graph, not a throughput guarantee. Timeout and partial-result policies determine how the architecture behaves beyond the ideal timing case.

Check your work

  • Compute 265 ms and 175 ms correctly.
  • State partial-result/deadline semantics.
  • Bound dependency work while retaining authorization.

3. Independent code, shared schema

An insurance company labels claims and reporting as separate microservices. Both have write access to the same claim tables, and reporting updates a processed flag that claims uses to decide whether a record may be edited. A reporting schema migration now blocks claims releases. Identify the coupling and propose a staged boundary repair that keeps reporting available during migration.

Worked answer

The services share schema and business-invariant ownership, so separate processes have not produced independent change boundaries. Assign claim lifecycle state to one authoritative owner and expose a supported API or event contract for reporting. Give reporting a derived read model whose processing progress does not directly control claim edits. During migration, populate and validate the read model alongside the existing path, define acceptable lag and reconciliation, then remove reporting’s direct writes. Avoid an immediate database split without preserving semantics. If reporting truly controls an edit constraint, model that interaction explicitly instead of hiding it in a shared flag.

A boundary is defined by ownership and contracts as well as deployment. A derived reporting model can reduce coupling but introduces freshness and reconciliation obligations.

Check your work

  • Identify schema and invariant ownership coupling.
  • Propose explicit authority and contract.
  • Stage migration with reconciliation and lag semantics.
