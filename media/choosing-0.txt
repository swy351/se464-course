Choosing a data store
Part 1 • Synthetic narration

Start with workload and invariants

Storage selection is an architectural argument about the application, not a contest between database labels. Start with a small set of operations and their promises. Then choose the least complicated arrangement that can meet and operate those promises. A community workshop needs to reserve machines, search project descriptions and serve tutorial photographs. Reservations must not overlap for the same machine. Search can tolerate a short indexing delay, while photographs are large immutable objects once published. These are three access patterns within one product; the shared user interface does not imply identical storage requirements. Begin with a relational reservation store and object storage for photographs, then evaluate whether its existing text-search capability is sufficient. A separate search service becomes worthwhile only when requirements justify its indexing pipeline and recovery work. Record expected request rates, acceptable staleness, atomic operations and who operates each component. A technically capable store may still be a poor choice if the team cannot back it up, diagnose failures or restore it within the required time.

Transactions and concurrency

A transaction groups changes, while its isolation and update protocol determine how concurrent requests interact. We can see the distinction with a single projector. Follow the successful path, the competing request, and then the failure that occurs halfway through. A makerspace has one spare projector. Two requests each read available_count equal to one and both attempt a booking. Wrapping each request’s statements in a transaction gives all-or-nothing changes, but does not by itself specify isolation strong enough to prevent both from making the same decision. The read-and-update interaction needs deliberate concurrency control. One approach conditionally decrements the count only when it is positive, checks whether exactly one row changed, and creates the reservation in the same transaction. The database’s supported atomic update semantics must ensure competing updates are evaluated safely. The losing request reports unavailability rather than inserting a booking. If creating the reservation fails, the decrement rolls back. Retried requests also need a way to recognize an already committed booking rather than silently creating a second one.

Storage models and analytics

One dataset can support both immediate operations and broad analysis, but those workloads ask the hardware to do different work. Trace the columns required by a dashboard and then compare its freshness needs with the live delivery service. A delivery dashboard computes average journey time by district from 120 million events. It needs district, duration and date, but not the driver’s notes or the full delivery address. A column-oriented representation can read a smaller relevant subset and compress repeated values. The final result may contain only a few dozen rows, so aggregation near storage avoids transferring the entire event collection. The operational service instead checks and updates one delivery’s state repeatedly throughout the day. That is a different access pattern, even if both stores accept SQL. If analytics imports events every fifteen minutes, a dashboard can omit recent completed deliveries without either database being broken. Display the data’s freshness and use the operational source for decisions that require current state. Benchmark representative queries rather than assuming a storage layout makes every query faster.
